# OCR の Rust の試作 — 報告

捨てる前提の試作。コードは `ocr-spike/` だけにあり、マージしない。

## 入れ物

- CPU: Intel(R) Xeon(R) Processor @ 2.10GHz（クラウドの VM）、4 vCPU（1 コア 1 スレッド）、メモリ 15 GB。
- onnxruntime 1.26.0（`npm run layout:fetch`）、`ort =2.0.0-rc.15`（`load-dynamic`、`api-26`）。worker と同じ。
- スレッド数は worker の `load_session` と同じ決め方（`min(6, 論理 CPU − 1)`）で、この入れ物では **3**。spinning は切る、`Level3`。

## 項目 2: Det と Rec を Rust で通す

できたこと:

- PaddleOCR 3.x（PaddleX 3.7.2 のソースを読んで写した）の前処理・後処理を、`ort` の上で `Vec<f32>` / `&[f32]` のまま書いた。pure-onnx-ocr の型や tract は経由しない。
  - 画像は `cv2.imread` と同じく **BGR** で持つ。PaddleOCR は ImageNet の平均と分散を B, G, R の順に当てるので、RGB で持つと黙って入れ替わる。
  - 検出の縮小: `DetResizeForTest.resize_image_type0`（各辺を 32 の倍数に、Python の `round` なので 0.5 は偶数側へ）。`cv2.resize(INTER_LINEAR)` を固定小数点の丸めまで写した（[imgops.rs](src/imgops.rs) `resize_linear`）。
  - DB の後処理: `prob > 0.3` の二値画像 → 輪郭（穴も含む、`RETR_LIST` 相当）→ 最小面積矩形（短辺 3 未満は捨てる）→ 矩形の内側の平均確率が 0.6 未満は捨てる → 矩形を `面積 × 1.5 / 周長` だけ角を丸めて膨らませる（pyclipper の手順を写した）→ もう一度最小面積矩形（短辺 5 未満は捨てる）→ 軸ごとの倍率で元の画像の座標へ（[engine.rs](src/engine.rs) `db_boxes`、[geom.rs](src/geom.rs)）。
  - 並べ方: `SortQuadBoxes`（上から下、y の差が 10 px 未満なら左から右）。
  - 切り出し: 最小面積矩形の 4 点から透視変換で軸に平行な矩形に展開する（`cv2.warpPerspective` の `INTER_CUBIC`・`BORDER_REPLICATE`、小数の位置は 1/32 に量子化）。`h / w ≥ 1.5` なら左に 90° 回す（`np.rot90`）。
  - 認識: 縦横比の小さい順に並べ、6 行ずつ束ね、各行を高さ 48・幅 `ceil(48 × 縦横比)`（キャンバスの幅は `max(320, int(48 × 縦横比))`、上限 3200）に縮め、束の中で一番広い行に合わせて右を 0 で埋める（PaddleX の `ToBatch`）。正規化は `/255 − 0.5) / 0.5`。CTC は貪欲法で、確信度は出した文字の確率の平均。
- 照合の試験: [tests/parity.rs](tests/parity.rs)（`cargo test --release`）。PaddleOCR の既定（`limit_type=min`、`limit_side_len=64`、つまり等倍）で動かし、参照と同じ順で行の数・文字・4 隅を比べる。手で見るときは `cargo run --release -- parity --model small`。

数字（`ja.jpg`、PaddleOCR 3.7.0 の出力との比較）:

| モデル | 行の数（参照 / 自作） | 文字が完全に一致 | 並び順 | 4 隅が完全に一致 | 4 隅の最大のずれ |
| --- | --- | --- | --- | --- | --- |
| small | 56 / 56 | 56 / 56 | 同じ | 47 / 56 | 2 px |
| medium | 54 / 54 | 54 / 54 | 同じ | 47 / 54 | 2 px |

一致しない所と理由:

- 4 隅が 1〜2 px ずれる行が 7〜9 本ある。多くは 4 隅がそろって 1 px ずれている（大きさは同じ）。原因は OpenCV の `minAreaRect`・`boxPoints` が float32 で計算し、整数のはずの角が `334.99994` のようになり、pyclipper がそれを切り捨てて 334 にすること（入れ物の `opencv-python-headless` で `cv2.boxPoints` を呼んで確かめた）。誤差の向きは矩形ごとに違うので、固定のずれ（1e-4）を足すと一致は 47 本から 16 本に減った。完全に写すには OpenCV の float32 の計算の順序まで写す必要があり、文字には効かない（ずれた行も文字はすべて一致）ので、2 px を許容の幅にした。
- `general_ocr_002`（中国語の搭乗券）は画像が取れず、照合していない。

突き当たったこと:

- 照合の参照は PaddleOCR の既定（`min`・64、つまり等倍）で作られている。採用する設定（`max`・1600）とは違うので、試験は既定で動かし、ほかの項目は `max`・1600 で動かす。

## 項目 3: 速さとメモリ

できたこと:

- Python の最小のスクリプト [scripts/ocr_min.py](scripts/ocr_min.py)（`onnxruntime` 1.26.0、`numpy`、`opencv-python-headless` だけ）で、同じ手順（縮小 → DB の後処理 → 並べ替え → 透視変換で切り出し → 6 行ずつ束ねて認識 → CTC）を書いた。Rust は `cargo run --release -- bench`（[main.rs](src/main.rs) `bench`）。
- 測り方: ページごとに 3 回慣らして 5 回の中央値。Det は縮小・正規化 → 推論 → 後処理、Rec は切り出し → 正規化 → 推論 → CTC。どちらもセッションの設定は同じ（`Level3`／`ORT_ENABLE_ALL`、intra 3 スレッド、inter 1、spinning 切り）。
- クラウドの CPU は実行ごとの揺れが大きい（同じ処理が ±30 % 変わる）ので、Rust と Python を交互に 3 回ずつ走らせ、ページごとに 3 回の中央値を取った（[scripts/bench.sh](scripts/bench.sh)、[scripts/bench_summary.py](scripts/bench_summary.py)）。
- ページ: `ja.jpg`（1536 × 839）と XFUND の val の 4 枚（300 dpi の A4、2480 × 3508 など）。検出は長辺 1600。

数字（small、ms、3 回の中央値）:

| --- | --- | ---: | ---: | ---: | ---: | ---: |
| ja.jpg | 56 / 56 | 261 | 262 | 622 | 596 | 1.04 |

| ja_val_1 | 108 / 108 | 347 | 471 | 1584 | 2073 | 0.76 |

| ja_val_3 | 33 / 33 | 366 | 483 | 594 | 839 | 0.71 |
| 合計 | | 1704 | 2060 | 5851 | 6767 | **0.86** |

| 段階（5 ページの合計、ms） | Rust | Python |
| --- | ---: | ---: |
| det の前処理（縮小・正規化） | 157 | 200 |
| det の推論 | 1483 | 1826 |
| det の後処理 | 48 | 39 |

- **Rust の Rec は Python より遅くない**（合計で 0.86 倍、Det も 0.83 倍）。検証で見た「Rec が 2〜3 割遅い」は、自分で書いた前処理・後処理では起きなかった。ページごとの差（0.64〜1.34）はほとんどが推論の時間の揺れで、推論は同じ onnxruntime なので、言語の差ではない。検証の遅さは pure-onnx-ocr の tract の型からの変換や、テンソルの作り直しにあったと考えるのが自然（ここでは `Vec<f32>` を作って `Tensor::from_array` に渡し、出力は `try_extract_tensor` でコピーせずに読む）。
- 時間の 9 割は rec の推論。300 dpi の帳票は 1 ページ 2〜2.5 秒（small、3 スレッド）。検証の PC（P コア 6 スレッド）で約 0.9 秒だったのと比べ、この VM は 2〜3 倍遅い。
- Python と Rust の文字は、`ja.jpg` は完全に同じで、XFUND では 4〜7 行が違う。Python のスクリプトは unclip を「矩形を各辺に同じだけ広げる」と簡単にしていて（pyclipper を使わないため）、枠が 1 px 違う行で読みが変わる。Rust は項目 2 で PaddleOCR の出力と一致を確かめた方。

Rec を詰めた所:

| 試したこと | 結果 |
| --- | --- |
| CTC の argmax を `iter().max_by(total_cmp)` から 16 レーンの最大値探し（ベクトル化される）に | CTC の時間がおよそ半分（5 ページで約 400 → 202 ms） |
| 切り出しで、透視変換が整数の平行移動だけのとき（傾いていない行）は画素をそのまま写す | 結果は同じ（3 次補間の重みが [0, 1, 0, 0] になるため）。`ja.jpg` で 35 → 13 ms。スキャンは少し傾いていて一般の経路を通るので、XFUND では Python の 3 倍（cv2 は SIMD）が残る。全体の 2〜3 % |
| 束ねる行の数（5 ページの Rec の合計、2 回の中央値） | 1 行ずつ: 6137 ms・ピーク RSS 749 MiB／**6 行: 5325 ms・1115 MiB**／12 行: 6056 ms・1689 MiB |

- 束ねる数は PaddleOCR と同じ 6 が速い。12 にすると、幅の違う行が同じ束に入り、右の 0 埋めが増えて遅くなる。
- 幅の揃え方: 縦横比の順に並べてから束ねるので、0 埋めは小さい。32 の倍数に揃える工夫（pure-onnx-ocr にある）は、onnxruntime では計画のキャッシュがないので要らない。

メモリ:

- ピーク RSS（5 ページ）: Rust 1115 MiB、Python 1280 MiB。仮想メモリのピーク（Linux の worker は `RLIMIT_AS` で 2 GiB に制限している）は、6 行ずつで 1493 MiB、1 行ずつで 1093 MiB。`prlimit --as=2GiB` の下で 5 ページを通せた。
- メモリを食うのは rec の出力（束 × 時間 × 18,710 クラスの float）と途中の活性化。幅が 3200 の行が 6 本そろうと、出力だけで 6 × 400 × 18,710 × 4 B ≈ 180 MB になる。本番では束を「行の数」でなく「幅の合計」（例: 幅の合計 ≤ 6 × 1280）で切ると、幅の広い行の多い帳票でも上限を保てる。
- セッションの読み込み（det + rec、small）は 0.15 秒（ファイルがページキャッシュにある状態）。

## 項目 4: 精度（XFUND 日本語 val 50 枚）

できたこと:

- 正規化（NFKC、空白と改行の除去、`·` → `・`、`〜`・`～`・`~` を同じ字に）と編集距離を [cer.rs](src/cer.rs) に書いた。`cargo run --release -- xfund --model small` で 50 枚を数える（標準出力には数字だけを出す）。
- 正解の単位は XFUND の「塊」（`document[]` の各要素。キー・値・見出しなど。`box` と `text` を持ち、`words` に 1 文字ずつの箱がある）。

数字（small、長辺 1600）:

| 数え方 | CER |
| --- | --- |
| **文字ごとに対応付け**（予測の各文字の位置（項目 6 の CTC からの推定）の中心が入る正解の塊に配る。どこにも入らない文字は挿入） | **4.27 %**（1494 / 34956） |
| 行ごとに対応付け（予測の行を、その面積の半分以上が入る正解の塊に配る。どこにも入らない行は挿入） | 13.13 %（4590 / 34956） |

- 文字ごとの対応付けで **4.27 %** になり、検証の 4.31 %（small、1600、val 50 枚）とほぼ同じ。
- 1 ページの時間（この VM、3 スレッド、50 枚の中央値）: Det 377 ms、Rec 1330 ms。ピーク RSS 1278 MiB。

外れた理由を探したこと:

- 最初に書いた「行ごとに対応付け」では 13.13 % と大きく外れた。誤りの内訳を [scripts/xfund_breakdown.py](scripts/xfund_breakdown.py) で分けると、どの塊にも入らない行による挿入が 4.50 %、行の付かない塊の脱落が 5.08 %、付いた塊の中の誤りが 5.07 %。
- 「行の付かない塊」の文字 1777 字のうち 1622 字は、ほかの塊に配られた行に 30 % 以上覆われていた。帳票では「氏名　山田太郎」のようにキーと値が 1 行として検出されることが多く（2 つ以上の塊にまたがる行が 222 本）、行ごとに配ると片方の塊は脱落、もう片方は余分な文字として 2 回数えてしまう。本当に検出されなかったのは 155 字（0.44 %）だけだった。
- 検証の「対応付け CER」の細かい定義は分からないが、文字の位置で配る数え方で 4.31 % に近い値が出たので、前処理・後処理・モデルの読みは検証と同じと見てよい。
- アプリとしての含意: 帳票で「キーと値が 1 行になる」のは検出器の性質で、画面で文字を選ぶ・検索するときは困らない（文字ごとの位置があるため）。塊（項目 5）を作るときに、1 行を 2 つの塊に分けたいなら、文字の位置と行の中の大きな空白で切る必要がある。

## 項目 5: 縦書きの読み順

できたこと:

- 縦書きのページを 4 枚作った（[vertical.rs](src/vertical.rs)、`cargo run --release -- vertical`）。1654 × 2339 px（A4 を 200 dpi）。IBM Plex Sans JP（`node_modules/@ibm/plex-sans-jp` の woff を fontTools で OTF に戻した）で描き、句読点・括弧・小さいかな・長音は、フォントの `vert` の置き換え（[scripts/vert_map.py](scripts/vert_map.py) で抜き出した 971 字）で縦書きの字形にした。
  - v1: 右に大きな見出しの列（「羅生門」）と作者名、本文 1 塊。
  - v2: 上に横書きの柱、本文を上下 2 段に組む、下に横書きのノンブル。
  - v3: 見出しの列と、本文を 3 段に組む。
  - v4: 会話（「」）の多い本文 1 塊と、横書きの柱。
- 本文: 芥川龍之介「羅生門」、夏目漱石「吾輩は猫である」「坊っちゃん」、宮沢賢治「注文の多い料理店」の冒頭（著作権の切れた文）。**青空文庫は、サイト（`www.aozora.gr.jp`）も GitHub の写し（`aozorabunko/aozorabunko`）もこの入れ物から取れなかった**ので、文はこちらで書き起こした。正解は描いた文そのものなので、底本との細かい違いは測定に影響しない。
- 読み順の規則を [order.rs](src/order.rs) に書いた（ファイルの先頭のコメントが規則の全文）。要点:
  1. 向き: 行の縦横比が 1.5 以上なら縦、1/1.5 以下なら横。その間（1〜2 字）はページの多数派に合わせる。
  2. 塊: 同じ向きで太さ（縦書きは列の幅、横書きは行の高さ）が 1.3 倍以内の行のうち、読む向きと直角に隣り合う（すき間が太さ以下で、読む向きに 30 % 以上重なる）もの、または同じ列（行）で続くもの（すき間が太さ以下）をつなぐ。見出し（大きさが違う）と段（すき間が広い）は別の塊になる。
  3. 塊の中: 縦書きは列を右から左、列の中は上から下。横書きは行を上から下、行の中は左から右。
  4. 塊の間: 上下に重なる塊を「帯」にまとめ、帯を上から下へ。縦書きが多い帯は右から左（右端がそろう段は上から）。横書きが多い帯は、塊をまたいで行（row）ごとに上から下へ読み、行を塊にする。

数字（small、長辺 1600）:

| ページ | 行（うち縦） | 見つけた塊（正解） | ページ全文 CER: PaddleOCR の順 | 並べ替えたあと | 対応付け CER |
| --- | --- | --- | ---: | ---: | ---: |
| v1 見出し + 本文 | 6（6） | 3（3） | 75.44 % | 14.04 % | 14.04 % |
| v2 2 段 + 柱 + ノンブル | 14（12） | 5（4） | 75.21 % | 7.44 % | 7.02 % |
| v3 3 段 + 見出し | 18（18） | 4（4） | 81.82 % | 7.85 % | 7.85 % |
| v4 会話 + 柱 | 7（6） | 2（2） | 79.08 % | 11.30 % | 11.30 % |
| 合計 | | | **78.08 %** | **9.84 %** | 9.73 % |
| XFUND val 50 枚（横書き） | | | 29.62 % | 28.34 % | |

- 並べ替えで、縦書きのページ全文 CER は 78 % から 10 % になった。残りの 10 % は、並べ替え後の CER と対応付け CER がほぼ同じことから分かるとおり、読み順ではなく認識の誤り。
- XFUND（横書きの帳票）は並べ替えで悪くならない（29.62 % → 28.34 %）。XFUND の正解の順は注釈の順（`ja.val.json` の `document[]` の順）で、読み順そのものではないので、絶対値は大きい。比べる意味は「PaddleOCR の順より悪くならない」ことだけ。

突き当たったこと:

- 最初の規則では、横書きでも縦に積まれた行を 1 つの塊にしていて、XFUND が 29.62 % から **39.33 %** に悪くなった。帳票ではキーの列が 1 つの塊になり、値より先に全部読まれるため。横書きが多い帯は行ごとに読む規則（上の 4）に変えて直した。代わりに、横書きの 2 段組み（論文など）は段をまたいで行ごとに読んでしまう（PaddleOCR の今の順と同じ）。横書きの段組みを扱うなら、ページの上から下まで通る白い帯で切る（XY-cut）などの規則を足す必要がある。
- 認識の誤り（検証と同じ弱点）: 本文では、句読点「、」「。」と括弧「」」がすべて落ち、長音「ー」が落ちる（「ニャーニャー」→「二ヤ二ヤ」）、小さい「っ」の一部が落ちる（「あった」→「あた」）、「く」が「<」になる。
- 大きな字の短い見出しの列が読めない: 72 px の「羅生門」は「牒州C」、40 px の 5 字の「芥川龍之介」は「三體」になった（本文の 44 px の長い列は読める）。短い縦の列は、切り出しを 90° 回すと「横に寝た字が数個だけ」の画像になり、モデルが苦手としているように見える。縦の短い列だけ回さずに読む・PARSeq に回すなどを次に試す価値がある。
- v2 で、塊が正解より 1 つ多い（下の段の上に、1 字だけの行「6」が別の塊として出た）。本文のどこかの字を 1 字だけ検出したもので、正解の段とは太さが違い、つながらなかった。

## 項目 6: 結果の型と worker への入れ方の案

### 型

[types.rs](src/types.rs) に「ページ → 塊 → 行 → 単語 → 文字」の型を書いた（`OcrPage` → `OcrBlock` → `OcrLine` → `OcrWord` → `OcrChar`）。

- **座標は pt（表示の向きのページ、左上が原点、y は下向き）**。worker の `RectPt` と同じ空間。理由: (1) OCR に使った描画の解像度は内部の事情で、ページの大きさや 1600 px の上限で変わるが、pt は変わらない。(2) PDF に透明な文字の層を重ねるときは pt で書く。(3) 画面は切り出しの候補をすでに pt から換算しているので、Tauri のままでも Slint に移っても、選択や検索の強調に同じ換算を使える。
- 各階層に位置・文字・確信度・向き（`horizontal`／`vertical`）を持たせた。行・単語・文字の位置は 4 点（`QuadPt`）で持ち、行と塊には当たり判定用の `bbox` も持つ。スキャンが傾いていると行も傾くので、矩形より 4 点の方が選択と文字の層が文字に沿う。4 点は「読む向きの始まりから」並べる（横書きは左上・右上・右下・左下、縦書きは右上・右下・左下・左上）。
- 単語: 行の文字を空白で区切った並び。日本語は空白がないので、1 行が 1 単語（中に文字が並ぶ）になる。英語は単語に分かれる。
- `engine`（使ったモデルの名前）を持たせ、モデルを更新したときに保存した結果をやり直せるようにする。
- 例（v3 の縦書きのページ、先頭の塊の最初の行の最初の 2 字だけ残して、数字を丸めたもの）:

```json
{"widthPt": 595.0, "heightPt": 842.0, "engine": "PP-OCRv6_small",
 "blocks": [{"bbox": {"x0": 366.6, "y0": 58.0, "x1": 490.3, "y1": 248.0}, "orientation": "vertical",
   "lines": [{"quad": [[490.3, 58.3], [490.3, 247.3], [479.9, 247.3], [479.9, 58.3]],
     "bbox": {"x0": 479.9, "y0": 58.3, "x1": 490.3, "y1": 247.3},
     "orientation": "vertical", "text": "親譲りの無鉄砲で小供の時から", "confidence": 1.0,
     "words": [{"quad": [[490.3, 58.3], [490.3, 247.3], [479.9, 247.3], [479.9, 58.3]],
       "text": "親譲りの無鉄砲で小供の時から", "confidence": 1.0,
       "chars": [{"quad": [[490.3, 58.3], [490.3, 70.5], [479.9, 70.5], [479.9, 58.3]], "text": "親", "confidence": 1.0}, "..."]}]}]}]}
```

### 文字ごとの位置（CTC から推す）

- 方法（[types.rs](src/types.rs) `char_cells`）: CTC の出力の 1 時刻は、高さ 48 に縮めた切り出しの 8 列にあたる。各文字が出た時刻の範囲の中心を文字の中心とし、隣の文字との中点を境目にする。最初と最後の文字は、文字の間隔の中央値の半分だけ外へ広げる。行の中の位置（0〜1）を、行の 4 点の上の辺と下の辺（縦書きは右の辺と左の辺）に沿って補間してページの座標にする。縦書きは切り出しを 90° 回しているので、その分を戻す。
- 確かめ方: XFUND は 1 文字ずつの箱（`words`）を持つ。予測の行の文字が正解の塊の文字と完全に同じ行（1526 行、12,751 字）で、文字ごとに比べた（`cargo run --release -- chars`）。

| 方法 | 推定の箱の中心が正解の箱に入る | 平均 IoU |
| --- | ---: | ---: |
| CTC の時刻から推す | **99.6 %** | 0.655 |
| 行を字数で等分する | 72.7 % | 0.456 |

- 中心はほぼすべて正しい字の上に乗るので、画面での文字の選択・検索の強調・文字の層には足りる。IoU が 0.66 にとどまるのは、推定の箱が行の高さいっぱいで、正解の箱は字の形にぴったりだから（横の位置はよく合う）。
- 項目 4 の「文字ごとに対応付け」の CER（4.27 %）も、この位置を使って出した。
- 縦書きの文字の位置は数で確かめていない（縦書きのページでは句読点が落ちるので、文字の並びが正解と完全にそろう列がほとんどない）。

### worker への入れ方（案）

[proposal.rs](src/proposal.rs) に、`protocol.rs` に足す形で書いた（`protocol.rs` は変えていない）。

- 要求: `Ocr { page, model }`（開いている PDF のページ）。画像 → PDF に文字の層を付けるなら `OcrImage { path, page, model }`。`model` は `small`（既定）か `medium`。
- 答え: `Ocr { page: OcrPage }`。JSON をヘッダーで返す。大きさは、縦書きのページで 177 KB、文字の多い帳票（XFUND の 1 枚）で 560 KB（文字ごとの 4 点が大半）。`MAX_HEADER_BYTES`（1 MiB）に収まるが余裕は 2 倍ほど。本番では座標を 0.1 pt に丸める、文字の 4 点を「行の中の位置（u0, u1）」だけにするなどで数分の 1 にできる。
- エラーコード: `OcrUnavailable`（モデルか onnxruntime を読めない、または推論に失敗）。`LayoutUnavailable` と分けるのは、OCR のモデルは別の取得物になり、画面でどちらが欠けているかを言い分けたいため。core の `ErrorCode` に 1 行足す。
- 描画の解像度: worker はページを**長辺 1600 px** で描いて、そのまま検出と認識に渡す。XFUND を先に長辺 1600 px に縮めてから OCR に通すと、CER は **4.02 %**（300 dpi の元の画像のままだと 4.27 %、長辺 2400 px だと 4.38 %）。認識は高さ 48 に縮めるので、高い解像度で描いても読みは良くならない。描画のメモリと時間も小さくて済む（A4 で約 137 dpi）。
- 時間の上限: `OCR_TIMEOUT`（`DETECT_TIMEOUT` と同じ 60 秒、最初のモデルの読み込みを含む）。この VM（4 vCPU、3 スレッド）で、文字の多い A4 が small で 1.4〜2.5 秒。
- メモリ: small・6 行ずつで、ピーク RSS 1.1〜1.3 GB、仮想 1.5 GB。worker の上限（2 GiB）には収まるが、pdfium の描画と同時に持つと余裕は小さい。束を「幅の合計 ≤ 6 × 1280」で切れば、幅の広い行が続くページでも rec の出力を 1 束 70 MB ほどに抑えられる（`OCR_REC_BATCH_MAX_WIDTH_SUM`）。1 行ずつにすると仮想 1.1 GB まで下がるが 15 % 遅い。

## 項目 7: medium と、pdfium で描いてから OCR

### medium（項目 3・4 をもう一度）

| | small | medium |
| --- | ---: | ---: |
| XFUND val 50 枚の CER（文字ごとに対応付け） | 4.27 % | **3.62 %** |
| 検証の値（val 50 枚） | 4.31 % | 3.42 % |
| 1 ページの中央値（XFUND 50 枚、この VM、3 スレッド） Det / Rec | 377 / 1330 ms | 1571 / 5088 ms |
| 5 ページの合計（Rust）Det / Rec | 1704 / 5851 ms | 7823 / 21575 ms |
| 同（Python）Det / Rec | 2060 / 6767 ms | 9280 / 25301 ms |
| Rec の Rust / Python | 0.86 | 0.85 |
| ピーク RSS（Rust、6 行ずつ） | 1115 MiB | 1939 MiB |
| 仮想メモリのピーク（Rust） 6 行／2 行／1 行ずつ | 1493／—／1093 MiB | **2652**／1886／1757 MiB |
| モデルの大きさ（det + rec） | 31 MB | 139 MB |
| セッションの読み込み | 0.15 s | 0.40 s |

- medium は 0.65 ポイント良いが、約 4 倍遅く、モデルは 4.5 倍。
- **medium を 6 行ずつ束ねると、仮想メモリが 2.65 GB になり、worker の `RLIMIT_AS`（2 GiB）を超える**。2 行ずつ（1.89 GB）・1 行ずつ（1.76 GB）なら `prlimit --as=2GiB` の下で通ったが、pdfium の描画を足すと余裕はほとんどない。medium を選べるようにするなら、OCR だけ上限の違う worker にするか、束を幅の合計で小さく切るかが要る。
- medium の速さは Rust と Python を 1 回ずつしか測っていない（時間の都合）。また、Rust の 1 回目の途中で pdfium の試験のビルドが重なった。比はページごとに 0.56〜1.08 とぶれている。

### pdfium で PDF のページを描いてから OCR

- `npm run pdfium:fetch`（chromium/8125）で pdfium を取り、`pdfium-render`（worker と同じ 0.9 系、`pdfium_7881`）で描いた（[pdf.rs](src/pdf.rs)、`cargo run --release -- pdf --page v3_three_tiers`）。
- スキャンの PDF を模して、項目 5 の縦書きのページを JPEG（品質 90）にして A4 の PDF に 1 枚貼り、長辺 1600 px（1131 × 1600）で描いて OCR に通した。

| ページ | 入力 | 行 | 塊 | 並べ替えたあとのページ全文 CER | Det / Rec |
| --- | --- | ---: | ---: | ---: | --- |
| v3 | PNG（1654 × 2339） | 18 | 4 | 7.85 % | 464 / 507 ms |
| v3 | PDF → pdfium（1131 × 1600） | 18 | 6 | 6.61 % | 433 / 452 ms |
| v2 | PNG（1654 × 2339） | 14 | 5 | 7.44 % | 435 / 570 ms |
| v2 | PDF → pdfium（1131 × 1600） | 14 | 5 | 7.85 % | 383 / 599 ms |

- 描画は 53〜58 ms（pdfium の読み込みを含む）。結果の座標は pdfium の返すページの大きさ（pt）で `OcrPage` にした。
- v3 で塊が 6 つになった（正解は 4）。解像度が下がって行の太さの比が変わり、段の中の短い列が別の塊に分かれた。文字の順は崩れていない（CER は下がった）。

## まとめ

### 1. 本番に入れるときの作り

- **置き場所**: `crates/worker/src/ocr/`（`layout.rs` と並べる）。中身は、この試作の `engine.rs`（det・rec・CTC）、`geom.rs`（最小面積矩形・unclip・矩形内の平均）、`imgops.rs`（OpenCV と同じ縮小・透視変換）、`order.rs`（読み順）、`types.rs`（結果の型）。セッションは `layout.rs` の `Detector` と同じく、最初の `Ocr` の要求で読み込み、失敗したら以後は同じエラー（`OcrUnavailable`）を返す。onnxruntime の `Environment` は 1 プロセスに 1 つしか作れないので、layout と OCR で共有する作りにする（今の `load_session` は自分で `init_from` を呼んでいるので、ここを分ける必要がある）。
- **要求と答え**: 項目 6 の案（`Ocr { page, model }` → `Ocr { page: OcrPage }`、`OcrUnavailable`、`OCR_TIMEOUT` 60 秒）。ページは worker が長辺 1600 px で描く（OCR の精度は 300 dpi と変わらず、むしろ良い）。
- **輪郭の抽出**: 試作は `imageproc`（MIT）の `find_contours` を使った。本番では、二値画像の連結成分（8 近傍）と穴の扱いを自分で書けば依存を増やさずに済む（100 行ほど）。`imageproc` は `nalgebra` などを引き込むので、自作を勧める。
- **辞書**: rec の `inference.yml` の辞書を、配るときに 1 行 1 字のテキストにしておけば、YAML の読み込み（`yaml-rust2`）は要らない。
- **モデルの配り方**: 今の `layout:fetch` と同じく、GitHub のリリースに置き、`npm run ocr:fetch`（仮）で取る。small は det 9.9 MB + rec 21.2 MB + 辞書 0.1 MB ≈ **31 MB**（medium は 139 MB）。ライセンスは Apache-2.0（PaddleOCR）で、`ThirdPartyNotices` に足す。int8 への量子化（layout では 130 → 34 MB）は試していない。
- **初回の読み込み**: small で 0.15 秒、medium で 0.40 秒（ファイルがキャッシュにあるとき）。最初の要求の時間に含めても問題にならない。
- **スレッド**: worker と同じ `min(6, 論理 CPU − 1)`。

### 2. 残る弱点と次に試すこと

- **縦書きの記号の脱落**（検証と同じ）: 「、」「。」「」」「ー」がすべて落ち、小さい「っ」の一部が落ちる。縦書きのページの CER は、読み順を直しても約 10 %。次は NDLOCR-Lite の PARSeq に縦長の行だけ回すことを試す（検証では縦書きが良くなった）。この試作の型では、行ごとに使ったモデルを替えても結果の形は変わらない（CTC でないモデルは文字の位置が出ないので、行を字数で等分する。項目 6 の比較で中心の一致は 73 %）。
- **大きな字の短い縦の見出し**が読めない（「羅生門」→「牒州C」）。短い縦の列は回さずに読む、または PARSeq に回すを試す。
- **横書きの段組み**は、読み順の規則が行ごとに読むので、段をまたいでしまう（PaddleOCR の今の順と同じ）。XY-cut などの規則を足す必要がある。帳票（XFUND）は、PaddleOCR の順より悪くならないことだけを確かめた。
- **キーと値が 1 行になる**: 帳票では 2 つの塊にまたがる行が多い（222 本）。文字の位置はあるので選択・検索には困らないが、塊を意味の単位にしたいなら、行の中の大きな空白で切る処理が要る。
- **メモリ**: small は worker の 2 GiB に収まるが、medium は束を小さくしないと超える。束を幅の合計で切ることを本番で入れる。
- **4 隅の 1〜2 px のずれ**（OpenCV の float32 の計算）は残る。文字には効かない。
- 測っていないこと: Windows・macOS での速さ（この試作は Linux の VM だけ）、int8 の量子化、縦書きの文字の位置の精度、`general_ocr_002`（中国語）との照合。

## 項目 8: 縦書きの行に NDLOCR-Lite の PARSeq を使う

### 作ったもの

- NDLOCR-Lite（`github.com/ndl-lab/ndlocr-lite`、**`d001dad`**（2026-10-08）で取得。今の `main` より 6 コミット前）の PARSeq を、`ort` の上で動かした（[parseq.rs](src/parseq.rs)）。モデルはリポジトリに入っていた（Git LFS ではない）ので、`git clone` で取れた。拒否はなかった。
- 3 つのモデルの入力と出力は、ファイルから読み取った（決め打ちしない）。読み取った値:

| モデル | 入力（N × C × H × W） | 出力（N × 時刻 × クラス） | 出せる字数 |
| --- | --- | --- | ---: |
| `parseq-ndl-24x256-30-tiny-…` | 1 × 3 × 24 × 256 | 1 × 31 × 7142 | 30 |
| `parseq-ndl-24x384-50-tiny-…` | 1 × 3 × 24 × 384 | 1 × 51 × 7142 | 50 |
| `parseq-ndl-24x768-100-tiny-…` | 1 × 3 × 24 × 768 | 1 × 101 × 7142 | 100 |

- 前処理と後処理は NDLOCR-Lite の `parseq.py` と同じ: 切り出しを入力の大きさに縦横比を保たずに伸ばし、RGB、`x / 127.5 − 1`。各時刻の argmax を最初の EOS（0）まで読み、クラス `i` は `NDLmoji.yaml` の `charset_train` の `i − 1` 番目（7,141 字。「、」「。」「」」「ー」と小さいかなを含む）。確信度は、出した字のソフトマックスの確率の平均。
- 振り分け: 縦の行（切り出しの `h / w ≥ 1.5`、PP-OCR の規則と同じ）だけを PARSeq に回す。横の行は PP-OCR のまま。PP-OCR の切り出しで縦の行はすでに左に 90° 回っているので、PARSeq の中では回さない。
  - モデルの選び方: 回したあとの切り出しの `w / h` を字数の見積もりとし、見積もり + 5 字が入る一番小さいモデルから読む。結果がモデルの上限に近い（30 字のモデルで 25 字以上、50 字で 45 字以上）なら、次のモデルで読み直す（NDLOCR-Lite の `process_cascade` と同じ）。100 字で 98 字以上のときに半分に割る処理は入れていない。
  - 横書きと判定した正方形に近い切り出し（`h > 0.8 w`）は左右に白を足して回さない、という 10 月の処理も `Parseq::read` に入れたが、この構成では縦の行（回したあとは `w ≥ 1.5 h`）しか来ないので、通ることはない。
- PP-OCR の読みは縦の行でも残す（文字の位置の推定に使うため。下の (4)）。

### (1) 縦書きの 4 ページ

| ページ | 並べ替えたあとのページ全文 CER: small だけ | small + PARSeq | 対応付け CER: small だけ | small + PARSeq |
| --- | ---: | ---: | ---: | ---: |
| v1 見出し + 本文 | 14.04 % | 1.75 % | 14.04 % | 1.75 % |
| v2 2 段 + 柱 + ノンブル | 7.44 % | 2.48 % | 7.02 % | 2.07 % |
| v3 3 段 + 見出し | 7.85 % | **0.00 %** | 7.85 % | **0.00 %** |
| v4 会話 + 柱 | 11.30 % | 0.42 % | 11.30 % | 0.42 % |
| 合計 | **9.84 %** | **1.12 %** | 9.73 % | 1.01 % |

- **句読点・括弧・長音**: small では「、」「。」「「」「」」がすべて落ちていたが、PARSeq ではすべて出た。長音も「スー」「タンタアーン」「弱虫やーい」は正しい。小さい「っ」（「あった」「帰って」「云った」）も正しい。
- **大きな字の短い見出し**: 「羅生門」（72 px、small では「牒州C」）と「芥川龍之介」（40 px の 5 字、small では「三體」）が、どちらも正しく読めた。v3 の見出し「坊っちゃん」も正しい。
- 残った誤り: 「ニャーニャー」→「二ヤー 一ヤー」、「蟋蟀」→「蟋蜂」、「揉烏帽子」→「操烏帽子」、「もう」→「ちう」、「鳥も」→「烏も」。字形の近い漢字と、カタカナの「ニ」を漢字の「二」と取る誤り。
- PARSeq の出力には空白が混じることがある（「が、 朱雀大路」）。CER の正規化で空白を除くので数字には効かないが、文字の層や検索では除く必要がある。

### (2) XFUND（横書きの帳票）が悪くならないこと

| 構成 | 文字ごとに対応付けた CER | 行ごとに対応付けた CER |
| --- | ---: | ---: |
| small だけ | 4.27 % | 13.13 % |
| small + PARSeq（ガードなし） | 4.42 % | 13.27 % |
| **small + PARSeq（ガードあり）** | **4.11 %** | 12.96 % |

- XFUND の val 50 枚には、縦と判定される行が 69 本ある（全 3,798 本のうち）。縦に書かれた注意書き・欄の名前（PARSeq は「っ」「ー」「（）」を足して正しくした）のほかに、**縦長の 1 字**（数字・記号。`h / w` が 1.5〜1.9）と、**縦の点線（リーダー）**がある。
- ガードなしでは、1 字の切り出しに PARSeq が字を足し（「2」→「20」、「1」→「11」）、点線では上限の 100 字まで点を出した。そのため 4.27 % から 4.42 % に悪くなった。
- ガード（[engine.rs](src/engine.rs) の `PARSEQ_MIN_CTC_CHARS`・`PARSEQ_RUNAWAY_SLACK`）: PP-OCR が 1 字と読んだ行と、PARSeq の字数が PP-OCR の 2 倍 + 3 を超えた行は、PP-OCR の読みを残す。69 本のうち 21 本が PP-OCR のままになり、CER は **4.11 %**（small だけより良い）になった。縦書きの 4 ページの結果は、ガードを入れても悪くならなかった（9.84 % → 1.45 % が 1.12 % に。v2 で 1 字だけ検出された行「6」を PARSeq が「10.0」と読んでいたのが、PP-OCR の読みに戻った）。
- ガードは XFUND を見て決めたので、この 50 枚には合わせすぎている可能性がある。別の帳票で確かめる必要がある。

### (3) 大きさ・読み込みの時間・メモリ

- **モデルの大きさ**: 3 つで 116.9 MB（36.5 + 37.8 + 42.6 MB）。字の表 `NDLmoji.yaml` は 30 KB ほど。small（31 MB）と合わせて約 148 MB。
- **読み込みの時間**: 3 つをそのまま読むと **6.6〜9.4 秒**かかった。ノードを数えると、PARSeq の ONNX は自己回帰の復号を出せる字数の分だけ展開していて（30 字 7,606 ノード、50 字 11,986、100 字 22,936。PP-OCR の rec は 481）、読み込みはグラフの大きさに比例する。最適化を弱めるとかえって遅くなった（最適化なしで 24.5 秒）。
  - onnxruntime で一度最適化したグラフ（`ORT_ENABLE_EXTENDED`、ハードウェアに依らない段階まで）を保存し、それを読むと **2.3〜3.0 秒**に縮んだ（推論の速さは同じ。ファイルは 113.5 MB）。この試作では入れ物の Python の onnxruntime 1.26.0（Rust と同じ版）で保存した（`models/parseq_opt/`、git には入れない）。本番では配る前に保存しておくか、`SessionBuilder::with_optimized_model_path` で最初の起動時に保存する。
  - さらに縮めるには、最初の縦の行が来るまで読み込まない、100 字のモデル（読み込みの半分）は 50 字で埋まったときだけ読む、が効く。
- **速さ**: 縦書きの 4 ページで、PARSeq は合わせて 2.4 秒（約 45 行、1 行 55 ms ほど。束ねられない（入力の N が 1 に固定）ので 1 行ずつ）。縦書きのページは 1 枚 0.4 秒（Det）+ 0.6 秒（PP-OCR の rec）+ 0.6 秒（PARSeq）ほど。XFUND と `ja.jpg` の 5 ページでは、PARSeq は合わせて 34 ms で、横書きのページの速さはほとんど変わらない。
- **メモリ**（9 ページ: XFUND 4 枚・`ja.jpg`・縦書き 4 枚、`prlimit --as=2GiB` の下）:

| 構成 | ピーク RSS | 仮想メモリのピーク | 2 GiB の下で |
| --- | ---: | ---: | --- |
| small だけ（今までの設定） | 1555 MiB | 2018 MiB | 通る（余裕 30 MiB） |
| small + PARSeq | 1775 MiB | **2673 MiB** | **落ちる**（PP-OCR の rec で 147 MB の確保に失敗） |
| small + PARSeq、PP-OCR は 1 行ずつ | 972 MiB | 1740 MiB | — |
| small だけ、onnxruntime の CPU アリーナを切る | 552〜578 MiB | 853〜878 MiB | 通る |
| **small + PARSeq、全セッションのアリーナを切る** | **753 MiB** | **1485 MiB** | **通る**（2 回とも） |

- メモリの大半は onnxruntime の CPU アリーナ（一度使った最大の大きさを抱え続ける）だった。`ort::ep::CPU::default().with_arena_allocator(false)` で切ると、small だけでも RSS が 1.5 GB から 0.55 GB に下がり、速さの差はこの VM の揺れ（±30 %）より小さかった。**PARSeq を入れるかどうかに関係なく、本番ではアリーナを切ることを勧める**。layout のセッション（`crates/worker/src/layout.rs`）にも同じことが言えるはず（測っていない）。

### (4) PARSeq の行の文字の位置

PARSeq は注意機構で 1 字ずつ出すので、CTC のような「どの列で出たか」がない。3 つの方法を試した（[parseq.rs](src/parseq.rs)、`--cells even|projection|aligned`）。縦書きの 4 ページは字の位置が正確に分かる（1 字は字の大きさの正方形）ので、PARSeq の字と正解の字を編集の経路で対にし（867 字）、比べた（`cargo run --release -- vchars`）。

| 方法 | 推定の中心が正解の字の中 | 列の向きの 1 次元 IoU の平均 |
| --- | ---: | ---: |
| 等分（行を字数で割る） | 97.2 % | 0.824 |
| 墨の投影（列の向きに墨の量を足し、等分の位置の ±30 % の中で一番白い所で切る） | 95.2 % | 0.743 |
| **PP-OCR の読みと対にする**（PARSeq の文字列と PP-OCR の文字列を編集の経路で対にし、同じ字は PP-OCR の CTC の位置を使う。PP-OCR が落とした字（句読点など）は、前後の対になった字の間を等分する） | **99.3 %** | 0.810 |

- PP-OCR と対にする方法が一番よい。縦の行でも PP-OCR の rec を走らせる必要があるが、どのみち 1 字の行と暴走のガードに PP-OCR の読みを使うので、追加の手間はない。
- この合成のページは全角の字が等間隔に並ぶので、等分に有利（97 %）。実際の文書では、半角の数字や英字が混じると等分はずれる。墨の投影は、「川」「小」のように字の中にすき間がある字と、小さな句読点で切る位置を間違える。

### (5) ライセンスと帰属の表示

- **NDLOCR-Lite**（プログラムと学習済みのモデル）: 国立国会図書館が **CC BY 4.0** で公開（`LICENCE`、README）。アプリに同梱するなら、`ThirdPartyNotices` などに次を載せる: 作品名（NDLOCR-Lite の PARSeq の学習済みモデル）、権利者（国立国会図書館）、ライセンス（CC BY 4.0 と、その URL）、元の場所（`https://github.com/ndl-lab/ndlocr-lite`）、**改変の有無**（onnxruntime で最適化したグラフに変えて配るなら「改変した」と書く）。CC BY 4.0 は MIT のアプリと一緒に配ることができる。`deny.toml` はクレートのライセンスだけを見るので、モデルのファイルは対象外（`about.toml` の表記とは別に手で足す）。
- README は、レイアウトのモデル（DEIM）のバックボーンに DINOv3 を使っているので DINOv3 のライセンスにも従うよう求めているが、これは**レイアウトのモデルだけ**で、PARSeq には当たらない。この試作は DEIM を使っていない。
- PARSeq の元の実装（`baudm/parseq`、Apache-2.0）のコードは使っていない（Rust で書いた前処理・後処理は NDLOCR-Lite の `parseq.py` の手順を写したもの）。
- 依存は増やしていない（`yaml-rust2` で `NDLmoji.yaml` を読む。配るときに字の表を素のテキストにすれば要らない）。Python 側は、グラフの数えと保存の確認に `onnx`（Apache-2.0）・`pyyaml`（MIT）を `.venv` に入れただけ。

### まとめ（項目 8）

- 縦書きは、PARSeq を縦の行にだけ回すと、句読点・括弧・長音・小さいかなと短い見出しがほぼ直り、ページ全文 CER が 9.84 % から 1.12 % になった。横書きの帳票は、ガードを入れれば悪くならない（4.27 % → 4.11 %）。
- 本番に入れるときの条件: (a) 全セッションの CPU アリーナを切る（切らないと worker の 2 GiB を超える）、(b) 最適化したグラフを配るか最初に保存する（読み込み 7〜9 秒 → 2〜3 秒）、(c) PARSeq は最初の縦の行で読み込む、(d) 1 字と暴走のガード、(e) 文字の位置は PP-OCR の読みと対にして出す、(f) 出力の空白を除く、(g) CC BY 4.0 の帰属の表示。
- 手間の見積もり（項目 7 の表に加えて）: PARSeq の移植・ガード・文字の位置で 3〜4 日、モデルの配り方（最適化したグラフ、遅延の読み込み）と帰属の表示で 1 日。

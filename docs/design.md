# 詳細設計書

対応する要件は [requirements.md](requirements.md) の ID（FR-xx / NFR-xx）で示す。画面の見た目は [mockup/project/](mockup/project/)（各画面の `.dc.html`）を正とする（`Accent*.dc.html` は色を選んだときの比較で、画面の仕様ではない）。方式の根拠は [spike-report.md](spike-report.md) にある。定数は名前で示し、値はコードが正本とする（値を決めた理由は、ここに残す）。

**この文書の書き方**

- design.md には、変えるべきでない決まり（プロセスの境界、セキュリティ、IPC の契約、エラーコード、保存とキャンセルの保証、依存の方針、テストの方針）と、その理由を置く。
- 実装の細部（定数の値、内部の関数の形、画面の見た目と文言、細かな振る舞い）の正本は、コード・テスト・モックアップ・辞書とする。design.md は定数を名前で示し、値を決めた理由だけを残す。
- 新しい機能の設計は、機能ごとの短い文書 `docs/design/<機能名>.md` に書き、design.md の決まりと矛盾させない。決まりを変える必要があるときは、先に design.md を直す。
- だれがいつ決めたかは書かず、コミットのメッセージと PR に残す。

## 1. 全体構成

```
┌──────────────── メインプロセス（Tauri アプリ） ────────────────┐
│  WebView（React + TypeScript）                                  │
│   ・一覧、設定、進捗の表示。ファイルパスを扱わない（ID のみ）    │
│            │ invoke / event（IPC）                              │
│  Rust（src-tauri）                                              │
│   ・ダイアログ、D&D、パスと ID の表、設定、変換の実行管理        │
│   ・画像 → PDF（crates/core を呼ぶ。pdfium は使わない）           │
│   ・ワーカーの起動・監視・強制終了                              │
│            │ 標準入出力（§5.1 のメッセージ）                    │
└────────────┼────────────────────────────────────────────────────┘
             │  1〜N 個
┌────────────┴──────── ワーカープロセス（同じ実行ファイル） ──────┐
│  `pdf-converter --pdf-worker` で起動。WebView を作らない          │
│   ・pdfium で PDF を開く、ページ数・大きさを返す                 │
│   ・ページを描画し、画像にして返す（サムネイルも同じ）           │
│   ・切り出しの範囲の描画、埋め込み画像の一覧、レイアウトの解析   │
│     （onnxruntime。§4.6、§4.7）                                   │
│   ・ファイルを書かない。読むのは渡された PDF 1 つだけ             │
└──────────────────────────────────────────────────────────────────┘
```

- PDF の読み込みと描画は、すべてワーカーで行う。pdfium が壊れた PDF で異常終了しても、終了するのはワーカーだけで、アプリは動き続ける（NFR-01）。無限ループとメモリの使いすぎも、時間とメモリの上限（§5.3）でワーカーごと止める。
- 画像 → PDF と画像の一覧のサムネイルは、画像の読み込み（image）と PDF の書き出し（krilla）がどちらも純 Rust なので、メインプロセスで行う。純 Rust で防げるのはメモリの破壊までで、画像も PDF と同じく外から来るファイルなので、次のように抑える。
  - 画素数を `MAX_IMAGE_PIXELS` 以下に限る（§4.1）。変換とサムネイルの直前にもヘッダーを読み直すので、寸法を偽った画像でも画素のバッファはこれを超えない。
  - 同時に読む画像は、§5.3 のデコードの予算に収める。
  - デコーダーの panic は、変換では `catch_unwind` で、サムネイルでは別のスレッドの失敗として受け、その画像の失敗にする。アプリは終了しない。
  - 抑えられないもの（受け入れている危険）: 予算より大きい 1 枚（上限の 16 ビットの PNG で約 2.3 GB）をメモリの少ないマシンで読んで確保に失敗したときの abort、デコーダーが極端に遅いか止まったときに時間切れがないこと（変換が終わらず、その画像の書き出しの間はキャンセルも効かない）、スタックの使い切りなど panic にならない異常終了。どれもアプリが終了するか止まるだけで、保存は §6.5 のとおり途中のファイルを残さない。画像は利用者が選んだ手元のファイルが主で、PDF ほど細工した入力に使われにくいので、ワーカーに移す作りの大きさ（PDF の組み立てと受け渡し、メモリの上限との釣り合い）に見合わないと判断している。
- 切り出し（FR-11）のレイアウトの解析も、ワーカーで行う。入力は信頼できない PDF を描いた画素で、onnxruntime は C++ のライブラリなので、異常終了をワーカーに閉じ込めるため。
- 変換の処理は Tauri に依存しない crate `crates/core` に置く（SVG Tracer の `crates/tracer` と同じ考え方）。WebKitGTK なしに `cargo test` できる。
- フロントエンドはファイルパスを Rust に渡さない。ダイアログと D&D は Rust で受け、パスは Rust の表に登録して ID だけを返す（SVG Tracer §6 と同じ）。

## 2. 技術選定

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| アプリ基盤 | Tauri 2 | 要件で決定済み |
| PDF の描画 | `pdfium-render` + bblanchon/pdfium-binaries（版を固定、§8） | スパイクで決定。暗号化された PDF を開ける、速い |
| PDF の書き出し | `krilla`（`raster-images` 機能） | スパイクで決定。JPEG を再圧縮せずに入れられる、純 Rust |
| PDF の暗号化 | `lopdf`（既定の機能なし）、`getrandom` | krilla も pdfium も暗号化した PDF を書けないため（§4.3.1）。純 Rust で、AES-256（revision 6）を持つ |
| 画像の読み込み | `image`（png、jpeg、webp、bmp 機能のみ） | 寸法・EXIF の向きの取得、BMP の読み込み、PDF → 画像の PNG / JPEG / WebP の書き出し |
| TIFF の読み込み | `tiff`（deflate、fax、jpeg、lzw 機能のみ） | `image` は TIFF の最初のページしか読まないため（§4.1.1）。純 Rust で、ファクスの G4 も読める |
| レイアウトの解析（切り出しの候補） | PP-DocLayout_plus-L（PaddlePaddle、Apache-2.0）を int8 に量子化したもの（§8.5）を、onnxruntime 1.26.0（Microsoft の公式のビルド、MIT）で動かす。Rust からは `ort`（`=2.0.0-rc.14`、`load-dynamic`、`api-26`） | 埋め込み画像の下調べ（2026-10-16）で、図・グラフ・表の 87 % の範囲が合い（論文・白書は 99 %）、int8 でも元のモデルとの一致が 99.7 %、ファイルは 130 MB から 34 MB になった。より小さい PP-DocLayout-M・S は 4 割前後を取りこぼした。`ort` は ocr-bench（OCR の検証）と同じ版で、同じ入力で Python の onnxruntime と同じ箱を出した |
| 並列処理 | `std::thread` とチャネル | ワーカーはプロセスなので、スレッドプールのライブラリは要らない |
| 一時ファイル | `tempfile` | 原子的な保存（§6.5） |
| IPC 型共有 | `ts-rs` | SVG Tracer と同じ |
| フロントエンド | React + TypeScript + Vite、素の CSS + CSS カスタムプロパティ | SVG Tracer と同じ。部品と仕組みを流用する |
| フロントエンドのテスト | Vitest + Testing Library + jsdom、`@tauri-apps/api/mocks` | SVG Tracer と同じ |
| ライセンス | `cargo-about`、`cargo-deny`、`license-checker-rseidelsohn`、pdfium の同梱ライセンス（§8.3） | NFR-05 |

- ライブラリは実装開始時点の最新安定版とし、`Cargo.lock` と `package-lock.json` をコミットして固定する。
- `pdfium-render` の pdfium の API の版を選ぶ機能（`pdfium_NNNN`）は、同梱する pdfium の版以下で最も新しいものを明示する（2026-10 時点では、同梱の 8076 に対して `pdfium_7881`。スパイクはこの組み合わせで動いた）。`pdfium_latest` は使わない（crate の更新で API の版が同梱の pdfium より新しくならないようにするため）。
- Tauri のプラグインは `tauri-plugin-dialog` だけを使い、Rust 側からだけ呼ぶ（§9）。
- `ort` はリリース候補の版（2.0.0-rc）しかない（2026-10 時点）。版を `=` で固定し、安定版が出たら §9 の依存の入手経路の規則（公開から 7 日）で移る。onnxruntime は実行時に読み込み（`load-dynamic`）、`ort` の既定のビルド時の取得（pyke の配布物）は使わない（§8.5 で版とハッシュを固定して取得するため）。

## 4. 変換の処理（crates/core）

### 4.1 画像の読み込み（FR-01、FR-02）

- 対象の拡張子は `png` `jpg` `jpeg` `webp` `bmp` `tif` `tiff`（大文字小文字を区別しない）。定数 `IMAGE_EXTENSIONS` にまとめる。
- 形式は中身の先頭バイトで判定する。判定できない、または上記以外の形式なら `UnsupportedFormat`。
- 一覧に追加するときは、ヘッダーだけを読んで、形式、寸法、EXIF の向き、解像度（dpi）を得る（`probe`）。画素は読まない。読めなければ `DecodeFailed`。ヘッダーより後ろだけが壊れているファイル（`corrupt.png`）は `probe` を通り、画素を読む変換のとき（§4.3）に `DecodeFailed` になる。
- 総ピクセル数の上限は `MAX_IMAGE_PIXELS`。A3 を 600 dpi で読み取った画像が収まる大きさにする。超えたら `TooLarge`。
- 解像度は横（`dpi_x`）と縦（`dpi_y`）を別々に持ち、PNG の `pHYs`、JPEG の JFIF の密度または EXIF の `XResolution`・`YResolution`、BMP のヘッダー、TIFF の `XResolution`・`YResolution`（§4.1.1）から読む。WebP と、値がない・単位が不明・`MIN_DPI`〜`MAX_DPI` の外にある場合は `DEFAULT_DPI` とする。
  - JPEG は、JFIF の密度の単位が dpi か dpcm ならその値を、そうでなければ EXIF の `XResolution`・`YResolution`（`ResolutionUnit` がインチかセンチメートルのとき。省略はインチ）を使う。
  - 横と縦の値は、それぞれ整数の dpi に四捨五入してから範囲を確かめる（pHYs の 11811 画素/m は 300 dpi になる）。どちらか一方でも使えないときは、両方を `DEFAULT_DPI` にする。片方だけを既定の値にすると、元の画像にない縦横比になるため。
  - 横と縦で値が違う画像（ファクスの TIFF の 204×98 dpi など）は、画素が正方形でない。ページの大きさ・配置（§4.2）とサムネイル（§6.1）は、画素の数ではなく「画素数 ÷ dpi」の縦横比で決める。横の値だけを使うと、ファクスの標準の解像度のページは高さが半分になる（U14 の前の試作）。
- BMP は `image` で読み、`image` が返した RGBA をそのまま使う。32 ビットの BMP の 4 つ目の成分を透過として扱うかは `image` の解釈に従う（アルファのマスクを持つ BMP（`BITMAPV4HEADER` 以降）は透過ありとして読まれ、マスクのない 32 ビットの BMP（スパイクで使ったもの）は不透明として読まれ、透過の部分は黒になる）。BMP の透過の扱いは規格で曖昧なので、アプリでは手を加えない。

#### 4.1.1 TIFF（FR-01、FR-02）

- TIFF は `tiff` で直接読む。`image` は最初のページしか読まず、複数ページの TIFF を 1 ページにしてしまうため。形式の判定（`II*\0`・`MM\0*`、BigTIFF の `II+\0`・`MM\0+`）は、ほかの形式と同じく先頭のバイトで行う。
- 1 つの TIFF の全ページ（IFD の並び）を、順に PDF のページにする。縮小画像の IFD（`SubIFDs` の先）は見ない。一覧では 1 つのファイルを 1 行にし、ページ数を持つ（§6.1）。
- `probe` は、全ページの IFD を読み（画素は読まない）、次をページごとに確かめる。1 つのページでも当てはまれば、ファイル全体をそのエラーにする（FR-01）。
  - ページ数が `MAX_TIFF_PAGES` を超える: `TooManyPages`（`detail` は `MAX_TIFF_PAGES`）。`probe` は追加のときにメインプロセスで全ページの IFD をたどるので、たどる数に上限を置く。上限は、スキャンやファクスの束より十分多く、600 dpi の A4 の白黒でもその数のページの PDF が数百 MB に収まる大きさにする（§4.3）。IFD の輪は `tiff` が誤りとして返す（`DecodeFailed`）。
  - 総ピクセル数が `MAX_IMAGE_PIXELS` を超える: `TooLarge`。上限はページごとに当てはめ、ページの合計には当てはめない（画素はページごとに読んで手放すため）。
  - 読まない種類: `UnsupportedFormat`。読む種類は次の表だけで、それ以外（CMYK、色の表（`Palette`）、`WhiteIsZero` のグレー＋透過、CIE Lab、浮動小数点や符号付きの値、`PlanarConfiguration` が 2（色ごとに分かれた並び）、下の表にない圧縮）は読まない。

  | 項目 | 読むもの |
  | --- | --- |
  | 色（`PhotometricInterpretation`） | 白黒・グレー（`WhiteIsZero`・`BlackIsZero`。1・2・4・8・16 ビット）、グレー＋透過（`BlackIsZero` だけ。8・16 ビット）、RGB（8・16 ビット）、RGB＋透過（8・16 ビット）、YCbCr（JPEG の圧縮のときだけ） |
  | 圧縮（`Compression`） | なし（1）、CCITT G4（4）、LZW（5）、JPEG（7）、Deflate（8・32946）、PackBits（32773） |

  - 読まないものの理由: CMYK は、スキャナー・複合機・ファクスの出力ではまれで、PDF/A では使えない（§4.3）。krilla の `CustomImage` は CMYK も受け付けるので、求める声が出たら通常の PDF で入れることを検討する。ファクスの G3（3）・CCITT の 1 次元（2）と古い形の JPEG（6）は、`tiff` が展開できない。複合機やスキャナーの出力は G4 が多いので、求める声が出てから `fax` の `decode_g3` で自前に読むことを検討する。ZSTD・WebP は、`tiff` の機能を足せば読めるが、スキャンの出力では使われない。色の表と `WhiteIsZero` のグレー＋透過は、`tiff` 0.11.3 が画素の読み込みを拒む（U14 の実装の途中で分かった）。色の表はスキャンの出力ではまれなので、求める声が出てから、ストリップを自前で展開して表を引くことを検討する。
- 透過（`ExtraSamples`）: 1 つ目の追加の値が `UnassociatedAlpha`（2）ならそのまま、`AssociatedAlpha`（1）なら色を透過の値で割り戻して（透過が 0 の画素は色も 0）、透過として扱う。`Unspecified`（0）の追加の値は透過ではない別のデータなので、捨てて不透明として扱う。2 つ目以降の追加の値も捨てる。
- 向き: `Orientation`（274）の 1〜8 を、EXIF の向きと同じ 8 通りとして扱う（§4.3 の変換行列）。値がない・範囲の外なら向きなし。ページごとに読む。
- 解像度: `XResolution`・`YResolution` と `ResolutionUnit`（2 はインチ、3 はセンチメートル、省略はインチ。1（単位なし）は不明として扱う）から、§4.1 の規則で `dpi_x`・`dpi_y` を決める。ページごとに読む。
- 色のプロファイル（`ICCProfile`、34675）は、そのページの画像の色として PDF に入れる（NFR-01 の「見た目に要る情報」）。色の種類（グレーと RGB）と合わないプロファイルは入れない。ほかのタグ（EXIF・GPS の IFD、XMP（700）、IPTC（33723）、`ImageDescription`・`Artist`・`DateTime`・`Software` など）は、画素から PDF の画像を作るので、何もしなくても PDF に入らない。
- 画素の読み込みは、展開の大きさに `MAX_IMAGE_PIXELS` から決めた上限を掛けて行う。ヘッダーの寸法と合わない圧縮のデータで、上限を超えて展開しないため。

### 4.2 ページの大きさと配置（FR-02）

- EXIF（TIFF）の向きが 90 度・270 度の回転を含むとき、表示上の幅と高さを入れ替えてから以下を計算する。`dpi_x` と `dpi_y` も入れ替える。
- 画像の大きさは「画素数 ÷ dpi × 72」pt を横と縦で別々に計算した値とし（§4.1）、下の 2 つと上限はどれもこの大きさとその縦横比で決める。
- **画像と同じ大きさ**: ページの大きさを画像の大きさとする（余白なし）。300 dpi の A4 の読み取り画像は A4 のページになる。204×98 dpi のファクスの 1728×1143 画素のページは、約 610×840 pt（A4 に近い）になる。
- **用紙**（`PaperSize`）: 次の 7 つ。寸法は縦向きの幅×高さ。A 判と B 判は mm で、Letter と Legal はインチで定め、1 インチ = 25.4 mm = 72 pt で pt に換算する（換算は 1 か所に置き、pt の値を用紙ごとに書き写さない）。B 判は JIS P 0138 の寸法で、ISO 216 の B 判（B5 は 176×250 mm）とは違う。日本の事務で B 判と言えば JIS のため。

  | 用紙 | 値 | 寸法 | pt（参考） |
  | --- | --- | --- | --- |
  | A3 | `a3` | 297×420 mm | 841.89×1190.55 |
  | A4 | `a4` | 210×297 mm | 595.28×841.89 |
  | A5 | `a5` | 148×210 mm | 419.53×595.28 |
  | B4 | `jisB4` | 257×364 mm | 728.50×1031.81 |
  | B5 | `jisB5` | 182×257 mm | 515.91×728.50 |
  | Letter | `letter` | 8.5×11 in | 612×792 |
  | Legal | `legal` | 8.5×14 in | 612×1008 |

- ページの向きは、どの用紙でも「向き」の選択（`PageOrientation`）で決める。
  - 自動（`auto`、既定）: 表示上の幅が高さより大きい画像は横向き、それ以外は縦向きにする。結合では画像ごとに決まるので、縦と横のページが混ざる。
  - 縦（`portrait`）・横（`landscape`）: 画像によらず、すべてのページをその向きにする。画像は回転させない（横長の画像を縦のページに入れると、幅に合わせて縮み、上下の余白が広がる）。
  - どの用紙・どの向きでも、四辺に `PAGE_MARGIN_MM`（10 mm）の余白を取り、残りの領域に縦横比を保って収まる最大の大きさで、中央に置く。小さい画像も拡大する。余白は用紙の大きさに比例させない。一般的な文書作成ソフトと同じく、用紙を変えても余白の長さは変わらない方が予想しやすく、最も小さい A5 でも 10 mm は家庭用のプリンターが印刷できない縁より広いため。
- 1 ページの辺の長さは `MAX_PAGE_SIDE_PT`（14400 pt = 200 インチ）までにする。Acrobat が扱えるページの大きさの上限で、これを超えると開けないビューアーがあるため。「画像と同じ大きさ」でこれを超える場合は、縦横比を保って上限に収まるよう縮める。

### 4.3 PDF の書き出し（FR-02、FR-03）

- 1 つの画像を 1 ページにする（TIFF はページごとに 1 ページ）。結合では一覧の順にページを並べ、TIFF の中のページはその位置にまとめて順に並べる。
- JPEG は、メタデータの区切りを外したバイト列を、そのまま画像のデータとして入れる（`DCTDecode`）。画像のデータ（量子化表、ハフマン表、フレーム、スキャン）には触れないので再圧縮はなく、CMYK の JPEG もそのまま入る。ICC を持たない CMYK の JPEG は、色の決まりがないので、PDF のビューアー（印刷の CMYK として直す）と画像のビューアー（素朴な計算で直す）とで違う色に見えることがある。どちらも誤りではなく、ICC を持つものは同じ色になる。krilla はファイル全体を画像のデータとして使うので、外さないと EXIF の位置情報などが PDF に残る（NFR-01）。
  - 外すもの: APP1（EXIF、XMP）、APP13（IPTC、Photoshop）、COM、ICC 以外の APP2（MPF など）、Adobe 以外の APP14、そのほかの APPn、JFIF 以外の APP0（JFXX）、EOI より後ろのデータ（モーションフォトの動画、MPF の 2 枚目以降の画像など）。JFIF（APP0）は残し、埋め込みの縮小画像は寸法を 0 にして除く。
  - 残すもの: JFIF の密度、ICC（APP2 の `ICC_PROFILE`）、Adobe（APP14。CMYK と YCCK の色の変換に要る）、メタデータでない区切りすべて。
  - EXIF は向きも含めて全部外す。向きと解像度は §4.1 の `probe` が元のバイト列から読み、向きはページの変換行列で表すので、画像の中に残す必要がない。外すのは `probe` のあと。
  - 区切りの処理は、Metadata Cleaner（同じ作者の別のアプリ、MIT）の `crates/core/src/jpeg.rs` の `parse` と `strip` を `crates/core` に写して使う（向きと解像度だけの EXIF を作り直す部分は要らないので、`strip` には残す EXIF を渡さない）。依存にしないのは、git の依存を `deny.toml` の `[sources]` で禁じていることと、Metadata Cleaner の core が PDF Converter に要らない crate（`kamadak-exif`、`serde`、`ts-rs`）を持つため。
  - 区切りを読めない JPEG（SOI がない、長さが壊れている、EOI に届かないなど）は、`image` で画素が読めても `DecodeFailed` とし、その画像をページに加えない。外せないまま元のバイト列を入れることはしない。
- PNG と WebP は、画素を変えずに可逆の圧縮で入れ、透過を保つ。16 ビットの PNG は 16 ビットのまま入れる。
- BMP は §4.1 の RGBA を入れる。
- TIFF（§4.1.1）は、ページごとに画素を読み、グレーか RGB の 8・16 ビットとして、透過は別のチャンネルとして入れる。RGBA にまとめないのは、グレーのページが 4 倍の大きさになるのと、16 ビットのページが 8 ビットに落ちるため。
  - 白黒・2・4 ビットのグレーは 8 ビットのグレーに広げる。`tiff` は `WhiteIsZero` を反転して `BlackIsZero` の値で返し、1・2・4 ビットは行ごとに詰めたまま返すので、広げるだけで反転はしない（自分でも反転すると白黒が逆になる）。krilla は 1 ビットの画像も CCITT のデータのそのままの埋め込みも持たないため。PDF は元の G4 の TIFF より大きくなる（U14 の前の試作で、ファクスの fine（204×196 dpi）で約 2.4 倍、300 dpi の A4 で約 3.1 倍、600 dpi の A4 で約 4.7 倍（1 ページ約 330 KB））。この大きさは受け入れ、README に書く。小さくする方法は、求める声が出てから考える。
  - JPEG の圧縮の TIFF は、`tiff` が色の変換を止めて JPEG の成分のまま返す。`PhotometricInterpretation` が YCbCr なら、JFIF の式（ITU-R BT.601 の全範囲。R = Y + 1.402(Cr − 128)、G = Y − 0.344136(Cb − 128) − 0.714136(Cr − 128)、B = Y + 1.772(Cb − 128)、四捨五入して 0〜255 に収める）で RGB に直し、RGB ならそのまま使う。JPEG のデータをそのまま入れる §4.3 の JPEG と違い、ファイルは大きくなるが画質は落ちない。
  - 16 ビットの値は、PDF の決まりどおり大きい桁から先のバイト列にする（`tiff` は CPU のバイト順の値で返すため。`MM` の TIFF も同じ）。
  - 1 つの TIFF のページは、すべての画素を読んで krilla の画像を作り終えてから、まとめて PDF のページにする。途中のページが読めないとき（`DecodeFailed`）、前のページだけが入った PDF を作らないため（FR-02）。krilla は画像を作った時点で圧縮して画素を手放すので、待たせる間のメモリは小さい（試作で、600 dpi の A4 を 20 ページで最大 59 MB）。
  - 補間（`interpolate`）は、ほかの形式と同じく通常の PDF だけで付ける。
- EXIF の向きは、画像のデータを変えずに、ページの中の変換行列で表す。
- PDF の文書情報には、作成ソフト（`PDF Converter <版>`）だけを入れる。元のファイル名やパスは入れない（意図せずに情報が漏れないようにするため）。
- PDF/A（§10.1 の切り替え）を選んだときは、krilla の PDF/A-2b の検証を掛けて書く。krilla は RGB とグレーの画像を sRGB・sGray の ICC 付きの色で書き、sRGB の出力インテントと XMP のメタデータを入れ、規格に合わない内容があれば `finish` で失敗する。文書情報には、通常の PDF と同じ作成ソフトに加えて、作成日時（書いたときの時刻を UTC で秒まで）を入れる。krilla は、PDF/A では文書情報に作成日時がないと `finish` で失敗する（作成ソフトと日時を XMP の履歴（`xmp:History`）に書くため）。UTC にするのは、地方時の時差から住んでいる地域の手がかりが残らないようにするため。時刻は依存を足さずに暦に直す。通常の PDF には作成日時を入れない。
  - 画像の補間（`interpolate`）は、通常の PDF では付け、PDF/A では付けない。PDF/A は `Interpolate` を禁じ、付けると krilla が `finish` で失敗するため。拡大した小さい画像が、ビューアーによっては PDF/A で粗く見えることがある。
  - CMYK の JPEG（フレームの成分が 4 つ。Adobe の YCCK も含む）は、PDF/A では `CmykNotAllowedInPdfA` とし、その画像をページに加えない。krilla は、画像が ICC を持っていても、文書の CMYK プロファイル（出力インテントになる）がないと `finish` で失敗し、同梱するプロファイルの選択には正解がないため（ICC のない画像の色は、選んだプロファイルで変わる）。見分けるのは、上の区切りの処理が読むフレーム（SOF）の成分の数。確かめるのは `probe` と画素の確認のあとで、区切りを外す前。
  - 上の 2 つを守っていれば、`finish` が PDF/A の検証で失敗することはない。失敗したら作りの誤りなので、通常の `finish` の失敗と同じく `WriteFailed` にする（§11.2 のテストが、全フィクスチャで起きないことを確かめる）。
- 画像のデータの誤り（`corrupt.png` など）は、krilla では文書の `finish` まで分からず、どの画像の誤りかも分からない。そのため、ページに加える前に `image` で画素を一度読み、読めなければ `DecodeFailed` としてその画像を加えない。
- `krilla` の出力をメモリに作ってから §6.5 の方式で書き込む。結合する画像の数の上限は設けないが、§6.2 の進捗を 1 ページごとに通知する（TIFF の中のページも 1 ページずつ）。パスワードを付けるときは、書き込む前に §4.3.1 の暗号化を行う。

### 4.3.1 PDF の暗号化（FR-02）

- krilla の `finish` が作った PDF を `lopdf` で読み、krilla の出力のバイト列を捨ててから暗号化し、メモリに書く。暗号化した PDF を §6.5 の方式で書き込む。`lopdf` が読むのは、krilla がその場で書いた PDF だけにする（外から来た PDF は §9 のとおりワーカーの pdfium だけが読む）。
- 方式は標準のセキュリティハンドラーの revision 6（AES-256）だけ。ストリームと文字列の両方とメタデータを暗号化し、制限（権限）は付けない。ファイルの鍵は OS の乱数から作り、lopdf が作るソルトと初期化ベクトルも OS の乱数で種を入れた乱数を使う。文書情報（作成ソフト）と XMP も暗号化され、パスワードなしでは見えない。
- 所有者のパスワードは、閲覧のパスワードと同じにする。空にすると、空のパスワードで所有者として開けて暗号を外せてしまうため。制限を付けないので、所有者として開いても閲覧と変わらない。
- `lopdf` の出力に次を足す。
  - 暗号化の辞書の `/Length 256` と、`StdCF` の `/Length 32`。lopdf はどちらも書かず、poppler 22.12（Linux の Evince・Okular などが使う）は鍵を短いものとして扱って、全ページが壊れて描かれる（U15 の前の試作。どちらか一方で直った）。qpdf と同じく両方を書く。
  - カタログの `/Extensions <</ADBE <</BaseVersion /1.7 /ExtensionLevel 8>>>>`。krilla は PDF 1.7 で書くので、1.7 で AES-256 を使うことを宣言する（qpdf と同じ）。
- パスワードは `OutputPassword` 型で持ち、規則を通ったものだけが作られる。規則は、空でないこと、すべての文字が U+0020〜U+007E（半角の英数字・記号・空白）であること、127 文字（`MAX_OUTPUT_PASSWORD_LEN`）以下であること。型の `Debug` は値を伏せる（§6.8 と同じ）。
  - 規則の理由（U15 の前の試作。pdfium・qpdf 11.3・poppler 22.12・mupdf 1.21 で確かめた）: lopdf は SASLprep（NFKC の正規化など）をしてからパスワードを掛けるが、4 つのビューアーはどれも入れた文字の UTF-8 のまま照合する。そのため、全角の英数字、全角の空白、半角カナ、ソフトハイフン、結合文字の濁点・アクセントは、同じ文字を入れても開けない。また、lopdf は 127 バイトで切り詰めずに掛けるが、qpdf・poppler・mupdf は仕様どおり切り詰めるので、128 バイト以上では開けない（pdfium だけは切り詰めずに開ける）。絵文字・タブ・制御文字は lopdf が拒む。U+0020〜U+007E の文字は SASLprep で変わらず、UTF-8 で 1 文字 1 バイトなので、どちらの食い違いも起きない。
  - 日本語のパスワードは、試作の 4 つのビューアーでは開けたが、受け付けない。試していないビューアーで開ける保証がなく、ビューアーのパスワードの欄では日本語の入力が使えないことがあり、付けられても開くときに入れられないおそれがあるため。
- 暗号化は元のバイト列の所有権を受け取り、読み込んだあとに捨てる（メモリを抑えるため）。lopdf が krilla の出力を読めない・書けないのは作りの誤りなので、`finish` の失敗と同じく `WriteFailed` にする。PDF/A の PDF には呼ばない（PDF/A は暗号化を禁じる。§7.1 が組み合わせを拒む）。
- 時間とメモリ（試作）: 288 MB の PDF で 0.8 秒、最大のメモリは krilla の出力を持ったままで約 2.9 倍（848 MB）。捨てれば約 2 倍になる。書き出しはメインプロセスなので、§5.3 のワーカーの上限は掛からない。

### 4.4 PDF → 画像の書き出し（FR-04）

ワーカーが pdfium の描画結果（BGRA）を受け取り、次のように画像にする。

- 背景は白で塗り、その上に描画する（どの形式でも）。PDF のページは紙を表すので、透過のまま出すと、表示するソフトによっては文字が黒い背景に溶けて読めなくなるため。
- 色: カラーは 8 ビットの RGB で書く。グレースケールは、pdfium のグレースケールの描画（`FPDF_GRAYSCALE`）で描き、8 ビットのグレー（1 チャンネル）で書く。この描画の結果はすべての画素で R = G = B になる（PDF の中の写真も灰色になる。U09 の前の試作で、`shapes.pdf` と、`photo.jpg`・`logo_alpha.png` を入れた PDF で確かめた）ので、1 つのチャンネルを取り出す。描画の速さはカラーと変わらない。
- PNG: 8 ビット（RGB またはグレー）。圧縮の強さは `image` の既定。
- JPEG: 品質は `JPEG_QUALITY`。グレースケールは 1 成分の JPEG。
- WebP: 可逆の圧縮（`image` の WebP の書き出し）。`image` が書ける WebP は可逆だけで、非可逆には C の libwebp が要るため、非可逆は扱わない。図形の多いページでは PNG のおよそ 3 分の 1、写真のページでは 7 割ほどの大きさになる（試作の値）。
- 描画の寸法は「ページの大きさ（pt）÷ 72 × dpi」を四捨五入した値。総ピクセル数が `MAX_RENDER_PIXELS` を超えるページは描かずに `RenderTooLarge` とする。A0 を 300 dpi で描くと約 1.4 億画素になり、これは上限を超える。
- 解像度は `RENDER_DPI_MIN`（36）〜`RENDER_DPI_MAX`（1000）の整数。既定は `DEFAULT_RENDER_DPI`（150）。上限は、A4 が `MAX_RENDER_PIXELS` に収まる切りのいい値（A4 を 1000 dpi で描くと 8268 × 11693 ≈ 9670 万画素、1100 dpi では約 1.17 億画素で超える）。このときの 1 ページの描画と書き出しは、試作で最大約 1.05 GB のメモリ、描画と書き出しを合わせて 2 秒ほど（JPEG が最も遅い）で、`WORKER_MEMORY_LIMIT`（§5.3）と `RENDER_TIMEOUT`（§5.2）に収まる。下限は 72 dpi の半分で、これより小さい画像はページの確認にも使いにくい。
- 画面の解像度の選択肢（72、150、300 dpi）は `DPI_CHOICES` で、フロントエンドだけが持つ（§10.1）。Rust の検査（`save_settings`、`start_pdfs_to_images`、ワーカーの `Render`）は選択肢ではなく範囲で行う。

### 4.5 ページの範囲（FR-04）

- 書式: 区切りは `,`（全角の `，` と `、` も受け付ける）。各要素は `n` または `a-b`（`-` は全角の `－`、`〜`、`～` も受け付ける）。前後の空白（全角の空白を含む）は無視する。
- 数字は半角の `0`〜`9` と全角の `０`〜`９` だけを受け付ける。日本語の入力のまま打った数字を通すため。`+` などの符号は受け付けない。
- `n`、`a`、`b` は 1 以上の整数で、`a ≤ b`。満たさなければ `InvalidPageRange`（どの要素が悪いかを `detail` に入れる）。
- `end` は PDF ごとの最後のページを表し、`n` と `b` の代わりに書ける（`end`、`5-end`。`end-end` は `end` と同じ）。半角の小文字だけを受け付ける（数字と同じく、半角に切り替えずに打てるため。`END`・`ｅｎｄ` は誤り）。`a` には書けない（`end-3` は `InvalidPageRange`）。qpdf・pdftk はこの形をページの逆順と読むが、このアプリは順序を正規化して逆順にしないので、別の意味に黙って読まないため。終わりを省いた `5-` は受け付けない（`5-end` で書ける）。入力欄に書き方の説明は出さない。
- `a-end` は区間 `(a, u32::MAX)` として持ち、ほかの区間と同じく PDF ごとにページ数で切り詰める。`end` だけの要素は PDF ごとに番号が違うので区間にできず、区間とは別の印として持ち、PDF ごとに最後のページを足す。
- 範囲はページ番号に展開せず、区間（開始と終了）のまま持つ。`1-4000000000` のような入力でも、メモリと時間が入力の長さに比例する程度で済むようにするため（この関数は入力欄の変更のたびにメインプロセスで呼ばれる）。ページ数との突き合わせ（変換するページとその数）は、PDF のページ数（`MAX_PDF_PAGES` 以下）の範囲だけを数える。
- 重なりと順序は正規化する（`5, 1-3, 2` → 1、2、3、5）。
- PDF のページ数を超える番号は、エラーにせず、その PDF では飛ばす（FR-04 の「あるページだけを変換する」）。1 ページも残らなければ、その PDF は「対象のページなし」。
- 解釈は `crates/core` の純粋関数にして、単体テストで網羅する。フロントエンドには同じ処理を持たず、§7 のコマンドで Rust に問い合わせる（解釈の規則を 1 か所にするため）。

### 4.6 切り出しの描画（FR-11）

根拠の試作は、リポジトリの外の `spikes/embedded-images`（README の「dpi を合わせた切り出しと元の画素の比較」「切り出しの事前の試作の残り」）。

- **座標**: 範囲は、ページを表示する向き（`/Rotate` を当てたあと）の座標で、左上を原点、単位を pt にした矩形で持つ（サムネイルとページの表示と同じ向き）。純粋な計算（`PageRect`、行の判定、写真の範囲との一致）は `crates/core` の `region.rs` に置き、pdfium に依存させない。
- **前段の座標の測り方**: `FPDF_RenderPageBitmapWithMatrix`（`pdfium-render` の `PdfRenderConfig::apply_matrix`）は、ページを「表示する向きで 1 pt = 1 画素」にする行列に、渡した行列を重ねて描く。この前段の行列は、`/Rotate` と `CropBox` から自分で組み立てず、`PdfPage::points_to_pixels` を大きな寸法（`DISPLAY_PROBE_SCALE`）で 3 点に呼んで測る。`/Rotate` の場合分けを書かずに済み、試作では `/Rotate` 0・90・270、原点からずれた `CropBox`、大きさが整数でないページ（A4 の 595.276 pt）のすべてで画素が一致した。ページの大きさを整数に切り捨てた行列を使うと、整数でないページで 2 画素までずれた。
- **手で選んだ範囲と候補の範囲**: ページを解像度（dpi）で描いたものから、その矩形を切り取ったものと同じになるように描く。倍率は `dpi / 72`、出力の寸法は矩形の幅と高さに倍率を掛けて四捨五入した値。総ピクセル数が `MAX_RENDER_PIXELS` を超える範囲は `RenderTooLarge`（§4.4 と同じ）。
- **写真の範囲（「写真は元の画質で書き出す」のとき）**: 埋め込まれた画像の元の画素と、出力の画素が 1 対 1 に重なるように描く。画像は、ページの上で縮小・拡大・回転・反転・せん断して置かれていても、元の画素の並びは変わらない。次の 3 つを守ると、写真の不透明な部分の画素は、pdfium がその画像だけを元の画素の数で描いた結果と完全に一致した（試作の 36 本の公開の PDF の 554 枚と、合成の PDF の 24 か所。Linux と Windows で同じ画素）。
  1. 描く行列を、画像の画素の格子に合わせる。画像の行列（フォームの入れ子の行列を掛けたもの）から「画像の画素 → ページ」の行列を作り、その逆に前段の行列の逆を掛けたものを渡す。出力の寸法は画像の画素の数（幅 × 高さ）。小数の位置のずれも、この行列で消える。
  2. 画像の矩形の各辺を、ごくわずか（`PHOTO_EDGE_INSET`）内側に寄せる。pdfium は画像の描画先の矩形を外側の整数に丸めるので、浮動小数点の誤差で 1 画素はみ出ると、画像を 1 画素引き伸ばしてぼかすため（試作では、寄せないと大半の写真がぼけた）。
  3. 前段の行列は上のとおり測る（整数に切り捨てない）。
  - 写真の範囲は、画像の矩形ではなく見える部分（下の「埋め込み画像の一覧」の見える範囲）。そのため、1〜3 で画像の格子の全体を描いたあと、写真だけを同じ格子で白と黒の背景に描いて、見える画素（どちらの描画でも背景のままの画素以外）の外接矩形（画像の画素の座標）を求め、その矩形で切り取る。切り抜き（クリップ）やマスクで一部だけを見せている写真で、見えない部分（隣の内容）を出力に含めないため（下調べでは写真の 14 % で、見える範囲が画像の矩形の 9 割に満たなかった）。表示するページ（`CropBox` と `MediaBox` の共通部分）の外も見えない部分で、行列を渡した描画を pdfium はページの枠で切らないので、外接矩形を、ページの枠が覆う画素の範囲でも切り詰める。範囲は、表示するページの四隅を格子に写した外接矩形で、一部だけ覆われる画素を含める。ただし、枠が画素の境目にあるときに浮動小数点の誤差で隣の画素を含めないよう、食い込みが `PAGE_EDGE_TOLERANCE_PX` 以下の画素は除く。表示するページは前段の座標の測り方で測った座標にあるので、`/Rotate` と `CropBox` の場合分けは要らない。何も残らなければ見える画素がないものとする。
  - 1 で描くと、画像は保存された向き（画素の格子の向き）で出る。ページの上で 90 度単位で回転・反転して置かれた画像は、描いたあとに画素を並べ替えて（ロスなし）、ページで見えている向きにする。90 度単位でない回転とせん断の画像（`PageImages` の `native` が `false`）は、元の画素の対象にしない。その画像の枠のクリックや写真の候補でも写真の範囲（`kind` は `photo`、`imageIndex` を持つ）にはなるが、外接矩形を dpi で描く（「写真だけを書き出す」と重なりの印は効く。ワーカーは `imageIndex` の画像の `native` を見て描き方を選ぶ）。試作の 541 枚のうち、回転・反転・せん断のない画像は 526 枚で、残りの 15 枚がどの置き方だったかは数えていない。
  - 元の画素の数が `MAX_RENDER_PIXELS` を超える写真は、縦横比を保って上限に収まる倍率で、同じ格子の向きのまま描く（画素は一致しない）。範囲の一覧に「縮小」を出す（§10.1）。
  - 解像度の範囲（§4.4 の `RENDER_DPI_MIN`〜`RENDER_DPI_MAX`）は、写真の範囲には当てはめない（論文には 1,250 dpi 相当の写真があった）。画素数の上限でメモリを守る。
- **写真だけを書き出す**: そのページを読み込み直し、内容の書き直しを止めて（`PdfPageContentRegenerationStrategy::Manual`）から、写真以外の物をすべて外して描く。入れ子のフォームの中の写真は、外側からたどり、各段で写真に至る物以外を外す。注釈は描かない（`FPDF_ANNOT` を付けない）。書き直しを止めないと、物を外したとき（と画像の行列を変えたとき）に pdfium-render がページの内容を書き直し、同じページを読み込み直すと何も描かれなくなった（試作）。
- **背景**: 白で塗ってから描く（§4.4 と同じ）。ただし「写真だけを書き出す」で PNG か WebP に書くときは、透明（`0x00000000`）で塗ったビットマップに描き、pdfium のアルファをそのまま書く（RGBA、グレースケールなら LA）。試作では、554 枚すべてで不透明な画素の色が一致した。アルファは、541 枚で白と黒の背景での描画の覆いと一致し、残りの 13 枚も出力としては正しかった（9 枚は、乗算のブレンド（`/BM /Multiply`）で黒の背景の描画が暗くなり、覆いの判定の側が食い違っただけで、出力は画像の画素とマスクに完全に一致した。4 枚は、ページの側のソフトマスクで写真の縁をぼかしたもので、出力はページで見えるとおりの縁になった）。そのため、白と黒の背景で描き直して確かめることはしない。
- **写真の上に何かが載っているか**（範囲の一覧の印、FR-11）: 物の外接矩形の重なりでは判定しない（試作で、描いた結果との食い違いが 4 枚に 1 枚あった）。写真の格子で、ページ全体と写真だけを描いて比べ、写真が覆う画素（写真だけを白と黒の背景で描いて同じ画素）のうち、どれかの色の差が `ON_TOP_COLOR_TOLERANCE` を超える画素が `ON_TOP_MIN_PIXELS` 以上なら「載っている」とする。数えるのは、表示するページが覆う画素だけ（ページの枠の外に隠れた写真の部分の上の物は、見えている写真の上にない）。速さのため、比べる描画は総ピクセル数が `ON_TOP_CHECK_PIXELS` 以下になる倍率で描く。
- **色と形式**: カラー・グレースケール、PNG・JPEG・WebP の書き方は §4.4 と同じ。グレースケールは `FPDF_GRAYSCALE` で描く。
- **埋め込み画像の一覧**: ページ直下とフォームの入れ子の中の画像を、描く順にたどって番号（`imageIndex`）を振る。注釈の中の画像は含めない（ページ上の位置を正しく求められないため）。元の画素の幅か高さが `MIN_PHOTO_SIDE_PX` 未満の画像と、ページの上で見える大きさの短い辺が `MIN_PHOTO_SIDE_PT` 未満の画像も含めない（PowerPoint から書き出した資料の 2×2 px の透明な画像が数百枚重なるため）。ページの上の枠（`rectPt`）は、見える範囲にする: 写真だけを、総ピクセル数が `VISIBLE_CHECK_PIXELS` 以下になる倍率の画像の格子（90 度単位でない置き方なら、単位正方形を写した外接矩形の格子）で、白と黒の背景に描き、見える画素（どちらの描画でも背景のままの画素以外）の外接矩形を、外側に 1 画素広げてページの座標に戻し、画像の枠で切り詰めたもの。見える画素を「白と黒で同じになる画素」（不透明な画素）にしないのは、不透明度が 1 未満で描かれた写真が一覧から消え、ぼかした縁が切り落とされるため。切り抜き・フォームの切り抜き・マスクをまとめて扱える（`pdfium-render` の切り抜きの経路（`get_clip_path`）は、フォームの入れ子の座標が絡むので使わない）。見える画素がない画像も含めない。写真だけを描くページは画像ごとに読み込み直して作るが、互いの格子に届かない画像どうし（格子を外側に 1 画素広げた範囲に、ほかの画像の枠が重ならないもの）は、1 回読み込んだページに一緒に残して確かめる。画像は自分の枠の外には描かれないので、結果は 1 枚ずつ確かめたときと変わらない。物の多いページは読み込み直しに 1 回 0.2 秒ほどかかり、隠れた層の航空写真のタイルが候補になる地図（米国地質調査所の地形図で 211 枚）では、1 枚ずつ確かめると 50 秒かかり、時間の上限（§5.2 の `RENDER_TIMEOUT`）に近づいたため。番号は同じ PDF・同じ pdfium なら変わらないので、ワーカーへの要求（§5.1）は番号で写真を指す。
- 描く時間（試作、release）: 写真 1 枚の格子に合わせた描画は中央値 2.6 ms、90 % 点 22 ms、最大 1 秒ほど。

### 4.7 レイアウトの解析（FR-11 の候補）

- モデルは PP-DocLayout_plus-L を int8 に量子化したもの（§8.5）。入力は 800×800、出力は 20 種類の箱。onnxruntime は §8.5 の版を実行時に読み込む。
- **前処理**: ページを長い辺 `LAYOUT_RENDER_LONG_SIDE` で白の背景に描き（PDF → 画像と同じ pdfium の描画）、モデルの入力の大きさに縮める（縦横比は保たない）。PaddleX の既定（PIL の bicubic）と縮め方と描画のエンジンの版は違うが、試作で Python の結果との一致は 99.0 %、目で全部が合うと判定した 15 本では 100 % だった。
- **後処理**: 出力の各行（種類、スコア、左上と右下の座標。描いた画像の画素）から、種類が `image`・`chart`・`table` で、スコアが `LAYOUT_SCORE_MIN` 以上のものを残す。`LAYOUT_SCORE_MIN` は、int8 にしたモデルで元のモデル（しきい値 0.5）と箱が最もよく一致した値。箱は描いた画像の範囲で切り詰める。重なりは PaddleX の `layout_nms` と同じく、同じ種類で IoU が `LAYOUT_NMS_SAME_CLASS_IOU` 以上、違う種類で `LAYOUT_NMS_ANY_CLASS_IOU` 以上のとき、スコアの低い方を除く（スコアの高い順に見て、残したどれかと重なる箱を除く）。重なりの判定は、種類で絞る前に、スコアが `LAYOUT_SCORE_MIN` 以上のすべての種類（文章や見出しを含む 20 種類）の箱で行う（試作の比べ方と同じ）。短い辺が `LAYOUT_MIN_SIDE_PT` 未満の箱も除く。下調べの 36 本で、これより小さい箱はほとんどがアイコン・番号・ロゴだった。少し大きい箱にはアイコン・QR コードとカタログの小さな絵が混ざるので、そこまでは除かない（候補は押すまで範囲に入らない）。
- **種類**: `chart` はグラフ、`table` は表。`image` は、埋め込み画像（§4.6 の一覧）の枠（見える範囲）と IoU が `PHOTO_MATCH_IOU` 以上のものがあれば、その画像の写真の範囲（枠はモデルの箱でなく画像の枠）にし、なければ図（図形で描かれた絵）にする。1 つの埋め込み画像に 2 つ以上の箱が一致したときは、スコアの最も高い箱だけを写真にし、ほかは除く（同じ範囲の候補を 2 つ出さないため）。候補はスコアの高い順に返す。写真の候補のスコアはモデルの箱のスコア。下調べでは IoU は 0.9 以上に山があるが、それより低い所にも散らばった（キャプションを含む箱など）。下げると、写真を含む図解が写真だけに縮むおそれがあるので、高めに置く（下回った写真は図として dpi で描かれる）。埋め込み画像の一覧は `image` の箱があるページでだけ求める（一覧が失敗すると解析の全体が失敗するので、要らないページでグラフと表の候補まで失わないため）。
- **セッション**: 最適化は最大、スレッドは `LAYOUT_THREADS` と論理 CPU 数 − 1 の小さい方、プールのスレッドの空回りを止める（止めないと同じ検出器が約 4 倍遅く出た（ocr-bench））。
モデルは最初の解析のときに読み込み（約 0.5 秒、読み込み直後のメモリ約 365 MB）、そのワーカーが終わるまで持つ。
- **速さとメモリ（試作）**: 推論は 1 ページ 0.42 秒（元のモデル、Python、6 コアに固定）、int8 で 0.58 秒、Windows の `ort` で 0.62 秒（コアの固定なし）。Python でのピークのメモリは 0.56 GB。Rust のワーカーでのメモリは測っていない（作業計画のタスクで `WORKER_MEMORY_LIMIT` に収まることを確かめる）。
- **使えないとき**: onnxruntime かモデルを読み込めない（配布物が壊れている）ときは `LayoutUnavailable`（§6.6）。その PDF を開いている間は候補を出さず、手で選ぶ範囲と写真の範囲は使える（FR-09）。

## 5. ワーカー（NFR-01）

### 5.1 メッセージ

メインプロセスとワーカーは、標準入力と標準出力でメッセージをやりとりする。標準エラー出力はログとして読み捨てる。

- 1 つのメッセージ = 4 バイトの長さ（リトルエンディアン）+ JSON のヘッダー + （あれば）バイナリの本体。本体の長さはヘッダーの `bodyLength` に入れる。画像を base64 にしないため。
- 要求と応答は 1 対 1 で、ワーカーは一度に 1 つの要求だけを処理する。

| 要求 | 内容 | 応答 |
| --- | --- | --- |
| `Open { path, password }` | PDF を開く。`password` は `null` か、利用者が入れたパスワード（§6.8）。前に開いていたものは閉じる | `{ pageCount, pages: [{ widthPt, heightPt }] }` またはエラー |
| `Render { page, dpi, format, color }` | 開いている PDF の 1 ページを描画して書き出す（`format` は `png` / `jpeg` / `webp`、`color` は `color` / `gray`、§4.4） | 本体に画像のバイト列 |
| `Thumbnail { page, maxSide }` | 長い辺を `maxSide` px にして描画し、PNG にする（切り出しのページの表示にも使う。`maxSide` は `PAGE_VIEW_MAX_SIDE` まで） | 本体に PNG |
| `PageImages { page }` | 1 ページの埋め込み画像の一覧（§4.6） | `{ images: [{ imageIndex, rectPt, pxWidth, pxHeight, native }] }`。`rectPt` は §4.6 の座標の枠、`native` は元の画素で書き出せるか（90 度単位の置き方か） |
| `ImageOnTop { page, imageIndex }` | 写真の上に何かが載っているか（§4.6） | `{ onTop }` |
| `Detect { page }` | 1 ページのレイアウトの解析（§4.7） | `{ candidates: [{ kind, score, rectPt, imageIndex }] }`。`kind` は `photo` / `figure` / `chart` / `table`、`imageIndex` は `photo` のときだけ |
| `RenderRegion { page, rectPt, imageIndex, dpi, format, color, photoNative, photoOnly }` | 切り出しの 1 つの範囲を描いて書き出す（§4.6）。`imageIndex` は写真の範囲だけ。写真の範囲は、`photoNative` なら元の画素で、そうでなければ `rectPt` を dpi で描き、どちらも `photoOnly` ならほかの物を外す | 本体に画像のバイト列。ヘッダーに `{ width, height, scaledDown }` |
| `Close` | 開いている PDF を閉じる | `{}` |

- エラーの応答は `{ code, detail }`（§6.6 のコード）。pdfium のパスワードのエラーは `PasswordProtected`、それ以外で開けないものは `PdfOpenFailed`。
- ページ数が `MAX_PDF_PAGES` を超える PDF は、`Open` で `TooManyPages` を返す。
- ワーカーはファイルを書かない。描画した画像はメインプロセスに返し、メインプロセスが §6.5 の方式で保存する。
- `Detect` は、onnxruntime とモデルを最初の `Detect` で読み込む。読み込めなければ `LayoutUnavailable` を返し、そのワーカーは以後の `Detect` に同じエラーを返す（ほかの要求は続けて受ける）。読み込みを試し直さないのは、一度失敗したあとに `ort::init_from` をもう一度呼ぶとワーカーが落ちるため。読み込めたあとの推論の失敗も `LayoutUnavailable` で返す（こちらはワーカーを使えないことにはしない）。メインプロセスはこの 2 つを区別しない（§5.2）。

### 5.2 ワーカーの管理（`worker_pool.rs`）

- ワーカーは必要になったときに起動し、使い終わったら次の要求のために残す。数の上限は、論理 CPU 数 − 1 と `MAX_WORKERS` の小さい方（1 以上）。pdfium はスレッドの並列に対応しないので、並列はプロセスの数で行う。
- 一覧の追加（ページ数の取得）、サムネイル、変換は、どれもプールからワーカーを借りて行う。
- 応答の待ちには時間の上限を設ける（要求の種類ごとに決め、新しい要求を足したときに既定の値に落ちないようにする）: `Open` は `OPEN_TIMEOUT`、`Render`・`Thumbnail`・`PageImages`・`ImageOnTop`・`RenderRegion` は `RENDER_TIMEOUT`、`Detect` は `DETECT_TIMEOUT`（最初のモデルの読み込みを含む）。超えたらワーカーを強制終了し、その要求を `WorkerTimeout` で失敗させる。
- ワーカーが応答の途中で終了した、または読めない応答を返した場合は、その要求を `WorkerCrashed` で失敗させ、ワーカーを捨てる。次の要求では新しいワーカーを起動する。
- 1 つの PDF でワーカーが続けて落ちるのを避けるため、`WorkerCrashed` / `WorkerTimeout` になった PDF は、その一括変換の中で再試行しない。
- 切り出しのレイアウトの解析（`Detect`）は、プールとは別の 1 つのワーカー（解析のワーカー）だけで行う。モデルを読み込んだワーカーが増えると、そのぶんメモリが増えるため（1 つで 0.5 GB 前後）。解析のワーカーは、切り出しの PDF を開いている間だけ持ち、PDF を入れ替えたら終わらせる。最初の `detect_layout` で起動して、その PDF を（パスワードがあれば付けて）`Open` し、以後の解析の要求は 1 つずつ順に送る。`WorkerCrashed`・`WorkerTimeout` になったらそのワーカーを捨て、次の要求で起動し直す。`LayoutUnavailable` を一度受けたら、その PDF を開いている間は覚えておき、以後の解析の要求にはワーカーを起動し直さずに同じエラーを返す（ワーカーの中の読み込みの失敗と推論の失敗を区別しない。推論の失敗はまれで、PDF を開き直せば試し直せる）。入れ替えるときに解析の要求が実行中なら、それを待たない（その要求が終わってからワーカーを捨てる。古い PDF の結果は、画面が `id` で見分けて捨てる）。ページの表示、写真の一覧、重なりの判定、書き出しは、ほかの機能と同じくプールのワーカーで行う。
- アプリの終了時には、すべてのワーカーを終了させる。

### 5.3 メモリの上限

- ワーカー 1 つが使えるメモリを `WORKER_MEMORY_LIMIT` までにする。超えた確保は失敗し、ワーカーは終了する（`WorkerCrashed` として扱う）。
- Linux: ワーカーが起動直後、pdfium を読み込む前に `setrlimit(RLIMIT_AS)` で自分に上限を掛ける。
- Windows: メインプロセスがワーカーを起動したあと、ジョブオブジェクトに入れて `JOB_OBJECT_LIMIT_PROCESS_MEMORY` を掛ける。あわせて `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を付け、メインプロセスが異常終了したときにワーカーが残らないようにする。最初の要求を送る前にジョブに入れるので、上限の外で pdfium が動くことはない。
- Windows の API の unsafe な呼び出しは、ジョブオブジェクトの操作（`crates/worker/src/windows_job.rs`）と、下のデコードの予算のための搭載メモリの取得（`crates/worker/src/system_memory.rs` の Windows の関数）に閉じ込め、ワークスペースで unsafe を許すのはこの 2 か所だけにする（ワークスペースの `unsafe_code` は、この 2 か所が例外を宣言できるよう `deny` にする）。ジョブオブジェクトは、`JOB_OBJECT_LIMIT_PROCESS_MEMORY` を設定できる安全な包みの crate がないため（`win32job` 2.0 はワーキングセットの制限だけで、これは確保を失敗させない）。
- Linux で親が異常終了した場合は、ワーカーの標準入力が閉じ、ワーカーは次の読み込みで終了する。pdfium の処理の途中で止まっているワーカーは、その処理が終わるか時間切れになるまで残りうる。
- スパイクでの最大は約 84 MB（23 ページの論文を 300 dpi）で、上限は十分な余裕を持つ。上限の値と仕組みが Windows でも働くことを、作業計画の最初のタスクで確かめる。
- メインプロセスで画像の画素を読む処理（§4.3 の書き出し、§6.1 のサムネイル）は、プロセスで 1 つのメモリの予算（デコードの予算）の範囲で並べる。メインプロセスにはワーカーのような上限がなく、確保に失敗するとアプリごと終了するため。1 枚ずつの変換は §5.2 の数のスレッドで並び、サムネイルは表示された行の数だけ同時に頼まれる。計測では、`MAX_IMAGE_PIXELS` に近い 16 ビットの PNG で、変換を 4 つ並べると約 9 GB、サムネイルを 8 つ並べると約 8 GB を使った。結合（1 つの PDF）は 1 枚ずつ読むが、サムネイルと同時に動くので同じ予算を使う。
  - 画像ごとに、ファイルを読む前に使うメモリを見積もって予算から借り、画素を手放したら返す。ファイルを読む前に借りるのは、元のファイルのバイト列もピークに入るため。
  - 見積もりは、デコードした画素の大きさ（幅 × 高さ × 1 画素のバイト数。TIFF は最も大きいページ）に、処理ごとの係数（`DECODE_MEMORY_FACTOR_PDF`、`DECODE_MEMORY_FACTOR_THUMBNAIL`）を掛けたもの。係数は計測の最大（書き出しで画素の大きさの 3.9 倍、サムネイルで 1.9 倍）より大きい切りのいい値にする。1 画素のバイト数（色の種類とビット深度）は §4.1 の `probe` でヘッダーから読み、一覧の項目に持たせる（IPC には出さない）。持たせないと最悪の 16 ビット RGBA で見積もることになり、8 ビットの写真まで並ぶ数が 4 分の 1 になるため。
  - 借りる順は頼んだ順にする。小さい画像が続いても、大きい画像が待ち続けないようにするため。
  - 見積もりが予算より大きい画像は拒まず、ほかに借りている処理がなくなってから 1 つだけで読む。画像の大きさの上限は `MAX_IMAGE_PIXELS`（§4.1）で決まっていて、予算をそれより厳しい上限にしないため。
  - 予算を待つ間もキャンセルを確かめる（NFR-02）。
  - 予算は、搭載メモリの 1/3 を `DECODE_MEMORY_BUDGET_MIN`〜`DECODE_MEMORY_BUDGET_MAX` に収めた値にする。メモリの多いマシンで大きな画像を待たせないため。
    - 空きではなく搭載量を使う。空きはそのときどきで変わり、同じ画像でも速さが毎回変わるため。
    - 1/3 は、OS とほかのアプリ、WebView、予算の外で動くワーカーの分を残すため。1/2 では、16 GB のマシンで 16 ビットの上限の画像が 3 枚並び（約 7 GB）、ほかのアプリの分と合わせて空きがなくなる。
    - 下限は `WORKER_MEMORY_LIMIT` と同じ値（メモリの少ないマシンと、搭載量を読めなかったとき）。上限は、16 ビットの上限の画像が `MAX_WORKERS` の数だけ並ぶ大きさ（それより大きくしても並ぶ数は増えない）。
    - 搭載量は、Linux では `/proc/meminfo` の `MemTotal`、Windows では `GlobalMemoryStatusEx` で読み、読めなければ下限にする。Windows の呼び出しは unsafe になるが、上の例外に加える。安全な包みの crate を足すより小さく（`windows-sys` はすでに依存にあり、機能を足すだけ）、外から来たデータを渡さない読むだけの呼び出しのため。

### 5.4 ワーカーの見つけ方

- メインプロセスは `std::env::current_exe()` を `--pdf-worker` 付きで起動する。別の実行ファイルを同梱しない。
- ワーカーは、同梱した pdfium のライブラリ（§8.2）の場所を引数で受け取る。Tauri のリソースのフォルダはメインプロセスだけが知っているため。onnxruntime のライブラリとモデル（§8.5）の場所も同じく引数で受け取る。onnxruntime は
ファイルの完全なパスで読み込む（Windows 11 には別の版の `onnxruntime.dll` が `System32` にあり、名前だけで読み込むとそちらを使うおそれがあるため）。ファイルの有無はメインプロセスでは確かめず、最初の `Detect` で読み込めなければ `LayoutUnavailable` にする（§5.1）。

## 6. 各機能の設計

### 6.1 一覧（FR-01）

- 「画像 → PDF」と「PDF → 画像」は、それぞれ 1 つの一覧を持つ。一覧の項目は Rust の表に登録し、フロントエンドには ID と表示用の情報だけを渡す。
- 追加の方法: 「画像を追加」「PDF を追加」（複数選択のファイルダイアログ）、「フォルダを追加」（フォルダダイアログ）、D&D。
- フォルダは直下だけを見る。サブフォルダ、シンボリックリンク、隠しファイル（`.` で始まる名前）、対応しない拡張子は追加しない。§7.1 の `skipped` には、サブフォルダを `folders`、対応しない拡張子を `unsupported`、一覧にすでにあるものを `duplicates` として数える。隠しファイルとシンボリックリンクは、利用者が意図して選んだものではないので数えない。ファイルダイアログや D&D で直接選ばれたファイルは、名前が `.` で始まっていても追加する。
- 追加、フォルダの選択、「PDF を保存」のダイアログは、コマンドを呼んだウィンドウを親にして開く。親がないと、アプリのウィンドウを押したときにダイアログがその裏に隠れたまま開いていて、もう一度押すと重ねて開けるため。
- D&D は Rust の `WindowEvent::DragDrop` で受ける。落とされたものを拡張子で分け、画像は「画像 → PDF」の一覧に、PDF は「PDF → 画像」の一覧に入れる。フォルダは中を見て同じように分ける。フロントエンドは、追加があった一覧のタブに切り替える（両方に入ったときは、表示中のタブのまま）。
- 同じファイル（正規化したパスが同じ）がすでに一覧にあれば、追加しない。
- 追加のときに、画像は §4.1 の `probe`、PDF はワーカーの `Open` を行う。失敗したファイルも一覧に入れ、行にエラーの理由を表示する。エラーの行は変換の対象にしない。パスワード付きの PDF も、ここで分かる（開き方は §6.8）。
- 画像の一覧のサムネイルは、Rust が画像を縮小して PNG で返す。TIFF は最初のページを使う。縦横比は §4.1 の「画素数 ÷ dpi」で決める（横と縦の dpi が違う画像を、画素の数のまま縮めるとつぶれて見えるため）。PDF のサムネイルはワーカーの `Thumbnail` で作る。どちらも長い辺を `THUMBNAIL_SIDE` にする。サムネイルは表示されたときに 1 つずつ要求する（多数の追加で待たされないようにするため）。画像のサムネイルの縮小は、§5.3 のデコードの予算の範囲で行う。
- 並べ替え（画像の一覧のみ。結合の順になる）: ドラッグ、各行の ↑↓ ボタン、行にフォーカスがあるときの Alt + ↑ / ↓。順序はフロントエンドが持ち、変換を始めるときに ID の並びとして渡す。
- 変換中は一覧を変えられない（追加・削除・並べ替えのボタンを無効にし、D&D は `ConversionRunning` で拒む）。

### 6.2 画像 → PDF（FR-02、FR-03、FR-05）

- 「1 つの PDF」: 「PDF を保存」で保存ダイアログを開く。初期ファイル名は一覧の先頭の画像の名前の拡張子を `.pdf` にしたもの。ダイアログで既存のファイルを選んだ場合は、OS のダイアログで上書きの確認が済んでいるので上書きする。Linux では、ダイアログをホームのフォルダで開く（指定しないと GTK がプロセスの作業フォルダで開き、AppImage では書き込めない読み取り専用のマウント先になるため）。Windows は OS が前回のフォルダを覚えているので指定しない。追加やフォルダを選ぶダイアログは「最近使ったもの」で開くので指定しない。
- 「1 枚ずつ」: 保存先のフォルダを選び、「変換を開始」で一覧の画像を 1 つずつ PDF にする。複数ページの TIFF は、1 つのファイルから全ページを持つ 1 つの PDF を作る（ページごとには分けない）。出力名は §6.4。並列の数は §5.2 と同じ式（ワーカーは使わず、スレッドで行う）。画素を読む間は §5.3 のデコードの予算に従う。
- どちらも、進捗を `job-progress`、1 件ごとの結果を `job-item` で通知し、最後に `job-finished` を送る（§7.2）。進捗はページで数える（`total` は一覧のエラーのない項目のページ数の合計、`done` は PDF に加えたか失敗したページの数）。200 ページの TIFF が 1 件と数えられて、長い間進捗が動かないのを避けるため。`job-item` は、TIFF でもファイルに 1 つ。TIFF の途中のページが読めなかったときは、そのファイルを `failed` にし、残りのページの分も `done` に足す。キャンセルは、TIFF の中でもページの間で確かめる。
- 「PDF の形式」（§10.1）が「パスワード」のときは、「PDF を保存」（1 つの PDF）・「変換を開始」（1 枚ずつ）を押すと、先にパスワードのダイアログ（§10.1）を開く。ダイアログで決めたら、1 つの PDF は保存ダイアログを、1 枚ずつは保存先のフォルダの確かめ（§6.5。未選択ならフォルダのダイアログ）を続けて行う。どちらかのダイアログを取り消したら何も始めない。パスワードは `save_merged_pdf`・`start_images_to_pdfs` の `password` で渡す（§6.9）。1 つの PDF は `finish` のあとに、1 枚ずつはファイルごとに `finish` のあとにそのスレッドで、§4.3.1 の暗号化を行う。1 枚ずつでは、その回のすべての PDF に同じパスワードを付ける（鍵とソルトはファイルごとに別）。暗号化はページの進捗に数えず、途中でキャンセルを確かめない（大きい PDF でも 1 秒ほどのため）。
- 「PDF の形式」の「PDF/A」（§10.1）は、「1 つの PDF」と「1 枚ずつ」の両方に使う。PDF/A で CMYK の画像は、ほかの読めない画像と同じく `job-item` で失敗にし（`CmykNotAllowedInPdfA`）、「1 つの PDF」では残りの画像で PDF を作る。

### 6.3 PDF → 画像（FR-04、FR-05）

- 一覧に PDF が 1 つのときは、ページのサムネイルを並べ、範囲の指定で変換するページを示す。複数のときは、一覧の表とする（モックアップ `PdfSingle` と `PdfBatch`）。
- 範囲を入力するたびに `check_page_range` を呼び、変換するページの合計を下部バーに表示する（§10.1）。書式の誤りがあれば「変換を開始」をすぐに無効にし、誤りの文言は入力が `FIELD_ERROR_REVEAL_DELAY_MS` 止まるか欄から離れたときに入力欄の下に赤で表示する。打ちかけの「1-」のような途中の文字で注意を出さないため。範囲に当てはまるページが全 PDF の合計で 0（`totalPages` が 0）のときは、下部バーの文言を赤にし、「変換を開始」も無効にする（押しても何も変換しないため）。一部の PDF だけにページがない（合計が 1 以上）ときは、そのまま変換でき、その PDF の行は「対象のページなし」になる。範囲の確認中は、書式の誤りのときと同じく無効にする。
- 新しい範囲の文字列が最初の `check_page_range` の答えを待つ間は、サムネイルの強調、表のページ数、下部バーの文言を、その前の表示のまま保つ。答えのない一瞬にすべてのページが外れたように見えて、ちらつくため。
- 「すべて」のときは、範囲として `1-{対象の PDF の最大のページ数}` を渡す。範囲の解釈（§4.5）は空の文字列を受け付けず、ページ数を超える番号は PDF ごとに飛ばされる（§4.5）ので、これで全 PDF の全ページになる。
- PDF が 1 つのときのサムネイルの格子では、変換するページを強調し、サムネイルのクリックでも変換するページを選べるようにする。どのページかは、`check_page_range` が返す `intervals`（正規化した区間）と `lastPage`（`end` だけの要素があるか）から、その PDF のページ数で求める。クリックで選んだときは、その結果から範囲の文字列を作り直して入力欄に入れ、手で入力したときと同じく `check_page_range` で確かめる。どちらでも、画面は範囲の文字列を解釈しない（規則は §4.5 の 1 か所）。範囲の誤りが出ている間は、手で入力した文字を上書きしないよう、クリックでは選べない。
- 「範囲を指定」に切り替えたとき、範囲の欄が空なら `1-{対象の PDF の最大のページ数}` を入れる。空の範囲はどのページも選ばないので、切り替えた途端にすべてのページが外れるため。
- 変換の結果があるときは、格子の選んだページに結果（完了・失敗・未処理）を示す。ページは先頭から順に処理するので、結果が届いたページは、選んだページの先頭から「保存した数＋失敗した数」までになる。キャンセルした PDF の `job-item` にも、それまでに失敗したページがあれば `failedPages` を入れる（届いたページの数が合うように）。PDF ごと失敗したときは、選んだページすべてを失敗とする。失敗したページは、選んだページの枠（アクセントの色）と赤が近いので、色だけでなく印でも示す（§10.3）。
- 「変換を開始」で、保存先のフォルダと、形式、色、解像度、範囲を渡す。PDF ごとにワーカーを 1 つ借り、`Open` → 対象のページごとに `Render` → 保存、を行う。PDF の単位で並列にする。
- 出力名: `元の名前_p{番号}.{png|jpg|webp}`。番号は、その PDF のページ数の桁数で 0 を詰める（8 ページなら `p1`〜`p8`、120 ページなら `p001`〜`p120`）。ファイルの一覧で名前の順に並べたとき、ページの順になるようにするため。
- 1 つの PDF の途中のページで失敗したときは、その PDF の残りのページを続け、その PDF を「一部失敗」として失敗のページ番号を表示する。

### 6.4 出力名の決定

SVG Tracer の §5.3 と同じ規則にする。

- 候補名が「保存先のフォルダに既にある名前」または「この変換で割り当て済みの名前」と重なったら、`name (1).pdf`、`name (2).pdf` … と番号を付ける。PDF → 画像では `report_p1 (1).png` の形になる。
- 重なりの判定は大文字小文字を区別しない。名前は**開始時に全件分まとめて決める**。
- 保存の瞬間に他のプロセスが同名のファイルを作っていたら、上書きせずに次の番号で保存し直す。
- 純粋関数として `naming.rs` に置き、単体テストで網羅する。
- 切り出し（FR-11）: `元の名前_p{ページ}_{番号}.{png|jpg|webp}`（例: `catalog_p03_2.png`）。ページの番号は PDF → 画像と同じく PDF のページ数の桁数で 0 を詰める。範囲の番号は、そのページで書き出す範囲を位置の順に並べて 1 から振り、そのページで書き出す範囲の数の桁数で 0 を詰める（9 個までは `1`〜`9`、10 個以上なら `01`〜）。範囲を選んだ順によらず、同じ範囲の組なら同じ名前になる。
  - 位置の順: 範囲を上端の座標の順に並べ、先頭から行に分ける。範囲は、今の行の最初の範囲と縦の重なりが、2 つのうち低い方の高さの半分以上あれば同じ行に入り、なければ新しい行を始める。行の中は左端の順。上端も左端も同じ範囲は、範囲の一覧の順（ページを表示したときの追加の順）。
  - 重なりの番号の付け方（` (1)`）は上と同じ。行の判定と番号は `region.rs` に置く。

### 6.5 保存とキャンセル

- 保存は、保存先のフォルダに一時ファイルを作って全内容を書き、`persist_noclobber` で最終名にする（SVG Tracer §5.4 と同じ）。書き込みの途中で失敗・中断しても、不完全なファイルは残らない。
- 一時ファイルは、保存先のフォルダに `.` で始まる名前で作る（ほかのアプリの一覧に途中のファイルが見えないようにするため）。
- Unix では、一時ファイルを `0666` で作る（OS が umask を引くので、通常は `0644` になる）。`tempfile` の既定は本人だけが読める `0600` で、名前を替えてもそのままなので、保存した PDF や画像を、ほかのアプリや別の利用者が読めなくなるため。設定ファイル（§6.7）は本人だけが読めればよいので、既定のままにする。Windows にはこの指定がない。
- 保存先のフォルダは、「画像 → PDF」「PDF → 画像」「切り出し」で 1 つずつ Rust の状態に持つ。`pick_output_dir` と設定の復元（§6.7、T09）が入れ、`start_images_to_pdfs`・`start_pdfs_to_images`・`start_crop_export` はそれを使う。まだ選ばれていなければ `InvalidParams` で拒む。
- 画面は、フォルダが未選択のまま「変換を開始」が押されたら、先に `pick_output_dir` でフォルダのダイアログを開き、選ばれたらそのまま変換を始める（選んだフォルダは設定パネルの欄にも出る）。ダイアログを取り消したら何も始めない。ボタンを無効にして先に設定パネルへ行かせるより、手順が 1 つ少ないため。
- `start_images_to_pdfs`・`start_pdfs_to_images`・`start_crop_export` は、変換中かどうかの確かめのあと、変換を始める前に保存先のフォルダを確かめる。
  - 存在しない、またはフォルダでない: 何も始めず、§6.5 の Rust の状態と設定ファイルの `outputDir` を未選択（`null`）に戻して `OutputDirMissing` を返す。ほかの画面の保存先は変えない。
  - フォルダはあるが、そこに一時ファイル（上の `.` で始まる名前）を作れない: 何も始めず `OutputDirNotWritable` を返す。権限を直せば使えるので、保存先は未選択に戻さない。
  - `detail` は付けない（`io::Error` の文言にフォルダのパスが入り、フロントエンドにパスを渡さないため）。
- 画面は、`OutputDirMissing` が返ったら、保存先の欄を「未選択」にし、一覧の上の `ErrorDisplay` でこの文言を出す。フォルダのダイアログは自動では開かない（帯と同時に開くと、理由を読む前に選ばせることになるため）。次に「変換を開始」を押すと、フォルダが未選択のときと同じ流れでダイアログが開く。`OutputDirNotWritable` は同じ `ErrorDisplay` で出して何も始めない。どちらも下部バーには繰り返さない。この帯には閉じるボタンを付けない。フォルダが使えない間は出しておき、保存先を選ぶ、設定や一覧を変える、変換を始めるのいずれかで消える（§10.1）。起動時の設定の復元（§6.7）が存在しないフォルダを未選択にするのは、これとは別に今のまま行う。
- キャンセルは共有フラグで行う。画像 → PDF は次のファイルの前に、PDF → 画像は次のページの前に確かめる。描画中のページは終わらせて保存する（pdfium の描画は途中で止められないため）。キャンセルした PDF は、保存済みのページ数を表示する。
- 変換中に出力の書き込みが `WriteFailed` で失敗したら、その変換を打ち切る。保存先は全項目で共通なので、続けても失敗し続けるだけのため。キャンセルと同じく、次の項目・次のページの前で止まる。
  - 画像 → PDF（1 枚ずつ）: 失敗した画像は「失敗」（`WriteFailed`）、残りの画像は「未処理」。
  - PDF → 画像: 失敗した PDF は、それまでに保存したページがあれば `partial`、なければ `failed`。`failedPages` は書き込みに失敗したページだけで、届かなかったページは入れない。残りの PDF は「未処理」。
  - `job-finished` は `cancelled: false` で、残りを `unprocessed` に数える。ほかのワーカーがすでに処理している PDF は、その PDF の最後まで進む（同じフォルダなら、そこで同じ失敗になる）。
  - 結合（1 つの PDF）は最後に 1 回書くだけなので、この扱いはない。
  - `WriteFailed` 以外の失敗は、その項目・ページだけが失敗して続ける（壊れた画像、描画の上限）。ワーカーの異常終了・時間切れは、§5.2 のとおりその PDF の残りのページを試さず、ほかの PDF は続ける。
- 結合（1 つの PDF）をキャンセルしたときは、PDF を書かない（`job-finished` は `cancelled: true`、`save_merged_pdf` は `savedName: null`）。画面は結果を消さず、帯と行の状態を残す（§10.1）。全部の画像が失敗して PDF を書かなかったときも同じ。
- キャンセルを押した直後に「キャンセル中…」を表示し、ボタンを無効にする（NFR-02）。

### 6.6 エラー（FR-09）

IPC では `{ code, detail }` の形で返す（SVG Tracer §5.5 と同じ。型の合わない引数を `InvalidParams` に変換するフロントエンドの仕組みも同じ）。表示の文言は、コードごとに `src/i18n` の辞書に置く。

| コード | 状況 |
| --- | --- |
| UnsupportedFormat | 非対応の形式 |
| DecodeFailed | 画像を読めない（壊れたファイル） |
| PdfOpenFailed | PDF を開けない（壊れたファイル） |
| PasswordProtected | パスワード付きの PDF。`unlock_pdf` ではパスワードの誤り（`unlock_pdf` の誤りはダイアログで別の文言を出す。§10.1） |
| TooLarge | 画像のピクセル数が上限超過 |
| TooManyPages | PDF・TIFF のページ数が上限超過 |
| RenderTooLarge | 描画の大きさが上限超過 |
| WorkerCrashed | ワーカーが異常終了した |
| WorkerTimeout | ワーカーが時間内に応答しない |
| ReadFailed | 読み込みの失敗 |
| WriteFailed | 書き込みの失敗（権限、容量など） |
| CmykNotAllowedInPdfA | PDF/A を選んだときの CMYK の画像（§4.3） |
| InvalidPageRange | 範囲の書式の誤り |
| ConversionRunning | 変換中に一覧や変換を操作しようとした |
| UnknownHandle | 存在しない ID |
| InvalidParams | 引数が範囲外（UI からは通常送られない） |
| OutputDirMissing | 変換を始める前に、保存先のフォルダがない、またはフォルダでない（§6.5） |
| OutputDirNotWritable | 変換を始める前に、保存先のフォルダに一時ファイルを作れない（§6.5） |
| LayoutUnavailable | 切り出しで、onnxruntime かモデルを読み込めない、または解析に失敗した（§4.7、§5.1） |

- 「対象のページなし」はエラーではなく、`job-item` の状態 `noPages` で表す（FR-04）。
- 書き出す PDF のパスワードの誤り（使えない文字、長すぎる、2 回の入力が違う）は、画面がダイアログの中で示す（§10.1）。IPC のエラーコードは足さない。画面と同じ規則を Rust も確かめ（§4.3.1 の `OutputPassword`）、届いたら `InvalidParams` で拒む。
- ワーカーが同梱の pdfium を読み込めないとき（ワーカー内のコード `PdfiumUnavailable`）は、IPC では `WorkerCrashed` として返す。配布物が壊れている場合にしか起きず、利用者に見せる文言は同じでよいため。
- `TooLarge`、`TooManyPages` の `detail` には、Rust が上限の定数を 3 桁区切りの文字列にして入れる（上限の数値をフロントエンドに書き写さないため）。`TooManyPages` は、PDF では `MAX_PDF_PAGES`、TIFF では `MAX_TIFF_PAGES`。

### 6.7 設定の保存（FR-07、FR-10）

- 保存先は `app_config_dir()` 配下の `settings.json`。読み書きの方式、壊れた設定や未知の `schemaVersion` で既定値に戻すこと、フォルダの扱いは SVG Tracer §5.6 と同じ。
- 内容: `schemaVersion`、`language`、画面ごとの設定（`imagesToPdf`・`pdfToImages`・`crop`）。画面ごとの設定は、その画面の設定パネルの選択肢と保存先のフォルダ（`outputDir`）で、切り出しの `format`・`colorMode`・`dpi` は `pdfToImages` と同じ値。`dpi` は §4.4 の範囲の整数。項目と値の型は Rust の設定の型（ts-rs で生成した型）が正本。
- 一覧の中身とページの範囲は保存しない（次回は空の一覧で始める）。切り出しの開いた PDF と範囲も保存しない。
- `crop` がない設定ファイル（切り出しより前の版が書いたもの）は、欠けた項目として既定値になるので、`schemaVersion` は `1` のままでよい。
- 既定値: 「1 つの PDF」、「画像と同じ大きさ」、用紙の向きは「自動」、PDF/A は使わない（`false`）、パスワードは付けない（`false`）、PNG、カラー、150 dpi。切り出しは PNG、カラー、150 dpi、写真は元の画質で書き出す（`photoNative: true`）、写真だけを書き出さない（`photoOnly: false`）。言語は未設定（`null`。画面が `navigator.language` から決める）。フォルダは未選択（`null`）。
- `language` は `"ja"`、`"en"`、`null` のいずれか。`outputDir` はフォルダの絶対パスか `null`。
- `get_settings` はパスを返さない。`outputDir` の代わりに `pick_output_dir` と同じ `{ dirLabel }`（未選択なら `null`）を返す。`dirLabel` はフォルダの名前（パスの最後の要素）。
- `save_settings` は、`revision`（数）と、`get_settings` の形から `outputDir` を除いたものを受け取る。`dpi` が §4.4 の範囲の外にある、`pdfA` と `encrypt` がどちらも `true` などの不正な値は `InvalidParams` で拒み、何も保存しない。`encrypt` はパスワードを付けるかどうかだけで、パスワードは保存しない（§6.9）。
  - `async` でないコマンドにし、メインスレッドで受け取った順に、値をメモリの設定に入れるだけにする。ファイルは別のスレッドで、そのときの最新の値を書く。書き込みは 1 つずつで、ファイルがすでに最新なら書かない。書き込みの失敗は返さず、設定はメモリに残して次の書き込みで再び試す（書くのは応答のあとなので返せない。FR-10 は Should）。メインスレッドはファイルの書き込みを待たない（メモリの設定のロックは写す間しか持たない）。
  - `revision` は、画面が呼ぶたびに 1 つ増やす。Rust は、同じページからすでに受け取ったもの以下の `revision` を捨てる。WebView が要求を `fetch` の順に Rust へ渡すことは保証されておらず、入れ替わると古い値が残るため。ページの読み込みが始まると（`on_page_load` の `Started`。再読み込みを含む）、画面は 1 から数え直すので、Rust も覚えている `revision` を捨てる。
  - アプリが終わるとき（`RunEvent::Exit`）、まだ書いていない設定があれば書く（書いている途中なら、それを待つ）。閉じるボタンや Alt+F4 のほか、Windows のログオフとシャットダウンでも来る知らせで、後者ではウィンドウに `CloseRequested` が来ない。Rust の側で受けるので、capabilities は変わらない。WebView がまだ Rust に渡していない変更は残らない。
- `pick_output_dir` は、選ばれたフォルダを §6.5 の Rust の状態と設定に入れ、設定ファイルを書き直す。書き込みに失敗しても、選んだフォルダはそのセッションで使い、`{ dirLabel }` を返す（設定ファイルの問題で変換を始められなくならないようにするため）。
- 起動時、保存されたフォルダが存在すればそれを §6.5 の状態に入れ、存在しなければ未選択に戻す。
- 読み込んだ値は項目ごとに確かめ、不正な項目（未知の値、型の違い、欠けた項目、存在しないフォルダ）だけを既定値に戻して、ほかの項目は残す。SVG Tracer のプリセットとパラメータのような組になった項目はない（`orientation` も `pageSize` とは別に確かめる。`orientation` がない設定ファイル（`v0.1.0` が書いたもの）は、欠けた項目として「自動」になるので、`schemaVersion` は `1` のままでよい。`colorMode` も同じく、ない設定ファイルは「カラー」になる。`pdfA` も同じく、ない設定ファイルは通常の PDF（`false`）になる。`encrypt` も同じく、ない設定ファイルはパスワードなし（`false`）になる。読み込んだ `pdfA` と `encrypt` がどちらも `true` のときは（手で書き換えたときだけ起きる）、`encrypt` を `false` に戻す。逆に、新しい版が書いた `a3` などの用紙、`webp`、`gray`、選択肢にない `dpi` を `v0.1.0` が読むと、その項目だけが既定値に戻り、ほかの項目は残る）。JSON として読めない場合と、`schemaVersion` が `1` でない場合は、すべてを既定値にする。

### 6.8 パスワード付きの PDF（FR-04）

- 追加のときに `PasswordProtected` になった PDF は、パスワードを入れると開ける（§10.1 のダイアログ）。閲覧のパスワードと所有者のパスワードのどちらでもよい（pdfium がどちらも受け付ける）。
- 入れたパスワードは、メインプロセスの一覧の表（`items.rs` の `Entry`）に項目ごとに持ち、その項目の `Open`（サムネイル、変換）のたびにワーカーに渡す。ワーカーは要求ごとに PDF を開き直し、どのワーカーが担当するかも決まっていないため。
- パスワードは設定にもログにも書かず、項目を外すか、アプリを終えると捨てる。`Debug` の表示にも出さない（パスワードを持つ型は `Debug` を手で書いて値を伏せる）。メモリの消去（`zeroize` など）は行わない。画面の入力欄と IPC の文字列も同じ値を持ち、メインプロセスだけ消しても守れる範囲が変わらないため。
- パスワードは入力のまま UTF-8 で pdfium に渡す。前後の空白を除かず、全角と半角も変えない（どれもパスワードの一部でありうるため）。pdfium は、古い方式（revision 2〜4）では UTF-8 を PDFDocEncoding に直して照合し、revision 6（AES-256）では UTF-8 のまま照合する。U11 の前の試作で、RC4・AES-128・AES-256 の「café」と、AES-256 の日本語のパスワードが、閲覧・所有者のどちらでも開けた。revision 2〜4 の PDF は、PDFDocEncoding にない文字（日本語など）をパスワードに使えない。
- NUL（U+0000）を含むパスワードは、ワーカーに渡さずに誤り（`PasswordProtected`）として扱う。`pdfium-render` が C の文字列にできずに panic し、ワーカーが落ちるため（試作で確かめた）。
- `unlock_pdf`（§7.1）は、まず対象の PDF をそのパスワードで `Open` する。結果が `PasswordProtected` なら誤りとしてそのまま返し、表は変えない。`WorkerCrashed`・`WorkerTimeout` も、パスワードが合っているか分からないので、表を変えずにそのエラーを返す。それ以外（成功、または `TooManyPages`・`PdfOpenFailed` などの別のエラー）は、パスワードを受け入れたとみなし、項目のページ数・最初のページの大きさ・エラーをその結果で置き換え、パスワードを持たせる。
- 対象を受け入れたら、一覧のほかの `PasswordProtected` の項目（パスワードをまだ持たないもの）にも、同じパスワードで `Open` を試し、同じ規則で受け入れたものだけを置き換える。同じところから来た PDF（同じ銀行の明細など）は、同じパスワードのことが多いため。試すのは追加（`add_pdfs`）と同じく 1 つずつ順に行う。合わなかった項目と、試す途中でワーカーが落ちた・時間切れになった項目は何も変えず、対象の結果は返す。
- 戻り値は置き換えた項目で、対象が先頭、ほかは ID の順。フロントエンドは ID で一覧の項目を置き換え、並びは変えない。一覧が変わったので、変換の結果は消える（§10.1）。

### 6.9 書き出す PDF のパスワード（FR-02）

- パスワードは、画面のダイアログ（§10.1）の状態から `save_merged_pdf`・`start_images_to_pdfs` の引数として Rust に渡り、その変換の間だけメインプロセスが `OutputPassword`（§4.3.1）として持つ。変換が終わるか、キャンセル・失敗したら捨てる。次の保存ではダイアログで入れ直す（ダイアログを閉じたら、画面の状態からも捨てる）。
- 設定・ログ・一時ファイルには書かない。ワーカーには渡さない（書き出しはメインプロセスで行う）。メモリの消去（`zeroize` など）は §6.8 と同じ理由で行わない。
- Rust も §4.3.1 の規則で確かめ、外れたら `InvalidParams` で拒んで何も始めない（画面が先に確かめるので、通常は起きない）。
- パスワード付きの PDF は、このアプリの「PDF → 画像」でも §6.8 のとおり開ける。

### 6.10 切り出し（FR-11）

- **開く**: 「PDF を開く」（ファイルダイアログ、1 つだけ選ぶ。`open_crop_pdf`）か、切り出しのタブを表示しているときの D&D で、1 つの PDF を開く。D&D で落とされたものが PDF のファイルちょうど 1 つのときだけ開き、2 つ以上のファイル、フォルダ、PDF でないファイルのどれかを含むときは何も開かず、「切り出しでは PDF を 1 つずつ開きます」/ `Open one PDF at a time to crop` を出す（ほかのタブを表示しているときの D&D は §6.1 のまま）。D&D は Rust が受けるので、画面はタブを切り替えるたびに `set_drop_target` でどちらの扱いかを知らせる。切り出しのタブでの D&D の結果は `crop-dropped`（§7.2）で返し、一覧には何も加えない。
- **保留と切り替え**: どちらの開き方でも、Rust は PDF を開いて（`Open` でページ数と大きさを求める）**保留**の切り出しの PDF にするだけで、開いている切り出しの PDF・範囲・解析のワーカーには触れない。画面は保留の `CropPdf` を受け取ってから、入れ替えの確認（下）を済ませ、`activate_crop_pdf(id)` で保留を開いている PDF にする（前の PDF と解析のワーカーを捨てる）か、`discard_crop_pdf(id)` で保留を捨てる。確認が要らなければ、すぐ `activate_crop_pdf` を呼ぶ。保留は 1 つだけで、新しい保留は前の保留を捨てる。保留の ID には、`activate_crop_pdf`・`discard_crop_pdf` のほかのコマンドは `UnknownHandle` を返す。
- **入れ替え**: PDF を開いているときに別の PDF を開くと、まだ書き出していない範囲（この PDF で一度も書き出していない範囲）があれば、「書き出していない範囲を破棄して開きますか？」の確認のダイアログを、開くファイルの名前を添えて出す（ファイルを選んだあと、`activate_crop_pdf` の前）。チェックを外した範囲も数える。「破棄して開く」で `activate_crop_pdf`、「キャンセル」（Esc を含む）で `discard_crop_pdf` を呼ぶ。開いたときのフォーカスは「キャンセル」に置く（Enter を押し続けて範囲を失わないため）。確認を出している間に次の保留が届いたら（D&D）、Rust はもう前の保留を捨てているので、ダイアログの名前と対象を新しい保留に替える。確認は、エラーのない保留と `PasswordProtected` の保留に出す（ほかのエラーの保留は、確認なしに捨てる。§10.1）。
- **切り出しの項目は一覧と分ける**: 切り出しの PDF（保留と開いているもの）は、一覧の表（`items.rs`）とは別に持つ。ID は一覧と同じ数え方で振る（ID が重ならないように）。同じファイルが一覧にあっても開ける（一覧の重複の判定に入れない）。一覧のコマンドは切り出しの ID を知らない ID として扱う（`start_pdfs_to_images`・`save_merged_pdf`・`start_images_to_pdfs`・`unlock_pdf` は `UnknownHandle`、知らない ID を飛ばす `remove_items`・`check_page_range` は何もせず数えない）。切り出しのコマンドに一覧の ID を渡すと `UnknownHandle`。`get_thumbnail` だけはどちらの ID も受ける。
- **パスワード**: パスワード付きの PDF は、`activate_crop_pdf` のあと、§6.8 と同じダイアログで `unlock_crop_pdf` を呼んで開く（戻り値が `CropPdf` で、一覧の `PdfItem` と形が違うため、`unlock_pdf` とは分ける）。受け入れの規則は §6.8 と同じ。一覧の PDF とパスワードを使い回さない（一覧の `unlock_pdf` は切り出しの PDF を試さず、`unlock_crop_pdf` は一覧の PDF を試さない）。開けない（エラーを持つ）切り出しの PDF には、`get_thumbnail`・`list_page_images`・`check_on_top`・`detect_layout`・`start_*` がそのエラーを返す。
- **ページの表示**: 左のサムネイル（`THUMBNAIL_SIDE`）でページを選び、中央にそのページを大きく出す（`get_thumbnail` の `maxSide` を表示の大きさと画面の倍率から決め、`PAGE_VIEW_MAX_SIDE` まで）。ページを表示したら、そのページの埋め込み画像の一覧（`list_page_images`）とレイアウトの解析（`detect_layout`）を要求する。どちらもページごとに 1 回だけ要求し、結果は PDF を入れ替えるまで画面が持つ。解析の結果を待つ間もページは操作できる。解析の要求は画面から同時に 1 つだけ送り、待っている間にページが変わったら、答えが来たあとに、最後に表示したページだけを次に要求する（間に表示したページは、表示し直したときに要求する。ページを次々にめくると解析のワーカーに要求が溜まり、今のページの結果が遅れるため）。
- **範囲**: 画面の状態で持ち、Rust は書き出すときにだけ受け取る。範囲は `{ key, page, kind, rectPt, imageIndex }`。`key` は画面が 1 から順に振る整数（`job-item` の `id` が数のため）。`kind` は `photo`（写真の範囲）・`figure`・`chart`・`table`（候補から）・`manual`（手で選んだもの）。写真の枠のクリックと、`photo` の候補は `photo` になる（`rectPt` は画像の枠。写真の候補の `rectPt` も画像の枠なので同じ）。`photo` の範囲を手で動かしたり大きさを変えたりしたら `manual` になる（元の画素の格子から外れるため。`imageIndex` と重なりの印を捨てる）。ほかの種類は、動かしても種類を変えない。動かす・大きさを変えた範囲は、書き出し済みでなくなる（書き出し済みの `key` から外し、入れ替えの確認で数える。書き出したものと範囲が食い違うため）。手で描いた範囲と、動かす・大きさを変えることには、下の重なりの判定を当てない（利用者が置いた位置のため）。範囲を追加したときに、`photo` なら `check_on_top` で重なりの印を求める。
  - **重なった範囲を 2 度加えない**: 範囲を加えるとき（枠・候補のクリック、「範囲を追加」の 3 つ、全ページの候補）、同じページに、加える範囲との IoU が `CROP_DUPLICATE_IOU` 以上の範囲がすでにあれば加えない。クリックのときは、加えずにその範囲を選ぶ。同じ画像の写真の枠と写真の候補は同じ枠なので、IoU は 1 になる。
  - **選ぶ**: 範囲は 1 つだけ選べる。ページの上の範囲か一覧の行を押すと選ぶ。クリックで加えた範囲と、手で描いた範囲（Enter でページ全体に描いたものを含む）は選ばれる（「このページの候補をすべて追加」と全ページの候補で加えた範囲は選ばない）。ページの空いた所を押すと選ぶのをやめる。選んでいる範囲を消すと、どれも選ばれていない状態になる。
  - **取り消し（Undo・Redo）**: 範囲の一覧を変える操作（加える、消す、動かす・大きさを変える、チェックを変える、候補を隠す）を、1 つずつ取り消し・やり直しできる。選ぶこと、ページと表示、書き出しの設定、書き出しは操作にならない。全ページの候補は、始めてから加えた範囲すべてで 1 つの操作。
    - 範囲の `key` は戻さない（次に振る `key` は増えるだけにする。書き出しの結果の `id` と重ならないため）。取り消しで戻ってきた・形が変わった範囲は書き出し済みから外す（書き出したものと合っているかを確かめず、書き出していない側に倒す）。
    - 履歴は `CROP_HISTORY_LIMIT` 個まで持つ。新しい操作でやり直しの履歴を、別の PDF を開くと履歴のすべてを捨てる。変換中（範囲を固めている間）は、取り消し・やり直しもできない。
  - **ページの問い合わせを順に送る**: 写真の範囲の書き出す大きさには、そのページの `list_page_images` の答えが要る。全ページの候補では表示していないページに写真の範囲が加わるので、画面は、そうしたページの `list_page_images` と `check_on_top` を、同時に 1 つだけ順に送る（どちらもプールのワーカーで PDF を開くので、一度に送るとワーカーが並ぶため）。表示中のページの `list_page_images` は待たせない。`check_on_top` が失敗したら印を出さない（書き出しは妨げない）。
- **全ページの候補**: 「全ページの候補をすべて追加」は変換の 1 つとして扱う（`start_detect_all`。同時に 1 つだけ、§7.1）。解析のワーカーで 1 ページ目から順に解析し、まだ解析していないページだけを処理する（Rust は、`detect_layout` と全ページの解析で答えたページを、切り出しの PDF ごとに覚える）。ページごとに `layout-page` で候補を返し、画面はそのページの候補のうち、すでにある範囲と重なるもの（上の「重なった範囲を 2 度加えない」）以外を範囲に加える。キャンセルは次のページの前に確かめる。1 ページが `WorkerCrashed`・`WorkerTimeout` になったら、そのページの `layout-page` にエラーを入れて次のページへ進む。`LayoutUnavailable` になったら、そのページの `layout-page` にエラーを入れて全ページの解析を終える。`layout-page` は Rust が解析したページだけに送る。すでに解析してあったページの候補は、画面が持っている結果から加える。画面は、始めたときに答えを持っているページの候補をすぐ加え、始めたときに `detect_layout` の答えを待っていたページは、その答えが届いたときに加える（Rust がそのページを解析済みとして飛ばすことがあるため。`layout-page` とその答えの両方が届いても、IoU の規則で 2 度は加わらない）。ただし、答えが届く前にほかの操作か取り消しをしたら、加えない（届いた範囲がどの操作にも属さず、取り消しで黙って消えるため。候補はそのページに残る）。`layout-page` の答えは、画面の持つそのページの解析の結果にもする（ページを表示したときに `detect_layout` を送り直さないため。エラーなら失敗の結果にし、`LayoutUnavailable` なら `detect_layout` と同じく以後の解析を送らない）。加える範囲の順は、ページの順、ページの中は候補の順（スコアの高い順）。進捗（`job-progress`）の `total` は解析するページの数で、`job-item` は送らない。`job-finished` はページで数える（`succeeded` は候補を返したページ、`failed` はエラーのページ、`unprocessed` はキャンセルか `LayoutUnavailable` で届かなかったページ）。解析するページがなければ、すぐに `job-finished`（すべて 0）を送る。
- **書き出し**: 「書き出す」で、チェックの入った範囲と、形式・色・解像度・写真の 2 つの選択肢を `start_crop_export` に渡す。保存先は §6.5 のとおり確かめる。名前は §6.4 の規則で、開始のときに全部を決める。範囲は、ページの順、ページの中は位置の順（§6.4。名前の番号と同じ順）に書き出す。プールのワーカーを 1 つ借りて PDF を 1 回 `Open` し、範囲ごとに `RenderRegion` を行い、§6.5 の方式で保存して、最後に `Close` する。並列にはしない（1 つの PDF なので）。進捗は範囲で数え（`current` は PDF の名前）、範囲ごとに `job-item`（`id` は範囲の `key`、`outputs` は保存した名前）を送る。失敗した範囲（`RenderTooLarge` など）は飛ばして続け、`WriteFailed` は §6.5 のとおり打ち切る。`WorkerCrashed`・`WorkerTimeout` になったら、その範囲を失敗にして、残りの範囲は試さない（§5.2 と同じく、同じ PDF でワーカーが落ち続けるのを避けるため。残りは書き出していないままなので、画面からもう一度書き出せる）。キャンセルは次の範囲の前に確かめる。届かなかった範囲には `job-item` を送らず、`job-finished` の `unprocessed` に数える。書き出した範囲（`job-item` が `ok`）は「書き出し済み」とし、入れ替えの確認の対象から外す。もう一度書き出すと、同じ名前の規則で書く（同名のファイルがあれば `(1)` を付ける）。
- **変換中の切り出しのタブ**: 書き出しと全ページの解析のどちらの間も、ほかのタブと同じく範囲と設定を固める（範囲を加える・描く・消す・動かす・大きさを変える・チェックを変える・取り消す・やり直す、書き出しの設定、「別の PDF を開く」、「範囲を追加」のメニュー）。ページの切り替え、表示の大きさ、「候補」の表示、範囲を選ぶことはできる。全ページの解析が加える範囲は、固めている間も加わる。ほかのタブの変換の間も同じに固める（Rust が、切り出しの PDF を開くことと、別の変換を始めることを拒むため）。ただし、プールのワーカーが 1 つのマシン（論理 CPU が 2 つ以下。§5.2）では、書き出しがそのワーカーを使い続けるので、まだ届いていないページの画像・サムネイル・写真の一覧は、書き出しが終わるまで出ない（要求は空きを待つだけで、失敗にはならない）。そうしたマシンはまれなので、書き出しの間に問い合わせのためのワーカーを空けておく作りにはしない。
- タブを切り替えても、開いた PDF と範囲は残る（画面の状態に持つ）。アプリを終えると捨てる。

| `items-dropped` | `{ images: ImageItem[], pdfs: PdfItem[], skipped, error: IpcError \| null }`（変換中に落とされたときは何も加えず、`error` を `ConversionRunning` にする。切り出しのタブを表示しているときの D&D では送らない） |
| `crop-dropped` | `{ cropPdf: CropPdf \| null, notOnePdf: boolean, error: IpcError \| null }`（切り出しのタブを表示しているときの D&D。§6.10。`cropPdf` は保留の PDF。PDF のファイルちょうど 1 つでなければ `notOnePdf` を `true` にして何も開かない。変換中は何も開かず `error` を `ConversionRunning` にする） |
| `job-progress` | `{ done, total, current: string \| null }`（`total` はどちらもページの合計。画像 → PDF では TIFF の全ページを数える。§6.2） |
| `job-item` | `{ id, status: "ok" \| "failed" \| "partial" \| "noPages" \| "cancelled", outputs: string[], error?, failedPages? }` |
| `job-finished` | `{ succeeded, failed, noPages, unprocessed, cancelled }` |
| `layout-page` | `{ id, page, candidates: Candidate[], error: IpcError \| null }`（`start_detect_all` の 1 ページごと。解析に失敗したページは `candidates` が空で `error` を持つ。§6.10） |

- `failedPages` は、PDF → 画像で書き込みやページの描画に失敗したページの番号。`partial` と `failed` のほか、キャンセルした PDF の `cancelled` にも、それまでに失敗したページがあれば入る。PDF を開けないなど PDF ごとの失敗では入らない。

## 8. pdfium の同梱と更新

### 8.1 取得

- `scripts/fetch-pdfium.ts` が、bblanchon/pdfium-binaries の GitHub Releases から OS ごとの tgz を取得し、SHA-256 を照合してから `src-tauri/pdfium/<os>/` に展開する。版とハッシュは `scripts/pdfium-version.json` の 1 か所に置く（版の正本）。
- 開発者は `npm run pdfium:fetch` を一度実行する。CI と release.yml も同じスクリプトを使う。取得したファイルはコミットしない。
- アプリは通信しない（NFR-01）。取得するのはビルドのときだけ。

### 8.2 同梱

- `tauri.conf.json` の `bundle.resources` で、その OS のライブラリ（`pdfium.dll` / `libpdfium.so`）をリソースとして同梱する。MSI、NSIS、AppImage、.deb のすべてで、メインプロセスが `resource_dir()` から場所を求め、ワーカーに渡す（§5.4）。
- 開発時（`tauri dev`）も、Tauri がリソースを `target/<profile>/pdfium/` に写すので、同じ `resource_dir()` の仕組みで見つかる。リソースの指定は `tauri.linux.conf.json` と `tauri.windows.conf.json` に OS ごとに置く。

### 8.3 ライセンス

- `scripts/generate-licenses.ts` が、取得した tgz の `LICENSE` と `licenses/` の 14 件を第三者ライセンス一覧に加える。版は `pdfium-version.json` から入れる。
- FreeType のライセンスが求める表示は、「このアプリについて」の一覧で満たす。
- ライセンスの許可リストの検査（NFR-05）と第三者ライセンス一覧は、配布物に入る依存だけを対象にする。テストとフィクスチャの生成にだけ使う dev-dependencies は除く（`deny.toml` の `[graph] exclude-dev = true`）。配布物に入らないものに同梱の条件は掛からないため。例: `jpeg-encoder` は IJG ライセンスを含むが、フィクスチャの生成にだけ使う。

### 8.4 更新の確認

- Dependabot は pdfium の版を見ないので、`.github/workflows/pdfium-update.yml` を月 1 回実行し、bblanchon/pdfium-binaries の最新の版が `pdfium-version.json` より新しければ Issue を作る（すでに同じ版の Issue があれば作らない）。
- 更新は手で行う: 版とハッシュを書き換え、`pdfium-render` の `pdfium_NNNN` 機能を §2 の規則で選び直し、§11 のテストを通してから PR にする。
- pdfium の脆弱性は、Chromium のセキュリティ修正として公開される。月 1 回の更新で取り込む。

### 8.5 onnxruntime とレイアウトの解析のモデル（FR-11）

- **取得**: `scripts/fetch-layout.ts` が、`scripts/layout-version.json` に置いた版と SHA-256 で次を取得・照合し、`src-tauri/onnxruntime/<os>/` と `src-tauri/layout-model/` に置く。`npm run pdfium:fetch` と同じく開発者・CI・release.yml が実行し、取得したものはコミットしない。アプリは通信しない（NFR-01）。
  - onnxruntime: microsoft/onnxruntime の GitHub Releases の OS ごとのアーカイブから、ライブラリと `LICENSE`・`ThirdPartyNotices.txt` を取り出す。
  - モデル: このリポジトリの GitHub Releases に置いた int8 のモデル（`layout-model-N` のタグ）。モデルの `LICENSE`（Apache-2.0 の全文）と改変の表示（`NOTICE`）は、Release には置かず `scripts/layout-model/` にコミットする（取得するものではなく、版ごとに変わらないため）。
- **量子化**: int8 のモデルは `scripts/quantize-layout-model.py` で作る（維持する人が一度だけ実行し、Release に置く）。元は Hugging Face の `PaddlePaddle/PP-DocLayout_plus-L_onnx` で、コミットとハッシュを固定して照合する（固定の値と量子化の手順はスクリプトが正本）。ネットワークを切ったコンテナで実行する（外から来たモデルを読むため）。同じ版の onnxruntime なら、何度実行しても同じファイルになった（試作）。ビルドのたびに量子化しないのは、CI に Python と onnxruntime の量子化の道具を入れずに済ませるため。
- **同梱**: pdfium と同じく、`tauri.<os>.conf.json` の `bundle.resources` で同梱し、`resource_dir()` から場所を求めてワーカーに渡す（§5.4）。インストーラーは、モデル（xz で約 23 MB）と onnxruntime（Windows の DLL は xz で約 4 MB）のぶん大きくなる。
- **ライセンス**: `scripts/generate-licenses.ts` が、onnxruntime の `LICENSE`（MIT）と `ThirdPartyNotices.txt`、モデルの `LICENSE`（Apache-2.0）と改変の表示（「PaddlePaddle の PP-DocLayout_plus-L を int8 に量子化した」。どちらも `scripts/layout-model/`）を第三者ライセンス一覧に加える。版は `layout-version.json` から入れる。
- **更新**: onnxruntime の版は、§8.4 の `pdfium-update.yml` と同じ月 1 回の確認に加える（新しい版があれば Issue を作る）。更新は手で行い、`ort` の `api-NN` 機能を合わせ、§11 のテストを通す。モデルの更新（新しい版のモデル）は、下調べと同じ比べ方で精度を確かめてから、`layout-model-N` を作って行う。

## 9. セキュリティ（NFR-01）

SVG Tracer §7 と同じにする（capabilities は `core:*` の最小集合、CSP、HTTP クライアントを `cargo-deny` の `bans` で禁止、WebView2 の起動オプション、止められない通信の README への記載、既知の脆弱性の検査）。加えて次のとおり。

- **依存の入手経路**: 悪意のある版が公開されても、多くは数日のうちに見つかって取り下げられる。そこで、公開から 7 日たっていない版は入れない（Dependabot の `cooldown`、npm の `min-release-age`。Dependabot のセキュリティ更新は待たない）。Tauri の crate と `@tauri-apps/*` の PR が同時に出るよう、cargo と npm の日数はそろえる。npm の依存のインストール時スクリプトは実行しない（`ignore-scripts`）。Rust の `build.rs` と proc-macro はビルドのたびに実行され、止められないため、入口を絞って補う。crate は crates.io からだけ取る（`cargo-deny` の `sources`）。CI とインストーラーのビルドは `Cargo.lock` と `package-lock.json` のとおりに入れる（`--locked`、`npm ci`）。pdfium は §8.1 のとおり SHA-256 で照合する。
- **リリースの書き込みの権限**: `release.yml` で Release を書ける権限を持つのは、下書きを作る最後のジョブだけにする。検査とビルドのジョブは外部の action と依存のビルドのコード（`build.rs`、npm のパッケージ）を実行するので、読み取りの権限だけで動かし、`actions/checkout` にもトークンを残させない（`persist-credentials: false`）。最後のジョブは GitHub CLI だけを実行し、ビルドの成果物を受け取って下書きに添付する。下書きは、検査と両 OS のビルドがすべて通ってから作る。タグは main にあるコミットに限る（main は両 OS の CI を通った PR からしか変わらないため）。
- 画像（TIFF を含む）はメインプロセスで読む。読み込みは純 Rust の crate（`image`、`tiff`）だけで行い、寸法と展開の大きさに上限を置く（§4.1、§4.1.1）。C のライブラリで読む PDF と違い、壊れたファイルで異常終了するおそれが小さいため、ワーカーに分けない。
- PDF はワーカーでだけ開く（§1、§5）。メインプロセスに pdfium を読み込まない。`crates/worker` 以外の crate が `pdfium-render` に依存していないことを、`cargo-deny` の `bans`（`wrappers` の指定）で確かめる。`ort`（onnxruntime）も同じく `crates/worker` だけに置き、同じ方法で確かめる。
- onnxruntime とモデルは §8.5 のとおり版と SHA-256 で照合して取得し、同梱する。モデルを読むのはワーカーだけで、入力は PDF を描いた画素だけ（モデルのファイルを利用者が差し替える手段は設けない）。
- ワーカーには、開く PDF のパス、利用者が入れたパスワード（§6.8）、pdfium・onnxruntime・モデルの場所だけを渡す。ワーカーはファイルを書かない。
- 書き出す PDF の暗号化（§4.3.1）はメインプロセスの `lopdf`（純 Rust）で行う。`lopdf` が読むのは krilla がその場で書いた PDF だけで、利用者が追加した PDF は読まない。書き出しのパスワードは §6.9 のとおり扱う。
- サムネイルと描画した画像は、`blob:` URL にして `<img>` で表示する。
- WebView2 の起動オプションの `--host-resolver-rules` は、SVG Tracer の `MAP * ~NOTFOUND` に `EXCLUDE localhost` を加える。`tauri dev` の画面は Vite（`devUrl` の `http://localhost:5173`）から読むので、`localhost` の名前解決まで失敗させると Windows で開発用の画面が開かない（`ERR_NAME_NOT_RESOLVED`）。製品版で `localhost` の名前解決が通っても、CSP が許す接続先は画面自身（`'self'`）と IPC だけなので、画面から `localhost` には接続できない。PAC や外部のサーバーへの名前解決は、これまでどおりすべて失敗する。

## 10. フロントエンド

### 10.1 画面構成

見た目と配置はモックアップ（`docs/mockup/project/`）、文言は `src/i18n` の辞書、細かな振る舞いは画面のテストを正本とする。ここには、画面をまたいで守る決まりと、その理由だけを置く。

**共通**

- ウィンドウの既定の大きさは 1200×800、最小は 960×640。画面の配置は、最小の大きさでも上部バー・ツールバーが 1 行に収まり、一覧とページが使える大きさに残ることで決める。
- 上部バー: アプリ名、タブ（画像 → PDF / PDF → 画像 / 切り出し）、言語の切り替え、「このアプリについて」。
- 押せない状態でも、選んだ値は状態と設定に残し、選んだ選択肢を示す。条件があって押せない欄は、隠さずに押せなくして理由を添える（画像 → PDF の「向き」は「画像と同じ大きさ」の間は押せない。出したり消したりすると、ドロップダウンを閉じた所に欄が現れて残像のように見え、下の欄も動くため）。
- 選択肢が多く設定パネルの幅に収まらないもの（「ページの大きさ」、解像度）はドロップダウンにし、ほかは切り替えのボタンにする。押すと選択肢が開くものは、画面のどこでも同じ矢印のアイコンで示す（WebView の矢印は使わない）。
- 用紙の選択肢には縦向きの寸法を添え、日英で同じ文字列にする（B 判が JIS か ISO かを寸法で見分けられるようにするため）。
- 解像度は、選択肢（`DPI_CHOICES`）と「数値で指定…」。数値の欄は §4.4 の範囲の整数だけを受け、範囲は Rust の `RENDER_DPI_MIN`・`RENDER_DPI_MAX` を写した定数で画面が確かめる（整数を読むだけなので、範囲の解釈（§4.5）と違い画面で確かめる。Rust も同じ範囲で拒む）。誤りの間は実行のボタンを押せず、状態と設定の `dpi` は最後の正しい値のままにする。「数値で指定…」を選んでいるかは保存しない。
- ページのサムネイルは、グレースケールで書き出すときもカラーのまま出す（ページの確認と選択のためのもので、出力の見本ではないため）。
- アプリ内のダイアログ（パスワード、このアプリについて、キー操作の一覧、確認）は、開いたときのフォーカスの置き場、Enter と Esc、閉じたときのフォーカスの戻し先を決めておく。範囲を失う確認では、フォーカスを取り消す側に置く（Enter を押し続けて範囲を失わないため）。
- WebView2 のブラウザーのショートカットのうち、Windows のインストール版で押して何かが出るもの（検索、印刷、再読み込み、ダウンロードの一覧、キャレット ブラウズ）は、入力欄にフォーカスがあっても止める（`BLOCKED_BROWSER_SHORTCUTS`）。拡大・縮小、コピー、貼り付け、全選択、元に戻すなどは止めない。WebView2 の `AreBrowserAcceleratorKeysEnabled` は Tauri から変えられず、`unsafe` を足すことになるので使わない。

**画像 → PDF の「PDF の形式」**

- 「標準」「PDF/A」「パスワード」の 3 つから 1 つを選ぶ切り替えのボタンにする。状態と設定は `pdfA` と `encrypt`（§6.7）の 2 つの真偽のままで、画面はその組から 1 つを示し、押したものに合わせて 2 つを一度に変える。PDF/A は暗号化を禁じる（§4.3.1）ので、2 つが同時にオンになることはない。規格の種類（2b）は画面に出さない。
- 「PDF/A」の間は CMYK の画像を使えないことを、変換を始める前に補足で示す。「パスワード」の間は、下部バーの予告にもパスワード付きであることを添える。

**パスワードのダイアログ**

- 書き出しのパスワード（§6.2、§6.9）: 「PDF を保存」「変換を開始」を押したときに開く。2 回入れ、条件（§4.3.1 の文字の種類と、2 回の一致）を満たしたときだけ進める。条件は打っている途中で赤にしない（確認の欄がパスワードの先頭と一致している間は、まだ判断しない）。条件の一覧は 1 文字ごとに読み上げさせない（`aria-live` にしない）。長さの上限は、超えたときだけ示す（ほとんどの人が届かない上限を常に見せないため）。入力欄に `maxlength` を付けない（貼り付けた文字が黙って切られ、利用者の知らないパスワードになるため）。長さのおすすめは出さない。「1 枚ずつ」では、すべての PDF に同じパスワードが付くことを示す。パスワードを忘れると開けなくなることを添える。
- パスワード付きの PDF を開く（§6.8）: パスワード付きの PDF（エラーが `PasswordProtected` の項目）は、エラーではなく入力を待つ状態として、鍵の記号と黄色（§10.3）で示し、「パスワードを入力」のボタンを添える。追加したときに自動ではダイアログを開かない（フォルダから多数の PDF を追加すると、ダイアログが続くため）。変換中は押せない。パスワードが違うときはダイアログを閉じず、誤りを出して入れ直せるようにする。ほかの PDF もあわせて開いたことは、行の表示が変わるので別に知らせない。読み込めない項目がすべて `PasswordProtected` のときは、下部バーを赤の「外してください」ではなく、パスワードを入れれば変換できるという文にする。
- どちらのダイアログも、閉じたら（取り消しでも）入れたパスワードを画面の状態から捨てる（次に開いたときは空）。

**一覧と下部バー**

- 右の一覧: 空のときはドロップ領域。画像は行の一覧（並べ替えと外すことができる）。PDF は 1 つならページのサムネイルの格子（§6.3）、複数なら表。
- 下部バーの左には、変換していない間、実行のボタンを押すと何が起きるかを 1 行で出す（数えるのはエラーのない項目だけ）。保存するファイル名の例は出さない（名前の規則を §6.4 の 1 か所に置くため）。「範囲を指定」のページ数は `check_page_range` の答えを使い、画面で範囲を数えない（§4.5）。一覧が空のとき、すべて読み込めない項目のときは、それぞれ実行のボタンを押せない理由を出す。
- 変換が終わったら、その画面の最後の変換の結果を、下部バーの左に件数の 1 行で出す（3 つの画面で同じ形）。一覧の上に帯は出さない（帯が出入りするたびに一覧が動き、同じ結果が下部バーにも出ていたため）。結果の成否は色と記号の両方で示し（§10.3）、理由は結果に書かずに一覧の各行に出す。「1 つの PDF」をキャンセルしたときと、全部の画像が失敗して PDF を書かなかったときは、PDF を保存していないことが分かる文にする（処理した件数を出すと、保存したように読めるため）。「1 つの PDF」をキャンセルしたときは、すでに処理した行も「キャンセル」とする。
- 結果は、その画面の一覧か設定が変わったら消し、下部バーは予告の 1 行に戻す（件数・行の状態・失敗したページが、もうない項目や設定を指すことになるため）。変換中は消さない。

**切り出しのタブ**（FR-11、§6.10）

- 配置: 左にページのサムネイルの縦の列、中央にページ、右に範囲の一覧と、その下に書き出しの設定。設定パネルをほかのタブのように左に置き、サムネイルをページの下の帯にする形は、最小のウィンドウでページと一覧が小さくなりすぎるので採らない。
- 書き出しの設定は見出しのボタンで開閉し、閉じている間は今の設定を 1 行の要約で出す。起動したときは、ウィンドウの高さにかかわらず閉じておく（開いた設定は高く、既定の大きさでも範囲の一覧がほとんど見えなくなるため）。開閉は保存せず、タブの切り替えや別の PDF を開いても変えない。
- 開くとき（§6.10 の保留と切り替え）: `PasswordProtected` 以外のエラーを持つ保留は、捨てて今の PDF をそのままにし、エラーを帯で出す（壊れたファイルで今の作業を失わないため）。`PasswordProtected` の保留は、入れ替えの確認のあと開いている PDF にし、パスワードのダイアログを開く（取り消したら、開き直すボタンを中央に出す）。PDF を表示できない間も、別の PDF を開けるようにしておく。お知らせとエラーの帯は、ツールバーが動かない場所（PDF を開いていればツールバーの下）に出す。`LayoutUnavailable` はエラーではなく、手で選べることを伝えるお知らせにする。
- ツールバーは最小のウィンドウでも 1 行に収める（長い名前は名前だけが縮む）。今のページの番号は出さない（サムネイルの番号と枠で分かるため）。
- ページの表示: 既定は「全体を表示」（ページのどこに何があるかを一目で見て範囲を選ぶため）。倍率は表示のメニュー、−・＋（`CROP_ZOOM_STEPS` の次の段）、Ctrl+ホイールで変える。Ctrl+ホイールは WebView 全体の拡大にしない。Ctrl+0 は割り当てない（WebView 全体の拡大を戻すキーのため）。ページの画像は、表示の大きさを `CROP_PAGE_SIDE_STEPS` の段に切り上げた大きさで求め（倍率を変えるたびに描き直さないため）、新しい画像が届くまでは前の画像を拡大・縮小して出す。
- ページの上には、候補の枠、写真の枠、範囲を重ねる。候補と写真の枠は、どちらも押すと範囲になり、見つけ方の違いは使い方を変えないので、見た目を分けない。重なりの判定（§6.10）で同じとみなす範囲がある候補と枠、写真の候補がある画像の枠は描かない（同じものが二重に描かれ、Tab も 2 度止まるため）。書き出さない範囲（一覧のチェックを外した範囲）は、ページを見るだけで分かる形（点線）にする。
- 重ねる順は、面積の大きいものほど下にし、押したときはその場所でいちばん小さいものが受ける（外側を誤って「図」と認識した候補や、ページ全体の範囲があっても、内側の写真や図を押せるようにするため）。外側の大きい範囲は、内側に何もない所か、札か、一覧の行で選ぶ。種類の札は、選んでいる範囲の札をいちばん上に出し、取っ手と重ならない位置に置く。
- ページの状態の札: 範囲を描く状態、解析を待つ間、候補を隠している間、そのページの問い合わせの失敗を、ページの領域の隅の札で知らせる（描く状態を示すボタンがなく、候補を隠したことはメニューの中でしか分からないため。候補の出ないページを、解析の失敗と取り違えないため）。札は押せず、札の下のページから操作を始められる。
- 範囲を加える手段: 枠・候補を押す、「範囲を追加」のメニュー（このページの候補をすべて、全ページの候補をすべて、範囲を描く）、範囲がないときの右の欄の「全ページの候補を追加」のボタン（主な使い方の入り口を、まず目に入る所に置くため）。「ページ全体を範囲にする」は置かない（ページ全体の画像は「PDF → 画像」が、スキャンしたページは写真の枠が受け持つ）。
- 範囲を描く: 何もない所から範囲を作るのは、「範囲を描く」か R を押したあとの 1 回だけにする（主な使い方は解析の候補を確かめて書き出すことで、手で描くのは補いのため。いつでもドラッグで描く作りは使いにくかった）。描く状態を切り替えるボタンは置かず、状態の札とカーソルで示す。描く状態で Enter を押すと、ページ全体の範囲を加える（ポインターを使えない利用者の道）。描く状態は保存せず、変換の開始、別の PDF を開く・閉じるで元に戻す。
- 範囲の編集（ポインター）: クリックとドラッグを動いた距離（`CROP_DRAG_THRESHOLD_PX`）で分ける。クリックは、枠・候補なら範囲を加え、範囲なら選び、空いた所なら選ぶのをやめる。ドラッグは、選んでいる範囲の取っ手なら大きさを変え、範囲の内側なら動かし、それ以外ならページの表示をつかんでスクロールする（倍率を上げたページを動かすため）。ホイールボタンのドラッグは、どこから押してもページの表示をつかむ（ページのほとんどを覆う範囲があると、主ボタンではつかむ所がなくなるため）。取っ手の押せる広さは見た目より広くする（`CROP_HANDLE_HIT_PX`）。範囲はページの中に収め、`CROP_MIN_AREA_SIDE_PT` より小さくしない。ドラッグの間は画面の中だけで形を描き直し、状態は離したときに 1 度だけ変える。Esc やページの切り替えなどでドラッグを取りやめたら元のままにする。変換中（範囲を固めている間）は、取っ手を出さず動かせない（選ぶこととページをつかむことはできる）。
- 取り消し・やり直しはキーだけにする（ボタンを置かず、キー操作の一覧で知らせる）。文字の入力欄、ダイアログ、ドラッグの間は効かせない。ほかの 1 文字のキー（R、`?`）も同じ。
- キーボード（NFR-07）: 写真の枠・候補・範囲はフォーカスを受けるボタンにし、Tab の順は重ねる順（大きいものから小さいものへ）にする。Enter・Space で加える・選ぶ、矢印で動かし、Alt+矢印で大きさを変え（Shift で大きく。`CROP_KEY_STEP_PT`・`CROP_KEY_STEP_LARGE_PT`）、Delete・Backspace で消す。候補で Delete を押すとその候補を隠す（誤って認識した候補を退けるため。取り消せる）。ドラッグできない利用者は、範囲を描く状態の Enter でページ全体の範囲を加え、矢印で動かして縮められる。フォーカスの輪は、範囲と選んだ行がアクセントの色を使う所では文字の色にする（輪がアクセントの色だと選んだように見えるため）。キーで範囲を消したあとは、ほかの範囲にフォーカスを移さない（輪がほかの範囲を選んだように見えるため）。
- ページの表示の右クリック（Shift+F10・メニューキーでも）では、ブラウザーのメニューを出さず、ページのメニュー（候補を隠す、隠した候補を戻す）を出す。マウスで候補を隠す手段を札の × にしないのは、札の × は小さく、隣の札の下に隠れることがあり、ポインターを乗せるたびに出入りして騒がしいため。メニューはどれも WAI-ARIA のメニューボタンの形にそろえる。
- 範囲の一覧の行: 書き出すかのチェック、プレビュー、種類、書き出す大きさ、重なりの印、消すボタン。書き出す大きさは画面が計算し、ワーカーの描き方（§4.6）と同じ規則にする（写真の元の画素、上限を超えた写真の縮小）。埋め込み画像の一覧がまだないページの写真は、大きさを出さずに待つ。重なりの印は、判定が物の種類を区別しないので、重なった物の種類を名指ししない。行はページごとにまとめ、一覧を送ってもそのページの行が見えている間は上に残るページの見出しを付ける（候補を何十個も加えると、行ごとのページ番号ではページの切れ目が分からなかったため）。選んでいる行は、チェックの入った箱（アクセントの色）と見分けられる色にする（「選んでいる」と「書き出す」が同じ色だと見分けられないため）。範囲を選んだら、その行が見えるように一覧を最小限だけ送る（範囲はたいていページで選ぶので、行が一覧の外に隠れたままになるため）。
- 行の状態は、ほかのタブと同じ語で出す。書き出した範囲は「書き出し済み」とする。書き出しの間に、どの行を書いているかは示さない（`job-progress` の `current` からは書いている範囲を割り出せないため。下部バーの進捗で示す）。
- 結果を消すのは、範囲と書き出しの設定が変わったとき（範囲を加える・消す・動かす・大きさを変える・チェックを変える・取り消す・やり直す、設定を変える、別の PDF を開く）。ページの切り替え、表示、範囲を選ぶこと、解析と問い合わせの答えでは消さない。全ページの解析が加えた範囲は、その実行の結果を消さない。

### 10.2 状態管理、多言語

SVG Tracer §8.3、§8.4 と同じ（`useReducer` と Context、`ja.ts` を基準にした型付きの辞書）。reducer は「画像 → PDF」「PDF → 画像」「切り出し」「変換の実行」「言語」に分ける。

- 「切り出し」の状態は、開いた PDF、ページごとの埋め込み画像の一覧と候補（要求したページだけ）、範囲、選んでいる範囲、書き出し済みの範囲の `key`、取り消しの履歴、隠した候補、範囲を描く状態。別の PDF を開いたら、範囲にかかわるものを捨て、`key` を 1 から振り直す。ドラッグの途中の形は状態に持たない（離したときに 1 度だけ状態を変えるため）。
- 「変換の実行」は 3 つの画面で共通にする（変換は同時に 1 つだけで、タブを切り替えても続くため）。`job-progress`・`job-item`・`job-finished` は `App` で 1 回だけ購読する。変換を始める前に状態を「実行中」にし、コマンドの戻りより先に届いたイベントも失わない。`job-progress` の `current` はファイル名だけで ID を持たないので、変換中の行は名前と渡した順から割り出す（同じ名前の 2 つが同時に変換中のときは、1 つだけが変換中に見える）。古い結果を消すのは、画面の状態が実際に変わった操作のときだけにする。
- D&D の結果は `App` で 1 回だけ受け、一覧に加えてタブを切り替える（§6.1）。サムネイルは要素が画面に入ってから要求し、`blob:` URL にして表示し（§9）、項目が変わるか消えたら解放する。保存先の欄はフォルダの名前だけを表示する。
- 設定（§6.7）: `App` は `get_settings` の応答を待ってから画面を出す（既定値で出してから保存した値に変わると、言語や切り替えボタンが一瞬ちらつくため）。言語は、表示している言語と、利用者が選んだ言語（`null` なら OS の言語に従う）を別に持ち、後者を保存する。変更は待たずに `save_settings` で保存し（閉じる直前の変更も残すため）、拒まれても表示しない（FR-10 は Should で、変換の妨げにしない）。

### 10.3 テーマ

- 色は `styles/tokens.css` の CSS カスタムプロパティで定義する（値の正本）。SVG Tracer の tokens.css を元にし、アクセントの色をテラコッタに替える。文字と背景の比は 4.5 以上にし、`tokens.test.ts` が `tokens.css` の値で確かめる（例外は、ダークの成功の緑が選んでいる行の地の上で足りないことだけで、緑は書き出し済みの行にしか出ないので受け入れる）。
- 状態は色だけに頼らず、記号を添える: 成功は緑と「✓」、失敗は赤と「✕」、入力を待つ状態（パスワード付きの PDF）は黄色と鍵、知らせるだけのお知らせは青と「i」。実行中・キャンセル・対象のページなしは記号を付けず本文の色にし（理由の灰色の補足と見分けるため）、待機と未処理は灰色にする。アクセントの色は状態の表示に使わない。
- 失敗の赤は、アクセントのテラコッタと見分けられるよう、色相を青寄りにした深紅にする（明るさは近いので、色相と記号で見分ける）。知らせるだけのお知らせを黄色にしないのは、黄色は入力を待つ状態の色で、何か入力が要るように見えるため。
- アクセントの色は「オンになっているもの」（チェックの入った箱、選んだ形式のボタン）に使い、一覧の選んでいる行の地は灰色にする。
- キーボードのフォーカスの枠は、すべての部品で同じ形にする（WebView2 の既定の枠はテーマの色に従わず、ダークで見えにくいため）。枠は部品の外に離して描き、選んだボタン（アクセントの地）でも見分けられるようにする。切り抜かれて見えなくなる所（切り替えのボタンの外側の箱、ウィンドウの上端のタブ、`overflow: hidden` の端）では、枠が切れない描き方にする。
- エラーの見せ方は 2 つだけにする。利用者の操作の失敗と、1 つだけの PDF が読み込めないとき（パスワード付きの PDF を除く）は `ErrorDisplay`（記号付きの赤い枠の帯）、入力欄や下部バーの 1 行のエラーは `.error-text`（赤の文字に「✕」）。灰色の `.hint` でエラーを出さない。追加のときに読み込めなかった項目は「読み込めません」とし、変換で失敗した項目の「失敗」と分ける。
- フォントは SVG Tracer §8.5 と同じ（同梱しない）。

- レイアウトの解析のテストは、§8.5 で取得したモデルを使う。CI も `fetch-layout.ts` を実行する（モデルの Release を先に作っておく）。

### 11.2 品質テスト（NFR-03）

- **画像 → PDF**: 「画像と同じ大きさ」で書いた PDF を pdfium で、元の画像の dpi で描画し直し、白の背景に重ねた元の画像と比べる（画素が 1 対 1 に対応する）。不一致の画素（RGB のいずれかの差が `COLOR_TOLERANCE_IMAGE` を超える）の割合が `MAX_MISMATCH_RATIO_IMAGE` 以下。T02 の実測では、CMYK を除く全フィクスチャで差の最大が 2、不一致は 0% だった。JPEG は、加えて元のバイト列が PDF の中にそのまま含まれることを確かめる。CMYK の JPEG は色の変換が表示側に依存するので、バイト列の確認だけにする。
- **画像 → PDF の TIFF**: 読む種類の TIFF のフィクスチャ（§11.1）を、上と同じ基準で比べる。期待の画素は `gen_fixtures` が TIFF に書く前の画素（テストが同じ関数で作り直す。`tiff` の読み込みを期待の値にしない）で、透過は白の背景に重ね、`rgba_assoc.tif` は割り戻したものとする。`photo_jpeg.tif` は、JPEG のデータを `image` で復号したものを期待の画素にする（`tiff` が使う復号とは別の実装）。複数ページの TIFF はページごとに比べ、PDF のページの数と順を確かめる。横と縦の dpi が違うもの（`fax_standard.tif`、`dpi_aniso.png`）は、描画の幅と高さを元の画素の数に合わせて（横と縦の倍率を別にして）描き、画素を 1 対 1 に対応させる。加えて、ページの大きさが §4.2 の値（`fax_standard.tif` は約 610×840 pt）であること。
- **画像 → PDF の用紙**: 画像が拡大・縮小され、画素の途中の位置に置かれるので、縁がぼけて画素ごとの比較は成り立たない（T04 の前の試行で、photo.jpg の不一致が 9.8%）。代わりに配置と向きを確かめる。
  - 白の画素を含まないフィクスチャ（向きの 8 つ、`dpi300.png`、`dpi300.jpg`、`opaque.bmp`）を A4 で書いて描画し、白以外の画素の範囲を求める。それが §4.2 の配置の矩形の外接矩形（開始は切り捨て、終了は切り上げ）と、各辺 1 画素以内で一致すること。試行では 11 個すべてで満たした。用紙の寸法の換算は単体テストで 7 つすべてを確かめ、描画での配置の試験は A4 のほかに、インチで定める Letter と JIS の B5 でも行う。
  - 向きのフィクスチャは、4 つの色の領域の中心の色が元の画像と同じであること（差が `COLOR_TOLERANCE_RENDER` 以内）。
- **画像 → PDF の TIFF のメタデータ**: `metadata.tif` の PDF に、`metadata.tif` の各タグの文字が残らないこと（圧縮されたストリームも展開して探す）。
- **画像 → PDF の JPEG のデータとメタデータ**: JPEG のフィクスチャ（`photo.jpg`、`photo_cmyk.jpg`、向きの JPEG、`exif_gps.jpg`）を PDF にし、§4.3 で外したあとのバイト列が PDF の中に切れ目なく入っていることを確かめる。メタデータを持つもの（向きの JPEG、`exif_gps.jpg`）は、元のバイト列が入っていないこと。`exif_gps.jpg` の PDF には、`Exif\0\0`、画像に由来する XMP（APP1 の `http://ns.adobe.com/xap/1.0/\0` とその中身）、IPTC、COM の文字列、EOI より後ろのデータのどれも残らないこと（圧縮されたストリームも展開して探す）。XMP の名前空間そのものは探さない。krilla が PDF の文書の情報として、自分で `xmlns:xmp="http://ns.adobe.com/xap/1.0/"` を含む XMP を書くため。CMYK の色と向きは、上の比較と配置のテストがそのまま確かめる。
- 画像 → PDF の品質テストは、pdfium をテストのプロセスに読み込んで描画する。`pdfium-render` は `crates/core` の dev-dependencies で、アプリのメインプロセスには入らない（§9 の検査は dev-dependencies を除く）。
- **PDF → 画像**: `shapes.pdf` を描画し、`gen_fixtures` が同じ図形から計算した期待の画像と比べる。図形の縁のぼかし方の差を許すため、基準は `COLOR_TOLERANCE_RENDER`・`MAX_MISMATCH_RATIO_RENDER` とする。T02 の実測では最も悪いページで 0.12% だった（pdfium は画像を x 方向に 1 画素ずらして描く、A4 の高さが整数の画素にならない、などの 1 画素の差が図形の縁に出る）。実測に数倍の余裕を残しつつ、描画の劣化を見逃しにくい値にする。
- **PDF → 画像のグレースケールと WebP**: グレースケールは、同じページを同じ dpi のカラーで描いた画像から BT.601 の輝度（`0.299R + 0.587G + 0.114B` を四捨五入）を求め、グレーの画像と全画素で差が `COLOR_TOLERANCE_GRAY` 以内であること、画像が 1 チャンネルであること。U09 の前の試作では、`shapes.pdf` と写真を入れた PDF で差の最大が 3 だった（`image` の `to_luma8` は BT.709 の係数で、差が最大 28 になるので基準にしない）。WebP は、同じページを PNG で書いたものと、復号した画素が完全に一致すること（可逆）。
- 出力した PDF が一般的なビューアーで開けること（NFR-03）は、手動の確認でブラウザー内蔵のビューアーで開いて確かめる。
- **切り出しの写真の範囲（NFR-03）**: `crop_align.pdf` の 0 度・90 度・反転の置き方の画像を、元の画素で書き出し（PNG）、`gen_fixtures` が書いた模様を、置き方の向きに並べ替えたものと全画素で一致すること（不透明な画素の差が 0）。3 ページすべて（`/Rotate` 0・90・270）で同じ結果になること。回転とせん断の画像は写真の範囲にならず（`native` が `false`）、外接矩形を dpi で描くこと。上に四角を重ねた画像は、ふつうに書き出すと四角が入り、「写真だけ」では入らないこと、`ImageOnTop` が前者で `true`、ほかで `false`。ソフトマスク付きの画像を「写真だけ」の PNG で書くと、アルファがマスクの値と一致すること。
- **切り出しの範囲（NFR-03）**: 手で選んだ範囲を書き出した画像が、同じ dpi の `Render`（§4.4）の画像から同じ矩形を切り取ったものと、`COLOR_TOLERANCE_RENDER`・`MAX_MISMATCH_RATIO_RENDER` の基準で一致すること。

- **PDF/A**: §11.1 の画像のうち CMYK の JPEG と読まない種類・壊れた TIFF を除くものを、PDF/A で「画像と同じ大きさ」と A4 にし、`finish` が成功することと、上の画像 → PDF の比較に通常の PDF と同じ基準で合格することを確かめる。通常の PDF には `/Interpolate true` があり、PDF/A にはないこと。CMYK の JPEG は PDF/A で `CmykNotAllowedInPdfA` になり、「1 つの PDF」ではほかの画像のページが作られること。通常の PDF では CMYK の JPEG も今までどおり入ること。
- **パスワード付きの PDF**: §11.1 の画像のうち読める画像を「画像と同じ大きさ」と A4 で結合し、通常の PDF と、同じ PDF を §4.3.1 で暗号化したものを作る。pdfium で、パスワードなしと違うパスワードでは `PasswordError` になり、正しいパスワードでは全ページの描画が通常の PDF の描画と画素まで一致すること（試作では 21 ページすべてで一致）。暗号化の辞書が `/V 5`・`/R 6`・`/Length 256`、`StdCF` が `/CFM /AESV3`・`/Length 32` で、カタログに §4.3.1 の `/Extensions` があること。暗号化した PDF のバイト列に、作成ソフトの文字（`PDF Converter`）がそのまま現れないこと。同じ PDF を同じパスワードで 2 回暗号化すると、違うバイト列になること（鍵とソルトが毎回作られること）。
- **パスワード付きの PDF の互換（CI）**: pdfium 以外のビューアーでも開けることを、CI（Ubuntu）で qpdf・poppler（`pdftoppm`）・mupdf（`mutool`）を `apt` で入れて確かめる（U15 の前の試作で、lopdf の出力のままでは poppler だけが全ページを壊して描いた。lopdf の更新でこの種の食い違いが戻らないようにするため）。`crates/core` の例 `write_encrypted_samples` が、上の画像の結合の PDF を、通常のものと、決まったパスワード（ASCII の記号と空白を含むもの）で暗号化したものの 2 つ書く。CI は、`qpdf --check` がパスワード付きで合格し、パスワードなしでは失敗すること、`pdftoppm` と `mutool draw` がパスワード付きで全ページを描け、通常の PDF の描画と同じ画像になることを確かめる。
- **PDF/A の検証（CI）**: krilla の検証は自己申告なので、外部の検証ツール veraPDF でも確かめる。`crates/core` の例 `write_pdfa_samples` が、上の画像を 1 枚ずつ「画像と同じ大きさ」と A4 で、加えて全部を結合した 1 つを PDF/A で書く。CI（Ubuntu）がそのフォルダを veraPDF の Docker イメージ（`verapdf/cli`。veraPDF の開発元が公開している）で `-f 2b` で検証し、1 つでも不合格なら失敗にする（veraPDF の終了コードが 1 になる）。
  - イメージは版のタグでなく digest で固定する（値は `ci.yml` が正本）。更新は手で行い、公開から 7 日たった版にする（§9 の依存の入手経路）。
  - コンテナはネットワークを切り（`--network none`）、フォルダは読み取り専用で渡す。
  - veraPDF は GPL / MPL だが、CI で動かすだけで配布物に含めないので、NFR-05 には関わらない。

### 11.3 テストの一覧

テストの一覧の正本はテストのコード。層ごとに、次のことを確かめる。

| 対象 | 種類 | 確かめること |
| --- | --- | --- |
| crates/core | 単体・品質 | 純粋な処理（JPEG の区切り、probe と TIFF、ページの配置、範囲の解釈、出力名、切り出しの範囲の幾何、書き出す PDF のパスワードの規則）と、§11.2 の画像 → PDF（PDF/A とパスワード付きを含む） |
| crates/worker | 単体・品質・結合 | 要求ごとの振る舞いと上限、パスワード、壊れた PDF、§11.2 の PDF → 画像と切り出し。単独のワーカーを起動し、テスト用の要求（`test-hooks` 機能）で、異常終了・時間切れ・メモリの上限のあとにメインプロセスの側が続けて動くこと |
| src-tauri | 単体・結合 | ワーカーの数の管理と時間の上限、変換の成功・失敗・キャンセル（一時ファイルが残らないこと、`WriteFailed` の打ち切り）、設定の読み書き、パスワードの解除と書き出し、切り出しの保留と切り替え・ID の分離・解析のワーカー・書き出し・全ページの解析 |
| フロントエンド | 単体 | 画面の振る舞い（§10.1 の決まりと、モックアップと辞書に従う表示）、IPC のエラーコードから文言、状態の色と記号 |
| 全体 | 手動 | 受け入れ基準（両 OS でインストーラーから）。文字を含む実際の PDF の描画、ブラウザーでの PDF の表示、パスワード付きの PDF をほかのビューアーで開くこと。`docs/manual-test.md` |

- 一括変換の中で特定の PDF だけでワーカーが落ちる状況は、`test-hooks` 機能のときだけ、ワーカーが名前 `CRASH_ON_OPEN_FILE_NAME` の PDF の `Open` で異常終了することで作る（T08）。機能を付けないビルドには含まれない。
- 性能（NFR-02）: `shapes.pdf` の A4 のページを 150 dpi で描画する時間を `--release` のテストで測る。CI では 3 秒を超えたら失敗とし、1 秒以内は基準環境（開発者の PC）で手動確認する。
- CI は Windows と Ubuntu で、SVG Tracer と同じ検査に加え、`npm run pdfium:fetch` のあとにワーカーのテストを実行する。Ubuntu では、§11.2 の PDF/A の検証（veraPDF）も行う。

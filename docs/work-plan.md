# 作業計画

[requirements.md](requirements.md)（要件）と [design.md](design.md)（設計）を実装するためのタスク分割と進め方。進め方は SVG Tracer と同じにし、そこで分かったこと（Windows での確認は早めに行う、依存の検査は最初から入れる）を取り入れている。

## 1. 役割

| 役割 | 担当 | 責務 |
| --- | --- | --- |
| 設計・レビュー | Opus 5.5 | 要件定義・設計・作業計画の作成と更新、タスクごとのレビュー、検証結果の設計への反映 |
| 実装・テスト | Gemini 3.8 | タスクの実装とテスト、PR の作成、レビュー指摘への対応 |
| オーナー | 利用者 | 判断が必要な事項の決定、GitHub リポジトリの作成、Windows 実機での確認、マージ |

- `docs/requirements.md` と `docs/design.md` を更新するのは設計担当だけ。実装担当は設計どおりに作れない、または設計が曖昧な場合、実装を止めて PR の説明に「設計への質問」として書く。
- 実装担当のコーディング規約は [GEMINI.md](../GEMINI.md)（T00 で SVG Tracer のものを元に作る）。
- リポジトリはオーナーが GitHub に作る（公開、名前は `PDF-Converter` を想定）。Settings → Advanced Security で **Secret scanning** と **Push protection**、**Dependabot alerts** と **Dependabot security updates** を有効にする。main には SVG Tracer と同じルールセット（PR 必須、両 OS の CI 必須、ブランチが最新であること）を掛ける。
- 実装担当の環境は新しい crate や npm パッケージを取得できないことがある。その場合、依存の追加は設計担当が小さな PR で先に行う。
- T00 と T01 は設計担当（Opus）が実装する。Gemini の権限の設定では、ひな形の作成、`npm install`、ネットワークへの接続（pdfium の取得）ができないため。レビューと報告の書式は Gemini のタスクと同じにする（§2）。

## 2. 1 タスクの流れ

1. オーナーが Gemini にタスク ID を渡す（例: 「docs/work-plan.md の T03 を実装して」）。
2. Gemini は `main` から `task/T03-<短い名前>` ブランチを作り、実装とテストを行う。コミットのたびに pre-commit フック（§2.3）が検査を走らせる。
3. §5 の共通の完了条件をすべて満たしたら、§2.1 の書式で報告を `pr-description.md`（リポジトリの直下、git の管理外）に書き、PR を作るためのコマンドを示す。§2.2 の条件に当たったら、PR を作らずに止める。
4. Opus が §6 の観点でレビューする。指摘があれば Gemini が同じブランチで直し、`pr-description.md` を今の PR の状態に合わせて書き直す。
5. Opus が承認し、CI が通ったら、オーナーがマージする（Squash and merge）。

1 つの PR に 1 つのタスクだけを含める。タスクの範囲外の変更（ついでのリファクタリング、依存の更新など）は含めない。

### 2.1 報告の書式

PR の説明（`pr-description.md`）は日本語で、次の節をこの順にすべて書く。当てはまるものがない節も消さずに「なし」と書く（書き忘れと区別するため）。会話の最後の返答には、報告の中身を繰り返さず、状態（完了 / 中断）と、オーナーが実行するコマンドだけを書く。

```markdown
# T03 画像の読み込み

- 状態: 完了 / 中断
- ブランチ: `task/T03-probe`

## 完了条件の満たし方

work-plan.md の完了条件ごとに、どのテスト・確認で満たしたか。

## 実行したコマンドと結果

実際に実行したものだけを書く。§5 のコマンドと、完了条件が求めた計測値（所要時間など）。

## 設計との差異

差異と、その理由。

## 見つけたが直していない不具合

タスクの範囲外で見つけたもの。

## オーナーに確認してほしい操作

Windows での確認、見た目の確認など、自動化できないもの。操作と、期待する結果を箇条書きで。

## 設計への質問

中断のときは、§2.2 のどの条件に当たったか、試したこと、最後に出たエラーの要点。
```

- 根拠として挙げるファイル、設定、設計の記述は、実在して、その内容が書いてあるものだけにする。

### 2.2 設計担当に相談する条件

次のどれかに当たったら、実装を止め、PR を作らずに、報告の「状態」を「中断」、「設計への質問」に理由を書いて知らせる。自分の判断で押し切らない。

- design.md の決定（プロセスの分け方、ワーカーの役割、パスを渡さない IPC、上限の値など）に反する変更が必要に見えた。
- 依存の追加・更新、ツールの導入、ネットワークへの接続が必要になった。または、必要なコマンドが権限の設定で拒否された。
- work-plan.md・design.md と、実際のコードやライブラリの API が食い違っている。
- 同じ失敗（コンパイル、テスト、clippy、pre-commit フック）を 3 回直そうとして解決しない。
- セキュリティの境界に関わる変更が必要になった（パスを受け取るコマンド、capabilities の権限、CSP、メインプロセスで PDF を開く処理）。

### 2.3 pre-commit フック

- `.githooks/pre-commit` が、§5 のローカルの検査（`cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`、`npm run format:check`、`npm run lint`、`npm run typecheck`、`npm test`）を走らせ、1 つでも失敗したらコミットを止める。人間のコミットも同じ検査を通る。
- フックを有効にする `git config core.hooksPath .githooks` は、オーナーが T00 を渡す前に一度だけ実行する。`.githooks/` ができるまでは何も走らないので、先に設定しておいてよい。同じリポジトリの作業ツリー（`task` と `chore`）は、この設定を共有する。Gemini は git の設定を変えない。
- `--no-verify` などでフックを迂回しない。フックが通らない状態ではコミットできないので、中断するときの報告はコミットせずに `pr-description.md` に置く。
- 文書だけのコミット（設計担当による `docs/` の更新など）も検査が走る。時間がかかっても迂回しない。

## 4. 各タスクの内容と完了条件

### T00 リポジトリと開発基盤の初期化

内容:
- Tauri 2 + React + TypeScript + Vite のプロジェクトを作り、design.md §3 のディレクトリ構成にする。Cargo ワークスペースに `crates/core`、`crates/worker`、`src-tauri` を含める。アプリの識別子とウィンドウの大きさ（既定 1200×800、最小 960×640）を設定する。
- `GEMINI.md` を SVG Tracer のものを元に作る（型、コメント、定数、多言語、コミットメッセージの規約）。あわせて、§2.1 の報告の書式、§2.2 の相談する条件、§2.3 のフックを迂回しない決まりを書く。
- `.githooks/pre-commit`（§2.3）を作る。
- ESLint と Prettier、`rustfmt`、`clippy`（`-D warnings`）の設定は SVG Tracer と同じにする（`any`、型アサーション、非 null アサーション、`class` 宣言を禁止）。
- `.github/workflows/ci.yml`: Windows と Ubuntu で fmt、clippy、`cargo test`、lint、型検査、フロントエンドのテストを回す。ジョブの名前は `Test (ubuntu-latest)` と `Test (windows-latest)` にする（main のルールセットが、この名前のチェックの成功を必須にしているため）。
- `LICENSE`（MIT）。`.gitignore` は SVG Tracer と同じ内容に、`src-tauri/pdfium/` と `spike/` の生成物を加える。
- 既存の `spike/` は残す（スパイクの記録）。ワークスペースには含めない。

完了条件:
- WSL（WSLg）で `npm run tauri dev` を実行すると空のウィンドウが開く。
- CI が両 OS で成功する。
- `any`、型アサーション、`class` を含むファイルを試しに作ると lint が失敗することを確認し、PR の説明に書く（確認用のファイルはコミットしない）。
- `core.hooksPath` を `.githooks` にした状態で、整形の崩れたファイルや失敗するテストを試しに入れると、コミットが止まることを確認し、PR の説明に書く（確認用の変更はコミットしない）。

### T01 pdfium の取得・同梱とワーカーの起動（両 OS で確認）

内容:
- `scripts/pdfium-version.json` と `scripts/fetch-pdfium.ts`（design.md §8.1）。`npm run pdfium:fetch`。
- `src-tauri/src/main.rs` の `--pdf-worker` の分岐と、最小のワーカー: pdfium を読み込み、版を返す要求 1 つだけに応える（本格的なメッセージは T06）。
- `bundle.resources` での同梱と、メインプロセスが `resource_dir()` から場所を求めてワーカーに渡す仕組み（§5.4、§8.2）。
- メモリの上限の仕組み（§5.3）: Linux の `setrlimit`、Windows のジョブオブジェクト。
- CI と、`tauri build` を試すための一時的なワークフロー（`workflow_dispatch`）で、4 種類のインストーラーを作る。

完了条件:
- 4 種類のインストーラー（MSI、NSIS、AppImage、.deb）からインストールしたアプリで、ワーカーが起動し、pdfium の版を返すことを確認する。Windows はオーナーが確認する。確認の手順と結果を PR の説明に書く。
- メモリの上限を超える確保をするテスト用の要求で、ワーカーだけが終了し、メインプロセスが続けて動くことを両 OS で確認する。
- Windows で、メインプロセスを強制終了したときにワーカーが残らないことを確認する。

### T02 フィクスチャの生成

内容:
- design.md §11.1 のフィクスチャを作る `crates/core/examples/gen_fixtures.rs`。生成したファイルをコミットする。
- 暗号化された PDF（閲覧のパスワード付き、制限だけ）の作り方を決めて実装する。
- §11.2 の比較の手順を小さなコードで試し、`COLOR_TOLERANCE` と `MAX_MISMATCH_RATIO_*` の実測値を報告する。

完了条件:
- すべてのフィクスチャがコミットされ、`gen_fixtures` を実行し直すと同じファイルができる（乱数を使う場合は種を固定する）。
- spike の `render-bench`（pdfium）で `encrypted.pdf` が `PasswordError`、`restricted.pdf` が開けることを確認し、PR の説明に書く。
- 実測の不一致率を PR の説明に書く。しきい値は設計担当が design.md に確定してから T04 と T06 で使う。

### T03 画像の読み込み（probe）

内容: design.md §4.1 を `probe.rs` に実装する。

完了条件:
- 対応 4 形式のフィクスチャで、形式、寸法、向き、dpi が期待どおりになるテスト。
- dpi の情報がない、範囲外、単位が不明の場合に 96 になるテスト。
- `corrupt.png` → `DecodeFailed`、テキストのファイル → `UnsupportedFormat`、上限超過 → `TooLarge`。上限超過は画素を読む前に検出されること（ヘッダーだけの画像で確かめる）。

### T04 ページの配置と PDF の書き出し

内容: design.md §4.2、§4.3 を `layout.rs`、`pdf_write.rs` に実装し、§11.2 の画像 → PDF の品質テストを作る。

完了条件:
- 配置のテスト: 「画像に合わせる」の pt の計算（96 dpi と 300 dpi）、A4 の縦と横の選び方、余白、拡大と縮小、`MAX_PAGE_SIDE_PT` を超える場合の縮小、EXIF の向き 8 通りでの幅と高さ。
- 品質テストが全フィクスチャ × 2 つのページの大きさで合格する。JPEG のバイト列がそのまま含まれること、透過が保たれること、向きが正しいことを含む。
- PDF の文書情報に、作成ソフト以外（ファイル名、パス）が含まれないテスト。

### T05 ページの範囲と出力名

内容: design.md §4.5 を `page_range.rs`、§6.4 を `naming.rs` に純粋関数として実装する。

完了条件: 次のケースを含む単体テスト。
- 範囲: `1`、`1-3, 5`、空白、全角の区切りと `〜`、重なりと順序の正規化、`0`、`3-1`、数字でない文字、空文字、ページ数を超える番号の除外、1 ページも残らない場合。
- 出力名: 重なりなし、既存のファイルとの重なり、入力同士の重なり、番号の繰り上がり、大文字小文字の違い、多重拡張子、PDF → 画像の番号の桁数（9 ページと 10 ページの境目、120 ページ）、入力の並び順を変えても結果が同じ。

### T06 ワーカーとワーカーの管理

内容:
- `crates/worker` の `protocol.rs` と `worker.rs`（design.md §4.4、§5.1）。
- `src-tauri/src/worker_pool.rs`（§5.2）。テスト用の要求 `CrashForTest`、`HangForTest` は `test-hooks` 機能のときだけ有効にする。

完了条件:
- ワーカーのテスト: `shapes.pdf` の `Open`（ページ数と大きさ）、`Render`（PNG と JPEG、寸法、背景が白）、`Thumbnail`。`encrypted.pdf` → `PasswordProtected`、`restricted.pdf` は開ける、`corrupt.pdf` → `PdfOpenFailed`、ページ数と描画の大きさの上限。
- 管理のテスト: 異常終了 → `WorkerCrashed`、時間切れ → `WorkerTimeout`。どちらのあとも、次の要求で新しいワーカーが起動して成功する。ワーカーの数が上限を超えない。
- 性能テスト: A4 の 1 ページを 150 dpi で描画して 3 秒以内（`--release`）。
- `test-hooks` を付けないビルドに、テスト用の要求が含まれないこと。

### T07 Tauri 基盤と一覧の IPC

内容:
- `items.rs`（ID の表）、エラーの直列化（§6.6）、ts-rs による型の生成。
- コマンド `add_images`、`add_pdfs`、`remove_items`、`get_thumbnail` と、D&D の `items-dropped` イベント（§6.1、§7）。
- capabilities と CSP（§9）。

完了条件:
- 追加のテスト（一時フォルダ）: フォルダの直下だけを見る、サブフォルダ・隠しファイル・非対応の拡張子・重複の件数、エラーの項目（壊れた画像、パスワード付きの PDF）が一覧に入り理由が付く。
- ts-rs の生成物がコミットされ、CI で「生成し直すと差分が出ない」ことを確かめる手順が動く。
- capabilities に dialog / fs / shell / opener / http の権限がないこと。どのコマンドもパスを引数に取らないこと（PR の説明にコマンドの一覧と引数を書く）。
- Windows と Linux で、画像と PDF を混ぜた D&D がそれぞれの一覧に振り分けられることを確認し、PR の説明に書く。Windows はオーナーが確認する。

### T08 変換の実行（Rust 側）

内容: design.md §6.2〜§6.5 を `jobs.rs` に実装し、`save_merged_pdf`、`start_images_to_pdfs`、`start_pdfs_to_images`、`check_page_range`、`cancel_job` とイベントをつなぐ。

完了条件: 一時フォルダを使う次のテスト。
- 画像 → PDF の「1 枚ずつ」と、PDF → 画像で、成功と失敗が混ざった一覧の成功分が保存され、失敗分の理由が記録される。
- PDF → 画像で、範囲の一部のページがない PDF はあるページだけ、1 つもない PDF は `noPages` になる。途中のページで失敗した PDF は `partial` になり、残りのページが保存される。
- 出力名の重なりが §6.4 どおりに解決され、保存の瞬間に同名のファイルが作られていた場合に上書きしない。
- キャンセル後に新しいファイル（ページ）の変換が始まらず、保存先に一時ファイルも不完全なファイルも残らない。結合をキャンセルすると PDF が作られない。
- 変換中の各コマンドが `ConversionRunning` になる。
- `CrashForTest` を起こす PDF を含む一括変換で、その PDF だけが `WorkerCrashed` になり、残りが変換される。

## 6. レビューの観点

Opus は各 PR を次の観点でレビューする。

1. **設計との一致**: design.md の該当箇所どおりか。差異がある場合、その理由は妥当か。
2. **正しさ**: 境界値、エラー経路、並行処理（ワーカーの貸し出し、時間切れ、キャンセル）の不具合がないか。
3. **テストの質**: 完了条件のテストが揃っているか。実装をなぞるだけで、壊しても通るテストになっていないか（機能を一時的に壊して確かめる）。
4. **セキュリティ**: パスを受け取るコマンドや新しい権限が増えていないか。通信する依存が入っていないか。メインプロセスで PDF を開いていないか。ワーカーがファイルを書いていないか。公開してはならない情報（API キー、トークン、個人のファイルパスなど）が含まれていないか。
5. **規約**: GEMINI.md（型、コメント、定数、多言語、コミットメッセージ）。
6. **範囲**: タスクの範囲外の変更が含まれていないか。

# 事前検証（スパイク）報告

要件定義書 §8 の事項を、小さなプログラムで確かめた結果をまとめる。検証用のコードは `spike/render-bench`（PDF の描画）と `spike/write-bench`（PDF の書き出し）にある。試験用の PDF は第三者のもの（pdf.js のテスト用の PDF ほか）なので、リポジトリには含めない。

- 実施日: 2026-10-04
- 環境: WSL2（Ubuntu）、x64。Windows での確認は、実装の最初のタスクで行う（§6）。

## 1. 結論

| 事項 | 決定 |
| --- | --- |
| PDF の描画エンジン | **pdfium**（`pdfium-render` 0.9.4、ビルド済みのライブラリは bblanchon/pdfium-binaries） |
| 描画を動かす場所 | **別のプロセス**（アプリと同じ実行ファイルを、描画用の引数を付けて起動する） |
| PDF を書く crate | **krilla** 0.8.2 |
| 画像の読み込み | image 0.25（BMP の読み込みと EXIF の向きの取得に使う） |

## 2. 描画エンジンの比較（pdfium と hayro）

試験用の PDF 16 個（透過、合成モード、CMYK、JPEG 2000、CCITT、Type3 フォント、CID フォント、注釈、暗号化、23 ページの論文など）を、150 dpi で全ページ描画した。

| 観点 | pdfium（chromium/8076） | hayro 0.7.1 |
| --- | --- | --- |
| 開けた PDF | 16 / 16 | 15 / 16（暗号化された PDF を開けない） |
| 速さ | 23 ページの論文で 399 ms | 同じ PDF で 1880 ms（2〜5 倍遅い） |
| 正確さ | ほぼ同じ。関数で色を決める CMYK のグラデーション 1 件で、色を誤る | ほぼ同じ。上記の 1 件は正しい |
| 安全性 | C++。壊れた PDF で異常終了しうる | 純 Rust で unsafe を使わない。ただし無限ループやメモリの使いすぎは防げない |
| 配布 | OS ごとにライブラリを同梱（Linux 版 7.8 MB、圧縮して約 3.7 MB） | 同梱するものなし（フォントを埋め込むため、実行ファイルが約 13 MB になる） |

- 2 つの描画結果の一致度（SSIM）は、ほとんどのページで 0.96 以上だった。文字の多いページで 0.95 前後になるのは、文字の縁のぼかし方の違いで、見た目の差はない。
- 一致度が最も低かったのは CMYK のグラデーション（0.90）。PDF の中身を調べると、右上の色は「黄（Y=255）に少し黒（K=64）」と指定されている。pdfium は濃い青に描き、hayro は正しく黄色に描いた。この描き方（ShadingType 1）は実際の PDF ではまれなので、pdfium を選ぶ妨げにはしない。
- **pdfium を選ぶ理由**: 印刷や編集の制限だけを掛けた PDF（閲覧のパスワードはない）も暗号化されており、実際によく見かける。hayro はこれを開けない。暗号化の対応は hayro の README でも未対応と明記されている。パスワード付きの PDF を見分けて専用のエラーを出す（FR-09）にも、pdfium の `PasswordError` が使える。
- **pdfium の弱点への対応**: 異常終了の可能性は別のプロセスで動かすことで扱う（§3）。どちらのエンジンでも無限ループとメモリの使いすぎは防げないので、別のプロセスは hayro を選んでも必要になる。
- hayro は、純 Rust で同梱の手間がないので、暗号化に対応した時点で再評価する。

## 3. 描画を別のプロセスで動かす

- アプリの実行ファイルを、描画用の引数を付けてもう一つ起動し、標準入出力でやりとりする形を想定する。
- 起動して pdfium を読み込み、小さな PDF を開くまでの時間は 10 ms 未満、メモリは約 8 MB だった（Linux）。プロセスを分ける負担は、ほぼない。
- 23 ページの論文を 300 dpi で描いたときのメモリの最大は約 84 MB だった。
- 時間の上限とメモリの上限の掛け方（Linux の `setrlimit`、Windows のジョブオブジェクトなど）、プロセスを使い回すか 1 ファイルごとに起動するかは、詳細設計で決める。

## 4. PDF の書き出し（krilla）

7 種類の画像を 1 枚ずつ PDF にし、pdfium で描画し直して元の画像と比べた。ページの大きさは 1 px = 0.75 pt（96 dpi）とした。

| 入力 | 結果 |
| --- | --- |
| JPEG（RGB） | 元のバイト列がそのまま PDF に入る（`DCTDecode`）。描画し直した結果と元の画像の PSNR は 76.7 dB |
| JPEG（CMYK） | 元のバイト列がそのまま入る。PSNR 30.6 dB（CMYK から RGB への変換の違い。§5） |
| JPEG（EXIF の向き = 90 度回転） | バイト列はそのままで、ページの中で回転させて正しい向きになった |
| PNG（透過、8 ビット） | 透過が保たれた。PSNR 58.6 dB（白の背景に重ねて比較） |
| PNG（透過、16 ビット） | 16 ビットのまま入る。PSNR 56.7 dB |
| WebP（可逆、透過） | 透過が保たれた。PSNR 53.8 dB |
| BMP（32 ビット） | 透過の部分が黒になった（§5） |

- krilla は EXIF の向きを読まない。image の `ImageDecoder::orientation()` で向きを取り、8 通りの向きを変換行列で扱う。
- krilla は PNG、JPEG、WebP を直接読む。BMP は image で読んで、RGBA の画素として渡す。

## 5. 詳細設計で決める事項（検証で見つかったもの）

- **BMP の透過**: 32 ビットの BMP の 4 つ目の成分を透過として扱うかどうかは、規格の上で曖昧で、作ったソフトによって意味が違う。image は今回の BMP の透過を読まなかった。透過を無視して不透明として扱う（黒が出る）か、透過として扱うかを決める。
- **CMYK の色**: CMYK の JPEG を PDF に入れたあとの見え方は、表示するソフトの色の変換に依存する。PDF にはそのまま入れる（FR-02 の「再圧縮しない」）ので、アプリの側で決めることは少ないが、受け入れの基準（NFR-03）で CMYK の JPEG の一致度をどう扱うかを決める。
- **PDF→画像の一致度の基準**: 文字の縁のぼかし方でも SSIM が 0.95 前後まで下がるので、しきい値はこれを考えて決める。
- **pdfium の更新**: ビルド済みのライブラリはほぼ毎週更新されている。Dependabot の対象外なので、版の固定と更新の確認の仕方を決める（NFR-06）。

## 6. 実装の最初のタスクで確かめること

- Windows でのビルド済みライブラリ（`pdfium-win-x64`）の読み込みと、Tauri のインストーラー（MSI、NSIS）、AppImage、.deb への同梱
- Windows で、別のプロセスの起動、異常終了の検知、時間とメモリの上限
- 同梱するライブラリのライセンス（pdfium-binaries に含まれる 14 件）を、第三者ライセンス一覧に自動で入れる方法

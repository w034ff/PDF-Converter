# 整理（FR-12）の設計

[design.md](../design.md) の決まりの上に、整理の機能の設計を置く。画面の見た目はモックアップ（`docs/mockup/project/` の整理の画面）を正とする。時間とメモリの値は試作（Linux と Windows、ワーカーと同じ 2 GiB の上限の中）で測ったもの。

## 1. 出力の作り方

整理の出力は、どの操作でも、新しい文書に元のページを写して作る。元の PDF を開いて書き換えて保存すると、作成者の名前・XMP・削除したページのフォームの値が残り（NFR-01）、操作によって残るものが変わるため。

1 つの出力（1 つの PDF）は、1 つのワーカーが 1 つの要求で、次の順に作る（§3）。

1. **元の PDF を順に開く**。1 つの PDF の使うページを処理し終えたら、すぐ閉じる。pdfium はページを開くたびに文書ごとにフォントや画像を抱えるので、開いたままにすると、メモリがまとめる PDF の合計に比例して増える。
2. **しおりを控える**: しおりの題名・段・行き先（ページと表示の仕方）を pdfium で読む。行き先のページが出力にないしおりは外し、その子を 1 段上げる。行き先のないしおりは、子がなければ外す。
3. **リンクを控える**: 使うページを 1 回ずつ開き、リンクの注釈の矩形と行き先（URL か、ページと表示の仕方）を控える。名前付きの行き先も pdfium が解く。行き先のページが出力にないリンク、URL とページ以外のリンクは外す。リンクは `annotations()` から `as_link_annotation()` で取り出す（`pdfium-render` の `links()` は、リンクとほかの注釈が混ざったページで同じリンクを重ねて返す）。
4. **注釈とフォームを固める**: リンク以外の注釈があるページだけ、一度小さく描いて（外見のない注釈の外見を pdfium に作らせる）、隠していない注釈に印刷の印を付けてから `flatten` する。リンクしかないページは固めない（固めなくても見た目が変わらず、時間が 3 分の 1 ほどで済む）。固めると、そのページの注釈はすべて外れる（リンクも）。
5. **ページを写す**: `copy_pages_from_document` で出力の文書に写し、回転を掛ける。写す時点で初めて失敗する PDF がある（描けるのに写せない）ので、その PDF の失敗として返す。
6. **保存して読み直す**: 出力の文書を `save_to_writer` で、見積もり（§2）の 1.1 倍を先に確保した `Vec` に保存し、pdfium の文書を閉じてから `lopdf` で読む。`save_to_bytes` は `Vec` を倍々に広げ、出力が 512 MiB を超えると 1 GiB の確保が要るため。
7. **付け直す**（`lopdf`）:
   - 写ったリンクの注釈（行き先が元の文書を指したままで使えない）を外し、控えたリンクを出力のページ番号で付け直す。リンクの枠（`/Border`・`/C`・`/H`・`/BS`）は、写ったリンクの注釈から取る（ページの `/Annots` の何番目のリンクかと、矩形の一致で対応させる）。固めたページのリンクは写っていないので、元の PDF から取る（下の「元の PDF を `lopdf` で読む」）。取れなかったリンクは枠なし（`/Border [0 0 0]`）にする。
   - しおりを閉じた状態で付け直す。文字の色と太さは写さない。まとめるときは、各 PDF のしおりを並べた順に続ける（PDF ごとにファイル名のしおりでまとめない。ファイル名を出力に入れないため）。
   - 先頭のページの PDF のカタログから、`/PageLayout`・`/PageMode`・`/ViewerPreferences` を写す。出力にしおりがないときの `/PageMode /UseOutlines` は写さない（空のしおりの欄が開くだけになるため）。
   - 文書情報を作成ソフト（`PDF Converter <版>`）だけにし、XMP を入れない。pdfium が入れる作成日時は時差の表記が誤っているので残さない。
   - 使われなくなったオブジェクトを捨てる（`prune_objects`）。
8. **暗号化する**（パスワードを付けるとき）: `lopdf` の文書にその場で暗号化を掛ける。方式と鍵の扱いは design §4.3.1 と同じ（`crates/core` に、文書を受け取る関数を `encrypt_pdf` から分けて置く）。保存してから読み直して暗号化すると、出力が 2 つ同時にメモリに載るため。
9. **送る**: `lopdf` の `save_to` で、§3 のメッセージの送り手に直接書く。

### 元の PDF を `lopdf` で読む

pdfium-render は、カタログ（表示の設定）と、注釈の辞書の値（リンクの枠）を返さない。そこで、次の PDF に限って、元の PDF を `lopdf` でも読む。

- 先頭のページの PDF（表示の設定のため）
- 固めたページにリンクがある PDF（そのリンクの枠のため）

決まり:

- 読むのは、その PDF のページを処理し終えたあと（元のファイルは変わらないので、pdfium で固めたあとでよい）。読んだ文書は、必要な値を取ったらすぐ捨てる。
- `lopdf` はファイル全体を読む（使うページの数によらない）。最大のメモリはファイルの大きさの 3.7 倍だった（暗号化した PDF。暗号化なしは 2.6 倍。`lopdf` は暗号化した PDF ではオブジェクトの選り分けを使わないので、減らせない）。そこで、読む前に見積もり（ファイルの大きさ × `RAW_MEMORY_FACTOR`）を、予算（`WORKER_MEMORY_LIMIT` − 読む直前のワーカーの使用量 − `RAW_MARGIN`）と比べ、超えるなら読まない。予算を固定の値にしないのは、読む時点の使用量が、先頭の PDF（まだほとんど写していない）と、後ろの PDF（それまでのページを抱えている）で大きく違うため。読まなかったときは、その PDF の固めたページのリンクが枠なしになり、先頭の PDF なら表示の設定が入らない。リンクとしおりは残る。
- 使用量は、上限が数えるもの（Linux は `VmSize`、Windows はコミットされたメモリ）を読む。`RAW_MARGIN` は、使用量に出ない確保の余り（pdfium と確保の仕組みの分）のため。
- 元の PDF にパスワードがあれば、pdfium と同じパスワードを `lopdf` に渡す。`lopdf` は、パスワードの要る PDF をパスワードなしで読むと、エラーにせずページのない文書を返すので、ページの数が pdfium と同じときだけ使う（違えば読まなかった扱い）。
- `lopdf` で読めない PDF も、読まなかった扱いにする（出力の失敗にしない）。
- `lopdf` の `max_decompressed_size` を `RAW_MAX_DECOMPRESSED` にする。オブジェクトストリームは読み込みのときに展開され、既定では展開の大きさに上限がないため。

## 2. 出力の大きさとメモリ

- ワーカーの上限（`WORKER_MEMORY_LIMIT`）は、ほかの要求と同じ値のままにする。整理だけを上げると、変換と並んで動いたときの最悪が増え、事務用の PC（8〜16 GB）で守りが弱くなるため。
- 1 つの出力のワーカーの最大のメモリは、出力の大きさのおよそ 2.8 倍（ページを写し終えた pdfium が 1.6〜1.9 倍、そこに保存したバイト列が加わる所が山。§1 の 6〜9 の形での試作の値。Linux・Windows とも）。2 GiB の中で作れる出力は 600 MB 前後まで。
- そこで、1 つの出力の見積もりが `MAX_ORGANIZE_OUTPUT_BYTES`（512 MiB）を超える整理は、作り始める前にメインプロセスが `OutputTooLarge`（§6）で断る。見積もりは、出力に入る元の PDF ごとに「ファイルの大きさ × 使うページの数 ÷ その PDF のページ数」を足したもの（まとめるときは実際の出力と 1% 以内だった）。分けて保存では、区切りごとの出力で見る。
  - ページを 1 つずつ写すと、ページが共有するフォントなどがページごとに写り、出力の合計が元の何倍にもなる PDF がある（試作で 11 倍）。少ないページを取り出す出力は見積もりより大きくなりうるが、その大きさは小さいので上限には効かない。
- 断るときの文言には、見積もった大きさと、分けてまとめれば作れることを入れる。

## 3. ワーカーの要求

| 要求 | 内容 | 応答 |
| --- | --- | --- |
| `Organize { sources: [{ path, password }], pages: [{ source, page, rotation }], creator, outputPassword }` | 1 つの出力を作る。`pages` は出力の順で、`source` は `sources` の番号、`page` は元の PDF の 0 から数えたページ。`rotation` は 0・90・180・270 で、元の回転に足す。`creator` は文書情報の作成ソフト（メインプロセスがアプリの版から作る）。`outputPassword` は `null` か書き出しのパスワード。開いている PDF があれば先に閉じる | `OrganizeProgress { done }`（処理し終えたページの数）を何度か、`OrganizeChunk`（本体に出力の一部、`OUTPUT_CHUNK_BYTES` まで）を何度か、最後に `Organized { bytes }`（本体の合計）。元の PDF に起きた失敗は `OrganizeFailed { code, detail, source }`、それ以外の失敗は `Error` |

- 出力の順に並んだページのうち、同じ元の PDF で続くものは 1 回の `copy_pages_from_document` で写す。写すたびに pdfium は共有のフォントなどを写し直すので、1 ページずつ写すと出力が大きくなるため。元の PDF は 1 回だけ開き、そのページを出力の位置に差し込む（あとから差し込む元の PDF のページの分だけ、差し込む位置を数え直す）。
- 文書情報の書き直し・暗号化・書き出しは `crates/core` の関数で行う（`lopdf` を持つのは `crates/core` で、pdfium なしでテストできるため）。ワーカーは pdfium の出力のバイト列と、書き出しの送り手を渡す。
- 1 つの要求に複数の応答を返すのは `Organize` だけにする。出力を 1 つの本体で返すと、ワーカーとメインプロセスの両方に出力が丸ごと載り、`MAX_BODY_BYTES` にも当たるため。メインプロセスは受けたそばから一時ファイルに書く（design §6.5）。ワーカーはファイルを書かない。
- 時間の上限は、要求の全体ではなく、応答と応答の間に掛ける（`ORGANIZE_STEP_TIMEOUT`）。全体の時間は出力の大きさに比例し、上限を決められないため。進捗はページを写すたびに送るので、止まったワーカーは見分けられる。
- キャンセルは、ワーカーを強制終了して行う（メインプロセスは一時ファイルを捨てる。NFR-02 の 1 秒）。pdfium の写す・固める処理は途中で止められないため。次の要求では新しいワーカーを起動する。
- 書き出しのパスワードはワーカーに渡す（暗号化をワーカーの `lopdf` で行うため。メインプロセスで暗号化すると、出力を丸ごとメインプロセスのメモリに読むことになる）。扱いは design §6.8・§6.9 と同じ（ログに出さず、`Debug` で伏せる）。

## 4. 画面と IPC

画面はモックアップの `OrganizeEmpty`・`OrganizeSingle`・`OrganizeSplit`・`OrganizeSplit960` を正とする。守る決まりは次のとおり。

- 配置はほかの一覧のタブと同じく、左に設定、中央にページの格子、下に実行のボタン。中央の上に PDF の札を 1 行に並べ、収まらなければ横にスクロールする（PDF が多いとき、札が何行も使って格子を押し下げないため）。追加は「PDF を追加 ▾」の 1 つのボタンにまとめ、ファイルとフォルダを選ぶ（切り出しの「範囲を追加 ▾」と同じ形）。
- ページの札には、元の PDF のページ番号と、どの PDF のページかを、色の点と名前で示す。色だけで見分けさせない（色の見分けにくい人のため）。並べ替えると PDF のページが混ざるので、PDF ごとの見出しで格子を分けない。
- 回したページは、サムネイルを回して見せ、角度を添える。
- 選んだページの上の帯に、選んだ数と「左に回す」「右に回す」「削除」を置く。選んでいない間は押せなくして、帯は残す（出したり消したりすると格子が動くため）。
- 「分けて保存」では、ページの間を押して区切りを入れ外しし、区切りごとの先頭のページに出力の番号を出す。「1 つの PDF」に戻しても区切りは捨てない（行き来して作り直させないため）が、格子には出さない。
- 下部バーには、保存するページの数と出力の数、見積もった大きさ（§2）を出す。上限に近い出力を作る前に、大きさが分かるようにするため。

- 整理の PDF は、一覧の表（`items.rs`）とは別の状態に持つ（切り出しの PDF と同じ。design §6.10）。ID は一覧と同じ数え方で振る。同じファイルが「PDF→画像」の一覧にあっても加えられる。パスワードは整理の PDF の中でだけ使い回す（design §6.8 の規則を整理の一覧に当てはめる）。
- D&D は、整理のタブを表示しているときは整理の一覧に加える（`set_drop_target` に `organize` を足す）。
- コマンド（design §7.1 に足す）:

| コマンド | 引数 | 戻り値 |
| --- | --- | --- |
| `add_organize_pdfs` | `source: "files" \| "folder"` | `{ added: OrganizePdf[], skipped } \| null` |
| `remove_organize_pdfs` | `ids` | – |
| `unlock_organize_pdf` | `id, password` | `{ items: OrganizePdf[] }`（規則は `unlock_pdf` と同じ） |
| `save_organized_pdf` | `pages: { id, page, rotation }[], password` | `{ savedName: string \| null } \| null`（保存ダイアログ。`save_merged_pdf` と同じ形） |
| `start_organize_split` | `parts: { id, page, rotation }[][], password` | –（区切りごとの出力を順に作り、`job-item` を出力ごとに送る。保存先は design §6.5 のとおり確かめる） |

  - `OrganizePdf`: `{ id, name, pageCount, pages: [{ widthPt, heightPt }], encrypted, error }`。`encrypted` は、元の PDF にパスワードがあったか（「元のパスワードは引き継ぎません」の表示のため）。
  - `get_thumbnail` は整理の PDF の ID も受ける。回転は画面がサムネイルを回して見せる（回転ごとに描き直さない）。
  - `pick_output_dir` の `kind` に `organize` を足す。
  - 見積もり（§2）は、メインプロセスが元の PDF の大きさとページ数から求める（ワーカーに聞かない）。`save_organized_pdf` は保存ダイアログを開く前に、`start_organize_split` は何も始める前に、上限を超える出力があれば `OutputTooLarge` を返す。
- 進捗（`job-progress`）は、すべての出力のページの合計で数える。
- 「1 つの PDF に保存」の保存ダイアログの初期ファイル名は、先頭のページの PDF の名前にする。元の PDF と同じファイルを選ぶこともでき（回転だけ直して元を置き換える使い方のため）、OS のダイアログが上書きを確かめる。出力は一時ファイルに書き終えてから置き換えるので、書き終えるまで元のファイルは変わらない。
- 「分けて保存」の名前は `元の名前_{番号}.pdf`（`元の名前` は区切りの先頭のページの PDF の名前）。番号は区切りの通し番号で、区切りの数の桁数で 0 を詰める。重なりは design §6.4 の規則で避ける。
- 整理の設定（design §6.7 に `organize` を足す）: 保存の方法（`single` / `split`）、パスワードを付けるか（`encrypt`）、保存先のフォルダ（`outputDir`）。一覧とページの並び、区切りは保存しない。

## 5. 変えない・入れないもの

- 元の PDF のページラベル、フォームとして入力できる状態、しおりの開閉と書式、開いたときのページと倍率（`/OpenAction`）、元のパスワードと制限は引き継がない（requirements §3.2）。
- 面付け（`FPDF_ImportNPagesToOne`）は使わない。リンクを含むすべての注釈が消え、並び順・余白・区切り線を選べないため。

## 6. エラー

| コード | 状況 |
| --- | --- |
| OutputTooLarge | 整理の 1 つの出力の見積もりが `MAX_ORGANIZE_OUTPUT_BYTES` を超える。`detail` に見積もりと上限を MB の文字列で入れる（上限の数値を画面に書き写さないため） |

- ページを写す時点の失敗（§1 の 5）は、その元の PDF の `PdfOpenFailed` として、出力の `job-item` に元の PDF の ID を添えて返す。「1 つの PDF に保存」では保存しない。「分けて保存」では、その PDF のページを含む出力だけが失敗し、ほかの出力は続ける。

## 7. design.md の決まりの変更

整理を入れるとき、design.md の次の決まりを直す。

- §1・§9「ワーカーはファイルを書かない。読むのは渡された PDF 1 つだけ」→「1 つの要求で読むのは、その要求で渡された PDF だけ」。ファイルを書かないのは変えない。
- §4.3.1・§9「`lopdf` が読むのは krilla がその場で書いた PDF だけ」→ メインプロセスの `lopdf` はそのまま。ワーカーの `lopdf` は、pdfium が書いた出力と、§1 の「元の PDF を `lopdf` で読む」の元の PDF を読む。どちらもワーカーの上限と時間の上限の中で動く。
- §5.1: `Organize` の要求と、1 つの要求に複数の応答を返す形。
- §5.2: `ORGANIZE_STEP_TIMEOUT`（応答と応答の間）と、キャンセルでワーカーを強制終了すること。
- §5.3: ワーカーが自分の使用量を読むこと（Windows ではメモリの量を返す関数の呼び出しが unsafe になるが、`crates/worker/src/system_memory.rs` の例外に加える）。
- §6.6: `OutputTooLarge`。
- §6.7: `organize` の設定。
- §6.9「書き出しのパスワードはワーカーに渡さない」→ 整理ではワーカーに渡す（§3）。
- §7: コマンドと `set_drop_target` の `organize`。
- §10.1: 上部バーのタブが 4 つになる。

## 8. テスト

- 単体（`crates/worker`）: しおりの外し方と段の繰り上げ、リンクの外し方と付け直し（名前付きの行き先、行き先のページの削除、逆順）、枠の対応（写ったリンク・元の PDF・取れないとき）、表示の設定（先頭の PDF、しおりがないときの `UseOutlines`）、文書情報、暗号化した出力が正しいパスワードで開けて違うパスワードで開けないこと、`lopdf` の読む・読まないの判定（予算、パスワードなしで空の文書が返る場合）。
- 見た目（NFR-03）: 出力の各ページを pdfium で描いた結果と、元のページを描いた結果が一致する（回転は回転したものと）。フィクスチャは、フォームと注釈を持つ PDF、しおりとリンクを持つ PDF、見開きの設定を持つ PDF、パスワード付きの PDF。
- 大きさ: 見積もりの計算と `OutputTooLarge`。上限に近い出力がワーカーの上限の中で作れることは、CI では重いので、手動の確認（requirements §7.2）で行う。
- 異常系: 写す時点で失敗する PDF、キャンセル（ワーカーの強制終了と一時ファイル）、応答の間の時間切れ。
- ほかのビューアー（requirements NFR-03）: poppler（Linux）、pdf.js、Acrobat（Windows）で、しおり・リンク・枠・表示の設定を確かめる。手動の確認の手順に入れる。

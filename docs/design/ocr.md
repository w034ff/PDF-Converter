# OCR の設計

[design.md](../design.md) の決まりの上に、OCR の設計を置く。この文書が決めるのは、文字を読む部分（ワーカー）、結果の型と PDF の透明な文字の層（`crates/core`）、ワーカーの要求、確かめるための開発用のコマンドだけ。画面、IPC、メインプロセスでの実行の管理は、導線を決めてから足す（§14）。

数字は試作（`spike/ocr-rs`・`spike/ocr-vertical`・`spike/ocr-textlayer` の各ブランチの報告）で測ったもの。試作は Linux の 4 vCPU の入れ物で動かしたので、時間は入れ物の中の比べにだけ使う。

## 1. 目的と範囲

- OCR は、画像の中の文字を読み、PDF に見えない文字の層を足す。PDF のビューアーで、検索・選択・コピーができるようになる。
- 対象は日本語と英語の活字（横書きと縦書き）。手書き、表の構造（セルの区切り）、ルビは扱わない。
- CPU だけで動かし、通信しない（NFR-01）。モデルはアプリに同梱する。
- 実装は 3 段に分ける。段ごとにテストで確かめられる形で区切る。
  1. **認識**（§3〜§7）: ワーカーがページを描いて文字を読み、結果の型（§2）で返す。
  2. **文字の層**（§9）: `crates/core` が結果を PDF に書き込む。
  3. **組み込み**: OCR を付ける画面と操作、メインプロセスでの実行の管理、IPC。
- **今作るのは段階 1 と 2 だけ**（PoC）。本番と同じ場所（`crates/worker`・`crates/core`）に作り、開発用のコマンド（§12）で出来を確かめる。画面、IPC、メインプロセスには触らない。
- OCR をどの画面のどの操作に付けるか（導線）は、タブの整理と一緒に決める（§14）。段階 3 はそれから設計する。認識と文字の層は、導線がどう決まっても共通の部品になる。

## 2. 結果の型（`crates/core/src/ocr.rs`）

ページ → 塊 → 行 → 単語 → 文字の入れ子にする。

| 型 | 持つもの |
| --- | --- |
| `OcrPage` | `width_pt`・`height_pt`、`engine`（使ったモデルの名前）、`blocks` |
| `OcrBlock` | `bbox`、`orientation`（`horizontal` / `vertical`）、`lines` |
| `OcrLine` | `quad`、`bbox`、`orientation`、`text`、`confidence`、`words` |
| `OcrWord` | `quad`、`text`、`confidence`、`chars` |
| `OcrChar` | `quad`、`text`、`confidence` |

- **座標は表示の向きのページの pt**（`/Rotate` を掛けたあと、左上が原点、y は下向き）。`PageRect`（design §4.6）と同じ空間で、`bbox` は `PageRect` を使う。理由:
  - OCR のために描いた解像度は内部の事情で、ページの大きさや描く長さの上限で変わる。pt は変わらない。
  - 文字の層は pt で書く（§9）。
  - 画面は切り出しの候補をすでに pt から換算している。選択や検索の強調にも同じ換算を使える。
- **位置は 4 点**（`quad`）で持つ。スキャンが傾くと行も傾くので、矩形より文字に沿う。4 点は読む向きの始まりから並べる（横書きは左上・右上・右下・左下、縦書きは右上・右下・左下・左上）。`bbox` は当たり判定のために行と塊に持つ。
- **単語**は、行の文字を空白で区切ったもの。日本語は空白がないので、1 行が 1 単語になる。
- **`engine`** を持つのは、モデルを替えたときに、保存した結果を読み直すべきかを見分けるため。
- 型を core に置くのは、文字の層を書くのが core だから（§9）。ワーカーは core に依存しているので、同じ型を作って返せる。
- serde で JSON にする（ワーカーの応答、§5）。TS の型にするかは、画面を決めるときに決める。

## 3. 方式

- **モデル**: PP-OCRv6 の small（検出 det と認識 rec。PaddlePaddle、Apache-2.0）。onnxruntime（design §8.5 と同じ版）で動かす。理由:
  - 精度: XFUND 日本語（帳票）の CER は 4.3 %。
  - 速さとメモリ: 文字の多い A4 が試作の入れ物で 1.4〜2.5 秒。`WORKER_MEMORY_LIMIT` に収まる（§7）。
  - 大きさ: det 9.9 MB + rec 21.2 MB。
- **前処理と後処理**は PaddleOCR 3.x の既定を写す（BGR で持つ、縮小の丸め、`unclip`、CTC の復号）。試作では、照合の画像で PaddleOCR 3.7 と行の数・文字・並びが一致し、4 隅のずれは最大 2 px だった。
- **入れないもの**（理由は §13）: medium、NDLOCR-Lite の PARSeq、縦書きの字ごとの切り出し（試作の方法 2）、int8 への量子化。

## 4. 認識の流れ（`crates/worker/src/ocr/`）

`layout.rs` と並べて、`ocr/` に置く。試作の `engine.rs`（det・rec・CTC）、`geom.rs`（最小面積の矩形、`unclip`）、`imgops.rs`（縮小と透視変換）、`order.rs`（読み順）が土台になる。

1. **描く**: ページを長い辺 `OCR_RENDER_LONG_SIDE` で、白の背景に描く（PDF → 画像と同じ pdfium の描画）。XFUND を長い辺 1600 px に縮めて読むと CER は 4.02 % で、300 dpi のまま（4.27 %）より良かった。認識は行を高さ 48 に縮めるので、高い解像度で描いても読みは良くならない。描画のメモリと時間も小さく済む。
2. **検出**: DB の後処理で、行の 4 点を求める。輪郭の抽出（二値画像の連結成分）は自分で書く。`imageproc` は `nalgebra` などを引き込むので使わない。
3. **向き**: 行の縦横比が `OCR_VERTICAL_ASPECT` 以上なら縦、その逆数以下なら横、その間はページの多数派に合わせる。縦横比は、行の最小面積の矩形の長い辺と短い辺で決める。試作は 4 点の頂点の順で決めていたので、2° 傾いた縦書きの列の多くを横書きと取り違えた。
4. **認識**: 縦の行は 90° 回して読む。行を幅の順に並べて束ね、束は `OCR_REC_BATCH_LINES` 行か、幅の合計 `OCR_REC_BATCH_MAX_WIDTH_SUM` で切る（幅の広い行が続くページで、rec の出力が大きくなりすぎないため）。辞書は 1 行 1 字のテキストで読む（§8）。
5. **文字の位置**: CTC の各時刻は、縮めた行の決まった幅にあたる。各文字が出た時刻の中心を文字の中心にし、隣との中点を境目にする。行の 4 点に沿って補間して、ページの座標にする。XFUND では、推した箱の中心が正しい字の箱に入るのが 99.6 % だった（字数で等分すると 72.7 %）。縦の行は、回した分を戻す。
6. **読み順**: 試作の `order.rs` の規則で、行を塊にまとめて並べる。
   - 縦書きは列を右から左、列の中は上から下。横書きは行を上から下、行の中は左から右。
   - 見出し（太さが違う）と段（すき間が広い）は別の塊にする。
   - 試作の規則 4（横書きが多い帯は、塊をまたいで行ごとに読む）は、帳票のキーと値を続けて読むためのもの。そのままだと横書きの 2 段組みを左右交互に読む。同じ幅の行が縦に続く塊は段として塊ごとに読み、帳票と分ける。この区別は試作にないので、段階 1 で作ってテスト（§11）で確かめる。
   - 縦書きのページの全文の CER は、並べ替えで 78 % から 10 % になった（残りは読みの誤り）。
7. **確信度で落とさない**: 読み誤った行と、正しい短い行（見出し、ノンブル）の確信度は重なる。落とすと正しい行も失うので、すべての行を返す。

**縦書きの弱点**（受け入れる）: 縦の行の句読点・括弧・長音・小さい「っ」が落ち、大きな字の短い見出しが読めない。縦書きのページの CER は約 10 % に留まる。直す案は §13。

## 5. ワーカーの要求

| 要求 | 内容 | 応答 |
| --- | --- | --- |
| `Ocr { page }` | 開いている PDF の 1 ページを読む（§4） | 本体に `OcrPage` の JSON |

- 結果をヘッダーでなく本体で返すのは、文字の多い帳票の 1 ページで JSON が 560 KB になり、`MAX_HEADER_BYTES` に近いため。本体は `MAX_BODY_BYTES` まで送れる。
- モデルは最初の `Ocr` で読み込み、そのワーカーが終わるまで持つ（small で約 0.15 秒）。読み込めなければ `OcrUnavailable` を返し、そのワーカーは以後の `Ocr` に同じエラーを返す。ほかの要求は続けて受ける。読み込みを試し直さないのは `Detect` と同じ理由（§6）。読み込めたあとの推論の失敗も `OcrUnavailable` で返す。
- 時間の上限は `OCR_TIMEOUT`（最初の読み込みを含む）。
- ワーカーは OCR のモデルの場所を、onnxruntime と layout のモデルと同じく引数で受け取る（design §5.4）。
- 画像から PDF を作るときに OCR を付ける場合も、書き出した PDF のページを pdfium で描いて読む形にする。座標がそのままページの pt になり、EXIF の向きや余白の計算をワーカーで繰り返さずに済むため。PDF をワーカーにどう渡すかは段階 3 で決める。

## 6. onnxruntime の環境

- onnxruntime の環境（`ort` の `Environment`）は 1 つのプロセスに 1 つしか作れない。今の `layout.rs` の `load_session` は自分で `ort::init_from` を呼ぶので、これを分ける。ワーカーは最初の `Detect` か `Ocr` のときに環境を 1 度だけ作り（遠隔計測を切る。design §8.5）、layout と OCR のセッションが共有する。
- 環境を作れなかったときは、以後の `Detect` に `LayoutUnavailable`、`Ocr` に `OcrUnavailable` を返す。一度失敗したあとに `ort::init_from` をもう一度呼ぶと、ワーカーが落ちるため。
- セッションの設定は layout と同じ: 最適化は最大、スレッドは layout と同じ数え方、プールのスレッドの空回りを止める、CPU のアリーナを使わない（design §4.7）。試作では、メモリの大半がアリーナだった。アリーナを切っても速さは変わらなかった（§7）。

## 7. メモリ

- アリーナを使うと、small の仮想メモリは 1.5〜2.0 GB だった（試作の測り方で違う）。`WORKER_MEMORY_LIMIT` すれすれで、pdfium の描画と同時に持つ余裕がない。アリーナを切ると、PARSeq を足しても仮想 1,485 MiB・RSS 753 MiB に下がった。束を幅の合計で切る（§4）ことでも、幅の広い行が続くページのピークを抑える。
- 文字の多いページを、Linux で `WORKER_MEMORY_LIMIT` の下で読み切れることをテストで確かめる（§11）。
- layout のモデルと OCR のモデルを 1 つのワーカーで同時に持つと、メモリの余地が狭まる。どのワーカーで OCR を回すか（解析のワーカーのような専用のものか、プールか、並べる数）は、段階 3 でメインプロセスの設計と一緒に決める。

## 8. モデルの用意・取得・同梱

- **用意**: 維持する人が `scripts/prepare-ocr-model.py`（仮）を一度だけ実行し、このリポジトリの GitHub Releases（`ocr-model-N` のタグ）に置く。元は Hugging Face の PaddlePaddle の PP-OCRv6 small の ONNX で、コミットとハッシュを固定して照合する。rec の `inference.yml` の辞書は、1 行 1 字のテキストにして一緒に置く。アプリが YAML を読まずに済むため。layout のモデル（design §8.5）と同じく、ネットワークを切ったコンテナで変換する。
- **取得**: `scripts/fetch-layout.ts` に OCR のモデルを足し、`scripts/layout-version.json` に版と SHA-256 を置く。取得先は `src-tauri/ocr-model/`。取得したものはコミットしない。onnxruntime を共有するので、取得の道具も 1 つにまとめる。
- **同梱**: 段階 3 で、layout のモデルと同じく `bundle.resources` で同梱し、`resource_dir()` から場所を求めてワーカーに渡す。インストーラーは約 31 MB（圧縮前）大きくなる。PoC では同梱しない。同梱すると、アプリのビルドがモデルを要るようになるため。PoC の間も、メインプロセスはワーカーに OCR のモデルの場所を渡す（ファイルがなければ `Ocr` が `OcrUnavailable` になるだけ）。
- **ライセンス**: Apache-2.0 の全文と、改変の表示（辞書の形式を変えた）を `scripts/ocr-model/` にコミットし、第三者ライセンス一覧に加える。

## 9. 文字の層（`crates/core/src/text_layer.rs`）

```rust
/// `pages` は (ページの番号 0 始まり, そのページの OCR の結果)。
pub fn add_text_layer(doc: &mut lopdf::Document, pages: &[(usize, &OcrPage)]) -> Result<(), PdfWriteError>;
```

- **lopdf で書く**。画像 → PDF もスキャンの PDF も同じ関数を通す。krilla は見えない文字（`3 Tr`）も縦書きの CMap（`Identity-V`）も書けないため。画像 → PDF は今どおり krilla で画像のページを書き（PDF/A-2b の検証も krilla のまま）、その出力を lopdf で読んで層を足す。パスワードを付けるときは、層を足してから暗号化する（`encrypt_document`）。試作では、層を足した PDF が veraPDF の PDF/A-2b を通り、AES-256 で暗号化しても文字を取り出せた。
- **字形のないフォント**を文書に 1 組だけ入れる。字の種類によらず約 1.5 KB で、どの字も書ける（本物のフォントでは、ない字が `.notdef` になり、ToUnicode も壊れる。OCR の辞書は簡体字も含む）。フォントの本体を同梱しなくて済む。**字形には em の四角の輪郭を入れる**。輪郭が空だと、pdfium（アプリ自身と Chrome・Edge）の取り出しで文字が消える。
- **字ごとに置く**。字ごとに位置（`Tm` / `Td`）を置き、横書きは字ごとの `Tz` で幅も合わせる。縦書きは `Identity-V`。縦書きの列を 1 つの文字列にすると、pdfium は列を左から右へ並べる（全文の一致 41 %）。横書きも字ごとのほうが箱が合い（95 % → 100 %）、余計な空白も出ない。費用は 1 ページ約 2.3 KB。
- **すでにある PDF の座標を直す**: `/Rotate`（90°・180°・270°）、MediaBox と CropBox の原点のずれ、`UserUnit`。結果の座標は表示の向きのページの pt なので、ページの空間に戻して書く。親（`Pages`）から継承した `/Resources`、配列の内容のストリーム、参照の `/Font` も扱う。
- 試作で確かめたのは pdfium・poppler・mutool だけ。Acrobat Reader での選択・コピー・検索は、段階 2 の終わりに、開発用のコマンド（§12）で作った PDF を Windows で手で確かめる（縦書きのコピーで字の間に改行が入らないか、印刷で層が黒く出ないか）。

## 10. エラー

- `OcrUnavailable`: onnxruntime か OCR のモデルを読み込めない、または推論に失敗したとき。`LayoutUnavailable` と分けるのは、モデルを別々に取得・同梱するので、画面でどちらが欠けたかを言い分けたいため。
- PoC では、worker だけのコード（`WorkerOnlyCode`。今の `PdfiumUnavailable` と同じ扱い）にする。core の `ErrorCode` に足すと TS の型が変わり、画面の文言まで要るため。段階 3 で、画面の文言と一緒に `ErrorCode` に移す。

## 11. テスト

- **照合**: PaddleOCR の照合の画像（`ja.jpg`）で、行の数・文字・並びが PaddleOCR 3.x と一致し、4 隅のずれが 2 px 以内であること。期待値の JSON はフィクスチャに置く。画像はライセンスを確かめてから置く。置けなければ、生成したページで PaddleOCR の出力を期待値にする。
- **生成したページ**（`crates/core/examples/gen_fixtures.rs`、IBM Plex で描く）:
  - 横書き、縦書き（見出しの列と本文、上下 2 段）、横書きの 2 段組み、帳票ふうのキーと値で、塊の数と並びが期待どおりであること。
  - 2° 傾けた縦書きのページで、列を縦と判定すること。
  - 文字の位置が行の 4 点の中にあり、読む向きに並ぶこと。
- **メモリ**: Linux で、文字の多いページの `Ocr` が `WORKER_MEMORY_LIMIT` の下で通ること。
- **使えないとき**: モデルがないと `OcrUnavailable` を返し、続く `Ocr` も同じエラー、ほかの要求は通ること。`Detect` のあとの `Ocr`（逆も）が、環境を共有して通ること。
- **遠隔計測**: `Ocr` のあとにホームの下に何も作られないこと（今の layout の試験に足す）。
- **文字の層**: pdfium で取り出した全文が結果と一致し、検索で当たり、字の箱の中心が結果の 4 点の中にあること。回転したページ（90°・180°・270°）、CropBox の原点がずれたページ、継承した `/Resources`、暗号化した PDF、PDF/A-2b（krilla の検証）でも同じこと。
- モデルが要るテストは、layout と同じく取得したモデルで動かす。CI でも取得する。

## 12. 開発用のコマンド

PoC の出来を、画面なしで確かめるための入口。`crates/worker/examples/ocr_pdf.rs` に置く。

- PDF を受け取り、全ページを OCR し、文字の層を付けた PDF を書き出す。指定すれば、ページごとの `OcrPage` の JSON も書き出す（読み順や確信度を見るため）。
- 本物のワーカー（`pdfconv-worker`。テストが使う単体のワーカー）を起動し、`Open` と `Ocr` を送る。ワーカーの中で `WORKER_MEMORY_LIMIT` の下で読むので、メモリの確かめにもなる。文字の層は、入力の PDF を lopdf で読んで `add_text_layer`（§9）で足す。
- pdfium、onnxruntime、モデルの場所の既定は、取得の道具が置く場所（`src-tauri/` の下）にする。
- 画像を試すときは、今の画像 → PDF で PDF にしてから渡す。
- 開発用なので、アプリには入れない。エラーは標準エラー出力に出して終わる。

## 13. 入れないもの

- **medium**: 帳票の CER は 0.65 ポイント良いが、約 4 倍遅く、モデルは 139 MB。6 行ずつ束ねると仮想 2.65 GB で `WORKER_MEMORY_LIMIT` を超える。
- **NDLOCR-Lite の PARSeq**（縦の行だけ回す案）: 生成した縦書きでは CER 9.8 % → 1.1 % だが、実際の昭和のスキャンでは差が小さい。モデルは 117 MB、読み込みに 2〜9 秒、CC BY 4.0 で帰属の表示が要る。PARSeq を足すとメモリが `WORKER_MEMORY_LIMIT` を超えた（アリーナを切ると収まった）。
- **縦書きの字ごとの切り出し**（試作の方法 2。モデルを足さない）: きれいな縦書きでは CER 12 % → 0.7 %、見出しも読めた。昭和のスキャンでは効果がわずかで、帳票の縦の欄を壊すので守りが要る。決める前に、現代の縦書きのスキャンで正解付きの材料が欲しい。入れるなら §4 の 4 の縦の行の読み方を差し替える形になり、結果の型は変わらない。
- **int8 への量子化**: 試していない。small は量子化しなくても 31 MB。
- 横書きの 3 段以上の複雑な段組み、表の構造、ルビ。

## 14. 決めていないこと

段階 3 の前に決める。PoC（段階 1・2）はどれにもよらない。

- **導線**: OCR をどの画面のどの操作に付けるか。今のタブの整理と一緒に決める。決めたら `requirements.md` に FR を足す。OCR の使われ方には性格の違う 2 つがある。
  - **検索できる PDF を作る**: 文書の単位の一括の処理。画像 → PDF や整理の保存に、選択肢として付ける形が考えられる。
  - **ページを見て文字を取る**: ページの単位で、見ながらの操作。切り出しの延長（範囲の文字をコピー）として付ける形が考えられる。選択の画面は、画面の土台（Tauri か Slint か）で作りが変わる。
- **文字がすでにあるページ**（デジタルの PDF、前に OCR したページ）を飛ばすか、上書きするか。
- 縦書きの改良（§13 の方法 2）を最初の版に入れるか。
- **PoC を main に取り込むか**。取り込むと、使う画面のないコードが main に入り、CI でモデルを取得する時間が増える。取り込まなければ、main から離れていく。
